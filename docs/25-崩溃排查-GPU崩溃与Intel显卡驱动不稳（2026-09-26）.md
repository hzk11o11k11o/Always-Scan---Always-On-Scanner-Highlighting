### 2.2 09-22 ~ 09-25 的 CPU 崩溃：崩溃线程栈里**零个**本 DLL 的返回地址

那一段（12 条 WER APPCRASH、7 份转储）是另一种形态：
`code=C0000374（HEAP_CORRUPTION）`、`addr=ntdll.dll+0x112165`、`params=[ntdll+0x1CC0E0]`，
**7 份转储签名逐字节相同**。用 `tools\re\dmpinfo.py` / `dmpdeep.py` 深查：

* 崩溃线程（tid 每次不同）的栈（捕获 11 KB）**全部落在 Intel 显卡驱动与 D3D12 之间**：
  `igc-default64.dll`（Intel 图形编译器 / JIT 代码）→ `igd12um64xe3.dll`（Intel D3D12 UMD）→
  `D3D12Core.dll` / `D3D12.dll` → ntdll 的堆错误上报路径；
* `dmpdeep.py --stack SAS_AlwaysScan` ⇒ **`SAS_AlwaysScan.dll` 的返回地址 0 个**；
* 唯一非驱动帧的线程（tid=35292）是游戏自己的主机（`Starfield.exe+0x2A19BA2`）。

## 三、依然保留的不确定性（如实记录）

* 无法 100% 排除「本 MOD 增加的高亮渲染负载是催化剂」——
  历史数据里**始终存在某个高亮 mod**（09-13/14/15 是上一代 mod、09-16 起是本 MOD），
  没有「完全无高亮 mod 且长时间游玩」的对照样本；
* 今天崩溃频率明显偏高（1 小时 5 次 vs 平时一天 1~2 次），
  但没有任何证据指向本 MOD 的代码路径（见 §1.2 / §1.3）。

**⇒ 建议做一次对照实验（比任何分析都直接）**：把本 MOD **F8 关掉**（或 MO2 里禁用本 mod）
玩 15~30 分钟（最好去今天崩溃的那个星球地表），若**仍出现 GPU 崩溃** ⇒ 与本 MOD 无关，属驱动/硬件；
若不再崩溃 ⇒ 回头查「高亮渲染 + Arc 驱动」的组合。

## 四、下一步建议（按性价比排序，都不涉及改代码）

1. **对照测试**（同上，先做这个）。
2. **显卡驱动**：当前 32.0.101.8974（2026-08-11）。到 Intel 官网 / Arc Control 看是否有新版；
   若刚更新过则考虑回退到上一版（GPU 崩溃从 09-13 开始，注意驱动包 08-25 才装）。
3. **画质设置**：`Documents\My Games\Starfield\StarfieldPrefs.ini`（09-25 22:30 被改过）
   目前开着 **帧生成**（`uiFrameGenerationTech=2`）、**动态分辨率**（`bDynamicResolutionEnabled=1`）、
   渲染分辨率 50%（`fRenderResolutionScaleFactor=0.5000`）—— 帧生成/动态分辨率是 Arc 上
   常见的掉驱动来源，先关掉帧生成与动态分辨率各试一局。
4. **清掉过老的着色器缓存**：`%LOCALAPPDATA%\Starfield\Pipeline.cache`（146 MB，09-08 生成）
   —— 删掉后游戏会重建（安全，代价是首次进游戏编译略慢）。
5. 出现 GPU 崩溃后**重启电脑**再玩（D3D12 设备丢过一次后驱动状态往往已经不干净）。

## 五、顺带发现的一个「取证能力」缺陷（与本轮崩溃无关，但吃掉了现场）

AGENTS 需求原文是「日志文件不能超过 1M，旧内容要做到**滚动删除**」，
而 `plugin\src\main.cpp` 的 `SizeLimitedFileSink` 是**整文件清空重来**：

```59:63:plugin/src/main.cpp
			// 先判断后写：最多超出「单条消息」的字节数，之后从 0 重算。
			if (_bytesWritten + formatted.size() > _maxBytes) {
				_file.reopen(true);
				_bytesWritten = 0;
			}
```

后果（今天真实发生）：会话 D 于 **17:05:31** 启动时日志已到 1 MiB ⇒ 第一条日志就把旧内容清空，
**16:57 / 16:59 / 17:04 三个会话（含 4 次 GPU 崩溃前的现场）全部丢失**，只剩会话 D。

⇒ 建议改成「滚动保留最后一段」：超限时把**尾部约 512 KiB** 另存为 `SAS_AlwaysScan.log.prev`
（或按行丢弃最旧 1/4），这样下次崩溃能直接对着日志看现场。属小改动（只动 `main.cpp` 的 sink），
**待用户确认后实施**。

## 六、本次用到的排查手法（可复用）

| 手法 | 命令 / 工具 |
| --- | --- |
| 列全部 Starfield 崩溃报告 | `Get-ChildItem "C:\ProgramData\Microsoft\Windows\WER\ReportArchive" -Directory \| ? Name -like "*Starfield*"` |
| 列全部转储 | `Get-ChildItem "$env:LOCALAPPDATA\CrashDumps" -Filter "Starfield*"` |
| 转储速览（异常 / 模块 / 栈） | `python tools\re\dmpinfo.py <dmp>` |
| 转储深查（线程 / 栈上某模块返回地址） | `python tools\re\dmpdeep.py <dmp> --threads` / `--stack SAS_AlwaysScan` |
| **游戏自己的 GPU 崩溃报告** | `Get-ChildItem "$env:LOCALAPPDATA\Starfield" -Filter "GPU_CRASH*"`（本次决定性证据） |
| GPU 崩溃现场命令流 | 解压 `GPU_CRASH__*.zip` 里的 `temporaryFile-InterruptedGPUCommandLists.txt`，看尾部 |
| 会话次数 / 时长（游戏本身不记） | Papyrus 日志轮转：`Logs\Script\Papyrus.0..3.log` 的 **首行 `Papyrus log opened`** |
| 系统层崩溃 / 挂起 | `Get-WinEvent -FilterHashtable @{LogName='Application'}`（APPCRASH / AppHang）与 `LogName='System'`（BSOD 1001） |
| 装过什么 mod / 何时 | `Get-ChildItem "D:\Mod Organizer 2\starfield_mods\mods" -Directory \| select Name,CreationTime` |

★ 关键经验：**游戏自己会把 GPU 崩溃写成文件**（`GPU_CRASH__*.zip`），
以后再遇到「无转储的崩溃 / 无响应的闪退」，**先看这个目录** —— 它能一眼区分
「CPU 侧异常崩溃」与「GPU 设备丢失」，后者根本不是 mod 代码能直接造成的形态。
