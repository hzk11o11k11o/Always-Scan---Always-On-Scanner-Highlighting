# 44 · key1 兜底「组件缺失」（v5.2 / 订正 R11）

> 用户报告（原文，2026-09-27）：
>
> ```
> 再次出现已扫描物件还是扫描前青色的现象，而且这次开关扫描仪都没自我修复，
> 从我的观察来看，新高亮的物体容易出现这个问题
> ```

结论：**R10 的「现读」确实生效了（`ready=1`），但直读判据仍然零成功查询** ——
每条查询都在第一步 `stage=3`（`0x81 组件拿不到`）失败。原因是**我们对 key1
（物种/资源 ID）的复刻只做了组件主路径，而植物引用根本没有 `0x81` 组件** ——
引擎自己 (0x7BCBD0) 会调 `0x910690` 兜底把 key1 找出来，**引擎画绿走的就是这条兜底**。

## 二、根因（离线反汇编 + 运行时证据，全部实证）

引擎取 key1 有**两级**（`0x7BCBD0` 反汇编，`tools/re/disasm.py`）：

```
007BCBE0  … r15 = rcx（ref）
007BCBF1  mov dl, 0x81
007BCBF3  mov rcx, [rcx + 0xc8]     ; 容器 = [ref+0xC8]
007BCBFA  call 0x347170             ; GetComponent(容器, 0x81)
007BCC18  test rax, rax
007BCC1B  je 0x7bcc50               ; ★ 组件缺失 → 兜底
007BCC29  cmp dword [rcx], edx      ; 或 [comp+0x28] == 0 → 兜底
007BCC2D  mov eax, [r9 + 0x28]      ; 主路径：key1 = [comp+0x28]
…
007BCC50:                           ; ★ 兜底入口
007BCC63  xor r9d, r9d
007BCC66  mov r8, r15               ; ref
007BCC6E  lea rdx, [rsp+0x30]       ; ctx（16 字节，全 0）
007BCC73  call 0x910690             ; ★★ 兜底：从 cell / 世界空间 / 全局把 key1 找出来
007BCC7A  mov [rsi], ecx            ; key1 = 兜底结果
```

* **`0x910690` 第一段**（0x9106BC）也是 `GetComponent([ref+0xC8], 0x81)` —— 组件在时与
  主路径同源；**缺失时**走长链（parent cell → 世界空间 → 关联 form 列表 →
  `0xAC2700` 映射 → `0x5DE3B0` / `0x786690` 反查 → 全局 `[0x5FD9C30+0x80]` 兜底值）。
* **`0x2C5C90` vs `0x347170`**（关键旁证）：`GetOutlineState` 用的 bool 版**只查
  「组件存在位图」** `[容器+0x18]`；指针版 `0x347170` 还要**遍历组件链表**
  `[容器+0x8]` 比对 `[节点+0x12] == id`。两者对 `0x2A` 组件都正常（`GetOutlineState`
  工作正常）⇒ **`[ref+0xC8]` 容器解读没错，是 `0x81` 这个位图位/链表节点真的不存在**
  —— 植物 ref 上**没有** `0x81` 组件。
* **`0x81` 组件的创建点在别处**（`0x502A35` / `0x51B485` / `0x51B5EA` / `0x51B787` /
  `0x522F52` 五处写 `[节点+0x12]=0x81`；创建时 `[comp+0x28]`（key1）初始为 0，之后才被填）
  —— 它挂在**别的宿主**上（不是每个植物引用）。
* ⇒ R10 文档里「`0x7BCBD0` 主路径 = ……（与实现一致）」是**未经运行时验证的推断**，
  本次被实测证伪：**主路径不是常态路径，兜底才是**。

## 六、经验

1. **「复刻引擎的某一步」要把这一步的『全部入口』数清楚**：0x7BCBD0 有两个 key1 来源
   （组件 + 0x910690 兜底），R10 只按反汇编的**前 30 行**复刻了组件路径 ——
   而运行时数据证明兜底才是常态。**看函数要看到所有 return / 所有分支出口**。
2. **「实测 stage」比「离线推断主路径」可信**：R10 文档写「主路径与实现一致」时没有任何
   运行时证据；本次 `stage=3` 100% 复现，一局日志就推翻了它。
3. **两个同类函数要对照着看**（`0x2C5C90` 只查位图 vs `0x347170` 位图+链表）——
   「工作正常的那个」能证明「数据/容器没错」，剩下的只能是「目标组件真的不存在」，
   把排查空间一次砍半。
4. **诊断要分层可枚举**（R10 的 `stage`）+ **每条路径要有可数的证据**（R11 的
   `k1来源=` / `兜底K1=`）——连续三轮都靠「一局日志里的一行」定位根因。
5. **「间接调用过」可以给「直接调用」背书**：`0x910690` 的副作用面不是靠静态审计
   （那条链太深），而是靠「我们早已通过 `0x1306E80` 每 5 秒间接调用它、跑了好几个版本
   没出问题」这一运行时事实 —— **历史行为是最便宜的审计**。
6. **签名校验失败的降级要分级**：兜底签名不符**只关兜底**（组件路径照常），
   而不是像 R9 那样把整条判据禁用（那次的教训）。
