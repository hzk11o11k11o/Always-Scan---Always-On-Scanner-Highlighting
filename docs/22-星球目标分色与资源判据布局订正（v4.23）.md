## 一、需求 2 的真根因：BSTArray 布局读反（离线 + 二进制双重证据）

### 1.1 ★ 离线证据（commonlibsf 头文件，逐行）

`tools/commonlibsf-main/include/RE/B/BSTArray.h`：

```cpp
// 第 52 行：
std::uint32_t _size{ 0 };      // 0
std::uint32_t _capacity{ 0 };  // 4
static_assert(sizeof(BSTArrayBase) == 0x8);

// 第 135 行：
template <class T, class Allocator = BSTArrayHeapAllocator>
class BSTArray : public BSTArrayBase, public Allocator
{ …
    // 第 380 行（唯一的成员）：
    void* _data{ nullptr };
};
static_assert(sizeof(BSTArray<void*>) == 0x10);   // 0x8 + 0x8 ⇒ data@+0x08
```

⇒ 正确布局 = **`_size@+0x00 / _capacity@+0x04 / _data@+0x08`**。

而 `TESObjectMISC`：`BGSKeywordForm` 基类 @**+0x1E8**（`RE/T/TESObjectMISC.h`），
`BGSKeywordForm::keywords` 在基类 **+0x20**（`RE/B/BGSKeywordForm.h`）
⇒ MISC 的关键词数组头在 **base + 0x208**（这一条一直是对的，错的是**字节序**）。

### 1.2 ★ 旧代码错在哪（当时的注释还特意写了「不套用」）

`plugin/src/AlwaysScan.cpp`（v4.17~v4.22）：

```cpp
// BSTArray 头（★ 这个数组的布局是 data 在前、size/capacity 在后）   ← ✗ 反了
const auto data = *reinterpret_cast<const std::uint64_t*>(raw + 0x208 + 0);   // 读到的其实是 size|cap<<32
const auto size = *reinterpret_cast<const std::uint32_t*>(raw + 0x208 + 8);   // 读到的其实是 _data 低 32 位
const auto cap  = *reinterpret_cast<const std::uint32_t*>(raw + 0x208 + 12);  // 读到的其实是 _data 高 32 位
```

* `data` = `size | capacity<<32`（例如 size=4/cap=4 → `0x0000000400000004`）⇒
  `IsPlausiblePointer` 否掉（用户态指针不可能这么小）⇒ **每个 MISC 都返回 false**；
* 同一份代码里 **cell 引用数组**用的是 `kOffArraySize/Capacity/Data = 0x00/0x04/0x08`
  （**一直是对的**，本 MOD 的高亮能工作就靠它）—— 偏偏这里当初写了一句
  「与常量区那一套不同，这里不套用」，把唯一正确的那套否掉了。

### 1.3 ★ 用户那一局日志完全吻合这个判定（`out` 已留档）

```
[09:51:59] [I] category (本轮选中): loot=24, weapon=24, apparel=24, ammoaid=0, note=24,
                             resource=0, container=0, …          ← 46 条统计行里 resource 恒为 0
[09:51:54] [W] resource keyword: 自检正样本还没进内存（7 个样本只拿到 1 个；第 1 次尝试）
                             -> 「资源」判据**仍在生效**（形状校验兜底），首次命中会另行打一条 INFO
（整个会话没有一条 `resource keyword: 判据自检**通过**` / `首个资源命中`）
```

* 唯一在内存里的那个正样本**也没命中** —— 如果只是「样本不在内存」，不会连它在内存时都不命中；
* 「兜底」理论上兜得住（形状校验），可**形状校验本身用的是错的布局** ⇒ 兜底也是空的；
* ⇒ 「资源和杂物同色（都是原版扫描仪的蓝色）」= 资源被静默归入杂项（state 2 蓝）。

### 1.4 修法（本次）

1. **布局订正**：`ScanKeywordsAt` 用 `kOffArraySize/Capacity/Data`（+0/+4/+8）读头；
2. **空数组合法化**：`size==0 && cap==0` 视为「合法空数组」（Credits 这类 MISC 是一个
   关键词都没有的 —— 旧代码把它当成「形状不对」，会污染标定判断）；
3. **偏移自适应**：候选表 `{0x208, 0x200, 0x1F8, 0x210, 0x218}`，逐个试，
   **第一个「形状合格且非空」的偏移被采纳并缓存**（会话级；同 `kCellRefsOffCandidates`
   的手法）。校验 = 头自洽（`1 ≤ size ≤ 64`、`size ≤ cap ≤ 4096`）∧ `data` 可读 ∧
   **每个元素都是 KYWD 记录**（能挡住 `0x1F8` = `formFolderKeywordLists` 这种
   「也是 BSTArray 但元素不是关键词」的邻居）；
4. **诊断两行**（下次复盘一眼定性）：
   * 找到读法：`resource keyword: 关键词数组标定 = base+0x208（布局 size@+0 / capacity@+4 /
     data@+8；首样本 base=0x… n=… kw=[…]）-> …`；
   * 全都不合格：`misc kw probe: base=0x… 候选偏移全不合格 … 原始读数 0x208(s=…,c=…,d=0x…) …`
     （≤6 条/会话；把这行发出来就能定位偏移 / 布局又漂到哪去了）。

> ★ 门控保持不变：`resKeywordTest != 2`（默认生效，只在拿到明确反证时否决）；
> 自检的 7 个正样本池、500ms 节流、负样本（Digipick / Credits）都在。

## 二、需求 1：星球扫描目标为什么「完全不显示」，以及怎么同时满足三个约束

### 2.1 引擎侧事实（反汇编 `0x159ED90`，本轮复核，`out/dis_159ED90.txt`）

原版扫描仪的**逐引用求值函数**（唯一会写 outline 状态的地方）产生的状态：

```
0159F13E  mov byte ptr [rbp + 0xe8], al    ; al = (距离² ≤ 阈值) —— **「是不是在扫描范围内」**（不是「已扫描」）
0159F61E  add edx, 7                       ; ⇒ state 7 / 8（= 远 / 近 的可扫描目标）
0159F63C  add edx, 2                       ; ⇒ state 2 / 3（另一组）
0159F643  setne dl                         ; ⇒ state 0 / 1（通用）
0159F601  mov edx, 0xa                     ; ⇒ state 10（另一类目标）
0159F31B  mov edx, 9                       ; ⇒ state 9（**正在扫描的那个对象**，条件是 [ref+0xF67] ≠ 0）
```

* 「扫描前 / 扫描后 / 正在扫描」的差别全部来自**引擎自己**往 7 / 8 / 9 / 10 写的东西，
  而这些槽位的**配色块我们一旦覆盖就没了**（v4.17~v4.21 就是借了 state 7 当资源色）；
* 用户上一轮的要求（原文）：「这两个状态保持游戏原版颜色即可」⇒ v4.22 归还 7/8，
  但顺手把整个「植物」类别关掉了 —— 于是**星球上什么都看不到**（原版只在举着扫描仪时上色）。

### 2.2 v4.23 的设计：三个约束同时满足（这是本轮的核心）

| 约束 | 做法 |
| --- | --- |
| 不举扫描仪时**看得见**（本 MOD 的立身之本） | 「植物」类别默认开，state = **7**（原版 `TargetScannable`），`ColorFlora` **不覆盖** ⇒ 用的是**原版那个青色脉冲轮廓**（脉冲 High `#72E8FF` / Low `#115B69`、基色 alpha=0 = 不填充），不是 MOD 自造色；且与「杂项蓝 / 资源紫 / 弹药绿」区分得很开 |
| 举着扫描仪时**原版说了算**（扫描前 / 扫描后能区分） | 新增 `YieldTargetsWhileScanning=1`：`MonocleMenu` 开着时，**这一类**不进候选集合（不挂新、不重申），并且 `SyncNativeOutline` 第 1 步**不给它排摘除**（否则 ~1.5 秒后会把管理器里那条 highlight 摘掉 —— 而那正是原版在用的槽位） |
| 「屏幕中央圆圈之外也高亮」不回归 | **只让这一类让位**，其余类别（武器 / 服饰 / 弹药 / 笔记 / 资源 / 容器 / 尸体 / 设备 / 门）照常重申 —— 引擎建扫描仪 HUD 时会销毁管理器 + 清空状态表（`0x17D4B30`，见 v3.2），整段停摆就等于举着扫描仪时圈外也不亮了 |

放下扫描仪那一刻，v3.2 的 `DetectEngineOutlineLoss`（`MonocleMenu` 由开变关）会把
已挂条目整批转入「待重申」，按每轮预算（默认 64 条）铺回青色常亮（约 0.8 秒）。

### 2.3 「动物」（活着的生物 / NPC）为什么不归本 MOD

* 红线不变：**活的东西一个都不亮**（活人 / 活生物）。动物属于 ACHR，按 `lifeState` 判活 ⇒ 跳过；
  它们由**引擎自己**在扫描时上色（state 7/8/9），本 MOD 不碰 —— 这正是用户要的「保持原版颜色」；
* 死了的生物（尸体）走「尸体」类别（橙），照旧。

## 六、可复用经验

1. **「形状校验」的前提是布局本身正确**：v4.17 就给资源判据配了三层形状校验，
   但因为**第一层读法**（BSTArray 的字节序）是错的，校验链再严密也只是把
   「读不到」包装成「不命中」⇒ **静默失效比崩溃更难查**。
   教训：凡是「读一个结构体」的代码，都要把**结构体的成员顺序**在注释里
   逐行引到**头文件的行号**（本轮就这么做了），别凭印象。
2. **同一个文件里出现两套互相矛盾的布局约定 ⇒ 一定是其中一套错了**。
   cell 引用数组用 `size/cap/data`，MISC 关键词数组用 `data/size/cap` ——
   同一种 C++ 类型不可能两种布局；当初那句「这里不套用」就是需要立刻停下来核对的红旗。
3. **「交还原版」必须先把「原版什么时候显示」问清楚**：原版扫描仪的高亮只在
   **举着扫描仪**时存在（`MonocleMenu` 生命周期内），把类别关掉 ≠ 交还原版，
   而是「什么都没有」。正确姿势 = **归还原版槽位 + 让位窗口**（我们让开、它来画）。
4. **让位的粒度要按「槽位归属」来定，不是「全部停摆」**：只有 state 7/8（及临时 9/10）
   是原版在用的槽位；其余类别停摆只会把自己「圆圈外也高亮」的卖点一起停掉。
5. **“让位”必须连「摘除」一起让**：光是不重申不够 —— 宽限期一到，
   我们的 `UnoutlineRef` 会把那一条从引擎正在用的管理器里摘掉，
   表现就是「扫描时目标闪一下就没了」。
