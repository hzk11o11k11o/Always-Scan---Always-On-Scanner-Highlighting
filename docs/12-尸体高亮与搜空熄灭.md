# 12 · 尸体高亮 + 容器/尸体「搜空即熄灭」（v4.2）

> 用户实测反馈（三条，2026-09-18）：
> ① 「地图内有一些预先放置的尸体，没高亮」；
> ② 「打死的敌人尸体没高亮」；
> ③ 「已经拿空的容器仍在高亮，拿完了就应该不亮了（**敌人尸体也要做同样处理**）」。
> 另补充：④ 「**怪物的尸体**也要和人类的尸体同样处理」；
> ⑤ （v4.2.1）「**炮塔 / 机器人尸体**也要高亮，一样拿空了就不高亮」。
>
> 本文记录定性、实现与验收判据。相关代码只在 `plugin/src/AlwaysScan.cpp`（DLL），
> 不需要动 ESM / Papyrus。

## 0. 结论速览

| 反馈 | 根因 | 修法 |
| --- | --- | --- |
| ①②④ 尸体不亮 | 旧版分类是**纯 base form 类型白名单**，而 `NPC_` / `LVLN` / `ACHR` 是**红线**（「活人不亮」）⇒ 尸体被一起挡掉 | 新增 `ClassifyRef()`：**按引用自己**分类 —— ACHR 引用先判死活，死的进新的 `corpse` 类别；`base = NPC_/LVLN` 的普通 REFR 也归 corpse |
| ③ 搜空还亮 | 旧版只按类型挑目标，**从不看库存** ⇒ 空箱子照常亮 | `RefLootState()`：读引用的库存列表，**把所有条目 stack 的 count 加起来**，和为 0 ⇒ 不进候选集合 ⇒ 由宽限期（1.5 s）摘掉描边 |
| ④ 怪物尸体 | 本来担心要单独处理 | **不需要**：Starfield 没有 `kCREA`，生物也是 `NPC_` 记录、也用 `ACHR` 引用摆 ⇒ 与人类尸体**同构**，一套规则全覆盖（离线数据已证，见 §1.3） |
| ⑤ 炮塔 / 机器人尸体（v4.2.1） | v4.2.0 把 `Starts Unconscious` 当「倒地活人」排除在默认值之外，而它实际上是**停机 / 报废单位** | `CorpseUnconscious` 默认改 **1**（数据：193 条引用的 26 个唯一 base 里 22 个是炮塔 / 机器人）；判空规则原样适用 ⇒ 拿空即熄灭（见 §1.4） |

## 1. 离线实证（先钉死数据形态，再写代码）

`out/achr_flags_scan.py`（ACHR/REFR 记录 flags 直方图）、

### 1.1 全量 `Starfield.esm`（1.16.244.0）统计

```
ACHR: n=9530  StartsDead(0x200)=2283  StartsUnconscious(0x2000)=193  InitiallyDisabled(0x800)=1843
   flags&0x3E00 top: 0x0000x6079, 0x0200x1235, 0x0A00x1044, 0x0800x707, ...
REFR: n=3291860  StartsDead(0x200)=487  StartsUnconscious(0x2000)=0
```

⇒ 「预先放置的尸体」在数据里就是 **ACHR 记录 flags `0x00000200` = `Starts Dead`**，
占 ACHR 的 24%（2 283 条）；其中 1 044 条同时带 `Initially Disabled`（不加载 = 不该亮）。

xEdit 的 Starfield 定义（`wbDefinitionsSF1.pas:16542`）确认这两个位的名字：
`{0x00000200} 'Starts Dead'` / `{0x00002000} 'Starts Unconscious'`。

### 1.2 判死的第三个信号：运行时 `Actor::boolBits` 的 kDead 位

`Actor::boolBits @+0x208` 的 `bit11 = kDead`（commonlibsf 的 `Actor::IsDead()` 就是读它）。
上一代项目用 `tools/re/scan_disp.py` 反查过引擎代码：
`or dword ptr [reg+0x208], 0x800`（战死置位）/ `and ..., 0xfffff7ff`（Resurrect 清位），
语义吻合。**打死敌人走的就是这一条** ⇒ 反馈 ② 靠它。

★ 但**不能只信它**：上一代项目实测过一具明确可搜刮、却读不到 kDead 位的身体
（`corpse=21/0`）⇒ 所以本版把「记录标志 Starts Dead」也当作判死依据（静态数据，
与引擎有没有置运行时位无关）。两者**取或**。

### 1.3 预置尸体的 base 都是 `NPC_`（人类 + 怪物同构）

dump 带 `Starts Dead` 的 ACHR 引用（`out/dbg_corpse_bases.py`）——样本：

## 2. 实现（全部在 `plugin/src/AlwaysScan.cpp`）

### 2.1 新增类别 `Category::kCorpse`

- 枚举追加在最后（保持既有 6 个类别下标不变），`kCategoryName` + `"corpse"`；
- INI 键：`StateCorpse`（默认 **9 = 橙，与容器同色**）、`EnableCorpse`（默认 1）、`ColorCorpse`；
- 日志里 `category (本轮选中)` / `config: stateByCategory` 自动带上 corpse。

### 2.2 判死：`ClassifyRef()`

```
ACHR 引用：
    kDead 位(+0x208 bit11)  ∨  记录标志 Starts Dead(0x200)   ⇒ corpse 类别
    （Starts Unconscious(0x2000) 且 INI 开了 CorpseUnconscious ⇒ corpse）
    否则 ⇒ -1（活人 / 生物 / 炮塔 / 机器人，一律不亮，红线）
其它引用：base 类型 ∈ {NPC_, LVLN} ⇒ corpse（「姿势固定的尸体道具」，原版没有，纯保险）
其余情形 → 走原来的 ClassifyBase（类型白名单）
```

- 全部是**纯内存读**（ref 的 `+0x2E` formType、`+0x20` formFlags、`+0x208` boolBits），零引擎调用；
- `+0x20 / +0x2E` 是 **TESForm 基类**成员（本项目长期实测读法正确，另加了 3 条 `static_assert` 钉死）；
- 诊断 `corpse probe:`（每会话最多 12 条）：打 `ref / base / formFlags / boolBits`，
  用户报「某具尸体没亮」时可直接对号入座。

### 2.3 判空：`RefLootState()` + `CalibrateInventory()`

- `TESObjectREFR::inventoryList` 是 `BSGuarded<BGSInventoryList*, BSReadWriteLock>`，
  commonlibsf 里成员顺序标着 `??`（data 在前还是在后不确定）⇒ **两个候选偏移 `0xA0 / 0xA8`
  都探测**：每会话一次，拿**容器**样本做形状校验
  （指针合理 + 可读 0x38 + `+0x28` 处 BSTArray 三元组自洽 + 非空时 data 可读），
  通过 3 个以上且坏样本 ≤2 就用它；都不行 ⇒ **永久降级**（不判空，容器/尸体照常亮）并打 WARN；
- 热路径判空：指针合理 → `+0x28` 的 `size/cap` 自洽 → `size==0` 直接判空；
  否则**逐条目把 stack 的 count 加起来**（上限 128 条目 / 1024 个 stack），
  **和为 0 才算空**。
  ★ 为什么要数 count：物品被拿光后引擎**可能留下 count = 0 的空 stack / 空条目**，
  只看 `data.size()` 会把已经搜空的箱子永远当成非空；
- ★ 热路径**零引擎调用、零 VirtualQuery**（标定完成后）；任何一步形状不对 ⇒ 返回「未知」⇒
  **按「有东西」处理（照常亮）** —— 最坏结果与旧版一致，绝不会因读错内存而崩。

### 2.4 接进主循环

```cpp
bool isCorpse = false;
const int cat = ClassifyRef(ref, base, isCorpse);      // ← 取代 ClassifyBase(base)
... 类别开关 ...
if (isCorpse || cat == kContainer) {                   // ← 判空只对容器 / 尸体做
    if (cfg.skipEmptyLoot && g_invOff) {
        const int loot = RefLootState(ref);
        if (loot == 0) { ++emptySkips; continue; }     // 空 ⇒ 不进候选 ⇒ 宽限期后摘掉
        if (loot < 0) { ++lootUnknown; }
    }
}
```

## 3. 风险与降级（都设计成「最坏 = 旧行为」）

| 风险 | 兜底 |
| --- | --- |
| `inventoryList` 偏移标定失败 | 不判空，容器 / 尸体照常亮（日志 WARN），**不崩** |
| 库存内存形状读到垃圾 | 任一步校验不过 ⇒ 「未知」⇒ 照常亮 |
| 「Starts Dead 的 ACHR」被任务复活 | 极罕见；且只要身上没东西就不会亮 |
| 活人误亮 | 判活规则只有「ACHR 且非死」一条，默认连 unconscious 都排除；INI 可回退 `EnableCorpse=0` |
| MSTT 等原本不亮的东西 | 分类规则未动，仅新增 corpse 一类 |

## 4. 实测验收点（本轮）

1. **尸体亮**（橙，默认与容器同色）：
   - 打死的敌人 / 生物 / 机器人 / 炮塔 ⇒ 立刻亮；
   - 预置尸体（如 `Loot_Corpse_*`、任务现场尸体）⇒ 进半径就亮；
   - **炮塔 / 机器人的报废体**（`Starts Unconscious` 那批）⇒ 进半径就亮，
     `corpse probe` 会打「尸体（Starts Unconscious：炮塔/机器人报废体、倒地可搜刮者）」；
2. **活人一个都不亮**：城市里站着看一分钟，正在站岗 / 巡逻 / 战斗的 NPC 与生物都不该有描边
   （统计行里 `炮塔/机器人/倒地=` 那一路会是 0，除非附近真有停机报废体）；
3. **搜空即灭**：把一个箱子 / 一具尸体拿空 ⇒ ~1.5 秒后描边消失；
   `corpse (窗口内累加)` 行的 `empty=` 持续增长；
4. **标定成功**：启动日志出现一次 `inventory calibration: off=+0xA0 或 +0xA8 … -> 搜空判空**启用**`；
   若出现 `FAILED … -> 搜空判空**关闭**` ⇒ 判空没生效（容器照常亮），把这一行发出来；
5. 不回归：F8 开关、用原版扫描仪后自动重挂、换场景不崩、`timing2` 无大值。

## 5. 经验（可复用）

1. **先扫数据再写判据**：`Starts Dead` 2 283 条 vs `Starts Unconscious` 193 条，
   以及「后者是炮塔/机器人」这条样本，直接决定了「哪个默认开、哪个默认关」——
   这类判断**不该靠猜**，一次 mmap 扫全量 ESM 只要几分钟。
2. **静态数据 + 运行时状态 取或**：记录标志（Starts Dead）与运行时位（kDead）各有盲区，
   单独用任一个都会漏；两个都用，最坏也只是「多亮一具尸体」。
3. **判空要看 count，不看条目数**：引擎的「0 件空条目」会让「按条目数判空」永远判不出来。
4. **新功能一律做成「失败即降级到旧行为」**：偏移标定失败 → 不判空；形状校验不过 → 照常亮。

# 6 · v4.3（2026-09-18 夜）—— 用户新反馈的定性：**判空/判死的偏移全部是对的**，坑在别处

> 用户实测反馈（两条，附截图）：
> ① 「预先放置在地图内的尸体，**拿空了物品还在高亮**」（截图：科学家尸体，搜刮面板是空的，仍橙色描边）；
> ② 「敌人的尸体**还有东西，却没高亮**」（截图：海盗尸体，面板里 7 件物品，没有描边）。

## 6.1 ★ 先做「全部偏移的离线实证」——把「读错内存」这条可能性彻底排除

用 `tools/re/versionlib.py` / `out/vt_actor.py` / `out/scan_actor_vfns.py` 在
`Starfield.exe`（1.16.244.0）上逐条反汇编核对（全部为当日新增的一次性脚本，`out/` 不入库）：

| 结论 | 证据（反汇编） |
| --- | --- |
| `TESObjectREFR::inventoryList` 的**数据指针 @+0xA0、锁 @+0xA8** | `TESObjectREFR` vtable slot 0xF0/0xF1 里的 `CreateInventoryList`：`lea rsi,[rcx+0xa0]` → `lea r15,[rsi+8]`（加锁）→ `[rsi]` 读写列表指针 |
| `BGSInventoryList` 布局与 commonlibsf 声明**一致** | 同一段里 `alloc(0x40)` 后逐字段构造：vtable@0 / `data(BSTArray)@0x28` / `ownerHandle@0x38` / `cachedWeight@0x3C` |
| `BSTArray` = `{size@+0, capacity@+4, data@+8}` | `CreateInventoryList` 里遍历 `TESContainer::entries`：`mov eax,[rdx+8]`（size）、`mov rbx,[rdx+0x10]`（data）、`lea rdi,[rbx+rax*0x18]`（stride 0x18） |
| `BGSInventoryItem`：`object@0 / instanceData@8 / stacks@0x10 / flags@0x20 / sizeof 0x28` | `0x140643C00` 里 `alloc(0x28)` + 构造；`0x14063E4E0`（item 构造器）里 `[rbx]=object`、`[rbx+8]=instanceData`（带 `lock xadd [rcx+8],1` 引用计数）、`vmovups [rbx+0x10]` 清零 stacks、`[rbx+0x24]=0xFE` |
| `BGSInventoryItem::stacks` 在 `+0x10`、元素 `Stack` **stride = 0x10** | `0x14063E980`：`mov eax,[r13+0x10]`（size）、`mov r12,[r13+0x18]`（data）、`shl rbp,4`（×0x10）；`0x14063EBA0` 也做同样的事 |
| **`Stack::count @ +0x08`** | `0x14063EB2F`：`cmp esi,[rsp+0x20]` → `mov edx,esi; add rdx,rdx; mov rax,[r13+0x18]; mov ecx,[rsp+0x98]; add dword ptr [rax+rdx*8+8], ecx` ⇒ `data[idx*0x10 + 8] += count` |
| `Actor::boolBits @+0x208`、`kDead = 0x800`（bit11） | `scan_disp.py 0x208 --imm 0x800` 命中 2 条 `or dword ptr [reg+0x208], 0x800`（战死置位）、`--imm 0xfffff7ff` 命中 3 条（Resurrect 清位） |
| `Actor` 主 vtable = **RVA 0x4CB9248**（417 槽） | `out/vt_actor.py` 把 commonlibsf 给的 25 个 VTABLE ID 全解析了一遍，只有 `REL::ID(451614)` 指向一个 417 槽的函数指针表；`rtti_vtable.py --vtable 0x4CB9248` 反查出 `.?AVActor@@` |

⇒ **判空与判死用到的每一个偏移都与引擎一致** ⇒ ①② 两个现象**不是读错内存**造成的。

## 6.2 那问题在哪：两条独立的线（一条已修、一条要日志）

| 反馈 | 最可能的根因 | v4.3 的处置 |
| --- | --- | --- |
| ① 拿空还亮 | 三选一：**(a)** 标定没成功（v4.2 的标定「第一轮 6 个容器样本一锤定音、失败即永久降级」）；**(b)** 引擎把 `inventoryList` **销毁/置空**（指针变成 null ⇒ 旧代码判「未知」⇒ 照常亮）；**(c)** 库存里真有引擎条目（不可见物品） | (a) 标定重做（见 6.3）；(b) **null ⇒ 判「空」**（见 6.4，带 INI 回退）；(c) 加统计区分（`notEmpty=`） |
| ② 有东西不亮 | 十有八九是**判死三信号全 false**（上一代 `高亮物品` v35 实测过这种情况：引擎对某些「可搜刮的倒地身体」**根本不置 kDead**）；其次是判空误判「空」 | 加 `actor probe:`（半径内**所有** ACHR 的明细，含 `life` 链路）⇒ 一次日志就能定位；**本轮不盲改判定**（见 6.5） |

## 6.3 标定重做（跨轮攒样本 + 强样本 + 永不放弃）

v4.2 的标定有真实缺陷：**只在「第一轮扫描」的「前 1500 个引用」里找「容器」样本，
凑够 6 个就下结论，失败即永久降级** —— 玩家第一个场景容器少（太空 / 飞船 / 小房间）

## 6.4 `null` 指针 ⇒ 判「空」（`TreatNullInvAsEmpty`，默认 1）

依据：唯一分配 `BGSInventoryList` 的函数（`CreateInventoryList`）**只有一个调用点**
（引用初始化的虚函数路径，`func.py callers` 查出的 `0x1A639EB`），
**没有找到「打开 UI / 走近时才懒创建」的第二条路径** ⇒ **指针为 null = 从来没有过库存
= 没有东西可搜刮** ⇒ 判「空」（不亮）是合理的。

⚠️ 本轮唯一带假设的改动 ⇒ 配了回退开关：若实测出现「从没搜过的身体 / 容器不亮」，
把 INI 的 `TreatNullInvAsEmpty=0` 即退回旧行为（null ⇒ 未知 ⇒ 照常亮），不用换 DLL。

## 6.5 `actor probe:`（v4.3 的诊断主力）

每会话最多 `ActorProbeMax`（默认 24）条，**覆盖半径内所有 ACHR（不论死活）**：

```
actor probe: ref=XXXXXXXX base=XXXXXXXX d=1.2m formFlags=0x00000000 boolBits=0x00102002
             dead=0 startsDead=0 startsUnc=0 life=- inv=ok loot=1 -> 活人（不进候选）
```

- `dead / startsDead / startsUnc` = 三个判死信号；
- `life` = 生命状态链路（`actor+0x228` → `+0x10` → `+0x264`）读到的值（读不到打 `-`）；
  ★ 2026-09-18 反汇编发现 `+0x264` 是个被 `cmp …, 3 / 4 / 7` 比较的状态枚举
  （`0x19200A8` / `0x190E95E`），**但 0..7 的语义还没实证** ⇒ 只作探针、不进判定；
- `inv / loot` = 库存指针（ok/null）与判空结果（1 有 / 0 空 / -1 未知 / -2 null / -3 未标定）。

**统计行同步细分**（一次日志就能定位「卡在哪一步」）：

```
corpse (窗口内累加): 尸体=… (kDead位=… StartsDead标志=… 道具=… 炮塔/机器人/倒地=…)
  | ACHR: 见到=N 判活跳过=M | StartsUnconscious跳过=…
  | 前置过滤: deleted/disabled=… 非本cell=…
  | 搜空: empty=… notEmpty=… unknown=… null=… shapeBad=… invOff=+0xA0
```

排查链条（「某具尸体完全没出现过」时按这个顺序看）：它在引用数组里吗（`refs=` / `off=`）→
被 `deleted/disabled` 挡了吗 → `parentCell` 对吗 → 在半径内吗（`cand=`）→ 分类成什么
（`ACHR: 见到/判活跳过` + 两条探针）→ 判空结果如何（`搜空:` 五项）。

## 7.2 ★★ 反汇编实证：`[Actor + 0xF8]` 的 bits 17..20 就是引擎自己的「生命状态枚举」

（全部为 2026-09-18 当日的一次性脚本：`out/probe_lifestate.py`、`out/dis_range.py`、
`out/probe_native.py`、`out/probe_strs.py`；配合既有的 `tools/re/scan_disp.py` / `findrefs.py`。）

**第 1 步 —— 找到三个 Papyrus native 判死函数的实现。**

在 exe 里搜名字字符串（`IsDead` @ 文件 0x4D12390 / `IsUnconscious` @ 0x4D1A908 /
`IsBleedingOut` @ 0x4BC39F8，都在 `.rdata` 的一串「名字池」里），再用 `findrefs.py` 找引用点：
三个都落在同一个函数 `0x1FCC740` 里 —— 那是 **Papyrus native 注册表**，
注册模式极其规整：

```asm
mov  ecx, 0x58                  ; 分配 0x58 字节的描述符
call <alloc>
lea  r9,  [rip + X]             ; ★ X = native 实现地址
lea  rdx, [rip + <名字串>]       ; 函数名
mov  rcx, rax
call <register>
```

从这三个注册点读出实现地址：

| native | 注册点 RVA | **实现 RVA** |
| --- | --- | --- |
| `IsUnconscious` | 0x1FCECDA | **0x1FD1470** |
| `IsDead` | 0x1FCE59F | **0x1FC7FB0** |
| `IsBleedingOut` | 0x1FCE48F | **0x1FC7F50** |

**第 2 步 —— 反汇编这三个实现。**

```asm
; IsUnconscious @ 0x1FD1470
mov  eax, [r8 + 0xF8]
and  eax, 0x1E0000
cmp  eax, 0x60000          ; ★ == 3
sete al
ret

; IsDead @ 0x1FC7FB0（薄壳：转发到 Actor vtable slot 0x10D）
mov  rax, [r8]             ; vtable
mov  dl, 1                 ; Papyrus 传「严格」标志
mov  rcx, r8
jmp  qword ptr [rax + 0x868]        ; 0x868 / 8 = slot 0x10D
;   → 实现 @ 0x18E4540：
;     mov r8d, [rcx+0xF8]; and eax, 0x1E0000
;     dl=1（严格）：v ∈ {1(0x20000), 2(0x40000), 5(0xA0000)} ⇒ 死
;     dl=0（宽松）：再加 7(0xE0000)

; IsBleedingOut @ 0x1FC7F50
mov  ecx, [r8 + 0xF8]
and  eax, 0x1E0000
cmp  eax, 0x100000         ; ★ == 8 ⇒ 出血
je   返回 1/2
cmp  ecx, 0xE0000          ; ★ == 7 ⇒ 出血
je   返回 1/2
mov  rcx, [r8 + 0x228]     ; AIProcess*
mov  rdx, [rcx + 0x08]     ; middleHigh*
cmp  byte ptr [rdx + 0x59C], 0     ; 「出血动画中」标志（第二个条件）
jne  返回 1/2
返回 0
```

**⇒ 结论（这就是引擎自己的判死判据）**：

```
lifeState = ([Actor + 0xF8] & 0x1E0000) >> 17        （4 位，0..15）

  0  = 活着                                  ← 红线：不亮
  1, 2, 5 = 死（引擎 IsDead 严格分支）
  3      = 昏迷 / 停机报废体（引擎 IsUnconscious）
  7, 8   = 倒地出血 / 濒死（引擎 IsBleedingOut）
```

**旁证三处**：
① `scan_disp.py 0xf8 --imm 0x1e0000` 命中 **11** 条 `test dword ptr [reg+0xF8], 0x1E0000`
（都是「是不是某种状态」的分支）；
② `scan_disp.py 0xf8` 命中 `and dword ptr [r14+0xF8], 0xFFFFC000` + `or dword ptr [r14+0xF8], eax`
（**写 lifeState**：清低 14 位再写值 —— 与「bits17..20 是枚举」自洽）；
③ commonlibsf 把 Actor 的 0xF8 标成 `IMovementStateStore` 接口 —— 从这两组读写看，
那里其实就是**状态字本身**（引擎按位读写它，不是取指针）。

★ 顺带否掉一条 v4.3 的旧假设：`life` 链路（`actor+0x228 → +0x10 → +0x264`）
**永远读不到**（日志里恒为 `-1`）—— 真正的枚举在 **Actor 自己身上**，不在 AIProcess 里。

## 9.2 ★ 旁证：第三方 mod `SimpleImmersiveLooting`（Nexus 12677）—— 用户本次下载

它的整个卖点就是**给尸体加一个「扒取装备」选项**，而脚本只有一句关键的：
`akTarget.UnequipAll()`（详见 `docs/11`）；同时它把原版 GMST
**`fEquippedArmorChanceToDrop` 从 0.1 覆盖成 0.0**（= 死亡时引擎**不再自动掉落**身上装备）。

⇒ 把两件事放在一起，引擎的模型就明确了：

1. **物品「被掉落 / 卸下」后（`fl` 归零）才进搜刮面板**；还穿在身上的（`fl≠0`）
   面板不列、玩家拿不走；
2. 原版是用那条 GMST（10% 概率）把部分身上装备「掉落」进尸体库存 —— 所以平时
   **能**在尸体上捡到宇航服，只是看概率；`SimpleImmersiveLooting` 把它设 0 之后，
   只能靠它的「扒取装备」（`UnequipAll`）主动卸下，卸下后才可搜刮。

这条规则同时解释了 v4.5 那半个坑（② 类），也解释了为什么 ③ 类（`fl=0`）才是「真能拿」。

1. **「面板拿不走」在引擎里有两条独立的判据，别只找一条**：记录标志 `0x04`（记录级，

## 11. v4.10：展示柜「拿空即灭」—— 用「容器界面的同一段打开期」分开两种「空」

> 用户实测（v4.9 如实记录的副作用被确认）：*「现在关着的武器箱会高亮了，
> 但是拿空了却不会熄灭了」*。本轮只改 DLL + INI（ESM / Papyrus 未动）。

### 11.1 ★ 问题定性：数据上「拿空」与「关着」长得一模一样

展示柜的内容只在搜刮界面打开期间以 `kTemporary` 条目投影进库存（v4.9 第十节实证），
所以关闭状态下永远是 `size=0`。于是三种情形在库存数据上无法区分：

| 情形 | 关闭时读到 | 打开时读到 |
| --- | --- | --- |
| 从没打开过（内容未知） | `size=0` | （打开后才有投影） |
| 打开过、没拿、关掉（东西还在） | `size=0` | `size=N`（投影条目） |
| 拿空后关掉（真的空） | `size=0` | `size=0` |

⇒ v4.9 的粗规则（读到空一律不熄灭）必然让第三种也一直亮；要区分第三种，
**只能引入一个独立于库存的信号**。

★ 另一种「靠库存形状区分」的想法经分析被否掉：v4.9 日志证明「关闭」时引擎把投影条目
**整体移除**（`size: 2 → 0`），而「拿走最后一件」同样是移除 ⇒ 两条路在库存层等价。

### 11.2 ★ 独立信号 = 容器界面（`ContainerMenu`）的「同一段打开期」

- **菜单名取证**（游戏自带 Papyrus，非猜测）：
  - `AudioContainerNoAnimScript.psc`：`RegisterForMenuOpenCloseEvent("ContainerMenu")`
    —— 用它给容器播「打开 / 关闭」音效；
  - `OutpostContainerScript.psc`：同样注册 `ContainerMenu`，`abOpening=true` 进 `busy`、
    关闭时结算前哨容器的联动物品 —— **它就是「容器界面开/关」的官方信号**。
- DLL 侧沿用 `MonocleMenu` / `LoadingMenu` 的做法：`RE::UI::IsMenuOpen` 轮询
  （每帧一次，成本与既有两次检测同量级）；菜单名可由 INI 覆盖（`ContainerMenuName`）。
- **段号（serial）**：每帧检测，每次「开 ↔ 关」翻转就把 `containerUiSerial` +1。
  它把「**这一段**打开期」与「上一段（已关闭）」严格分开：
  - 「拿空」发生在打开期内 ⇒ 该 ref 的 `lastTpSerial == 当前段号` ⇒ 判空；
  - 「关掉（没拿）」发生在段号翻转之后 ⇒ `lastTpSerial != 当前段号` ⇒ 不判空。
  ★ 这正是「时间窗」做不到的：关闭时投影也会立刻收回（`size=0`），只看时间窗会把
  「关掉没拿」误判成「拿空」；段号则不会。

### 11.5 验收判据（v4.10）

1. **关着的武器箱 / 武器架照旧亮**（`展示柜跳过=` 增长）—— v4.9 成果不回归；
2. **打开武器箱 ⇒ 把东西全拿光**（界面还开着）⇒ **约 1.5 秒内熄灭**，
   统计行 `展示柜拿空=` 开始增长；
3. **拿空后关闭**（箱子关着）⇒ **保持熄灭**（这是本轮核心）；
4. **打开武器箱但不拿、直接关掉** ⇒ **保持亮**（东西还在；`cont probe` 里
   `ui=0 st=1 tpS=1`，`why=` 写「关闭状态…内容未知 ⇒ 照常亮」）；
5. 往（已拿空的）展示柜里**放东西**（转移）⇒ 重新亮；
6. 不回归：普通容器 / 尸体拿空 ~1.5 秒熄灭（`empty=` 仍增长）；F8 / 扫描仪自愈 /
   换场景不崩 / 活人一个都不亮。
7. 若 2 / 3 没生效：日志里看 `cont probe` 的 `ui=` —— 若全程 `ui=0`，说明容器界面
   的菜单名不是 `ContainerMenu`（改 INI `ContainerMenuName`，不用换 DLL）。

### 11.6 经验（可复用）

1. **「同一个数据形态」要用「独立的第二个信号」去区分**：库存分不清「拿空」与
   「关着」，但「UI 开着吗」能 —— 而官方脚本里就有现成的菜单事件名字。
2. **信号要拼「段号」而不是「时间窗」**：凡是「A 事件导致数据立刻变成 B 形态」的
   场景，时间窗一定会误判；把「状态翻转」编号，同一段内的观测才是可信的。
3. **先查游戏自带脚本再想逆向**：`ContainerMenu` 这个名字来自两个自带 `.psc`
   的使用方式（容器开合音效 / 前哨结算），成本远低于逆向菜单对象。
4. **粘性是「用户可见结果」的关键**：判空一次就记住（关掉后保持熄灭），否则
   「熄灭」只发生在界面开着的一瞬间，观感仍是「拿空不灭」。
