## 3. 崩溃点 A：`SAS+0x4098A`（10 次 · 主崩溃）

### 3.1 符号化

```
> python tools\re\pdbsym.py "<SAS_AlwaysScan.dll>" 7FFFD9070000 4098A
SOURCE : D:\workspace\starfield mod\always scan\tools\commonlibsf-main\lib\commonlib-shared\src\REL\IDDB.cpp : 457  (+0x7)
```

`IDDB.cpp:457` = `IDDB::GetOffset...` 里的 **Address Library v5 表查询**：

```cpp
const auto offset = static_cast<std::uint64_t>(m_v5[a_id]);   // ← 本行
```

（`m_v5` 声明为 `std::span<std::uint32_t>`，数据直接指向地址库文件映射，见 `REL/IDDB.h:69`。）

### 3.2 反汇编（从函数入口 0x40790 起解析，指令边界已核验）

```asm
0004093B  4883bf8800000000     cmp  qword ptr [rdi + 0x88], 0   ; m_v5.size == 0 ?
00040943  753e                 jne  0x40983                     ; 非空 → 查询
00040945  ...                                                    ; 组装 REX::FAIL 消息（行号 0x1C7 = 455）
00040983  488b8780000000       mov  rax, qword ptr [rdi + 0x80] ; rax = m_v5.data
0004098A  8b1cb0               mov  ebx, dword ptr [rax + rsi*4]  ; <=== 崩溃：m_v5[a_id]
0004098D  85db                 test ebx, ebx
0004098F  0f85b4000000         jne  0x40a49                     ; offset != 0 → 返回
```

> `rdi` = IDDB 实例；`+0x80` = m_v5.data、`+0x88` = m_v5.size（span 布局）。
> `rsi` = a_id。**v5 分支是裸索引，没有边界检查** —— 对照 `IDDB.cpp:433-449` 的 v0 分支
> （`std::lower_bound` + `it == m_v0.end()` 检查），两条路径的保护不对称。

### 3.3 现场（两份转储完全同型）

| 寄存器 | 06:54 样本（24512） | 09:07 样本（24876） | 含义 |
| --- | --- | --- | --- |
| RAX | `0x0000021C39050060` | `0x000001D039920060` | `m_v5.data`（低 12 位 = **0x060** = 映射视图 + 头部偏移） |
| RSI / RDX | `0x9756` | `0x9756` | **a_id = 38742（两次相同）** |
| RDI | `SAS+0xA5910` | `SAS+0xA5910` | IDDB 静态实例（在 SAS 内，同一位置） |
| 读地址 | `0x0000021C39075DB8` | `0x000001D039945DB8` | **= data + 38742×4（精确吻合）** |

算术验证：`data + 0x9756*4 = data + 0x25D58` → `0x1D039920060 + 0x25D58 = 0x1D039945DB8` ✔（两份都吻合）

### 3.4 关键观察（供定位）

1. **每次崩溃都是同一个查询：`m_v5[38742]`** —— a_id 固定（两份样本一致），
   这也解释了 10 次的读地址为什么低 16 位恒定：
   `data` 低 16 位（0x0060）+ `0x9756*4` 低 16 位（0x5D58）= `0x5DB8`。
2. 读地址换算到**文件内偏移 = 155,064 字节**，而 `versionlib-1-16-244-0.bin` 有
   5,099,968 字节 —— **位置本身在文件范围内，却不可读**。
   ⇒ 优先怀疑：
   - **m_v5.data 指向的映射视图此刻不可读**（视图已 unmap / 尚未建立 / 生命周期竞态），
   - 其次是「v5 数据区条目数 < 38742」（地址库条目布局/版本与请求不符）。
3. `[rdi+0x88]`（size）非 0 才会走到查询（0x4093B 的空表检查通过），
   说明 IDDB 自认为表是有效的 —— 这与「视图失效/指针过期」的假设互相印证。

### 3.5 建议排查

1. 在查询处加诊断（临时）：打印 `a_id / data / size`，并检查 `data` 与 `data+size*4` 的可读性
   （或直接用 SEH 包住读取）；
2. 找出 **谁持有 `SAS+0xA5910` 这个 IDDB 实例**、以及 `REX::FMemoryMap` 的构造/析构/重建时机
   （是否有 reload / 多线程首次触发的路径）；
3. 把 **38742（0x9756）反查为符号**（Address Library 的 ID→符号数据库）⇒ 直接指向调用的
   `REL::ID` 与源码位置；
4. 复核 SAS 编译用的 commonlibsf 版本与 `versionlib-1-16-244-0.bin` 的匹配状况；
5. 可选（上游）：给 v5 分支补边界检查（`a_id < m_v5.size()`），把静默崩溃变成可诊断的 FAIL。

## 4. 崩溃点 B：`SAS+0x2023A`（09:50:46 · 本次）

### 4.1 符号化

```
SOURCE : ...\always scan\plugin\src\AlwaysScan.cpp : 4442  (+0x0)
```

= `RefLootState()`（判空链路）里的库存数组读取：

```cpp
const auto  size = *reinterpret_cast<const std::uint32_t*>(inv + kOffInvData);      // 4442 ← 本行
const auto  cap  = *reinterpret_cast<const std::uint32_t*>(inv + kOffInvData + 4);  // 4443
```

### 4.2 反汇编（边界已核验）

```asm
00020220  488d81fffffeff        lea  rax, [rcx - 0x10001]       ; IsPlausiblePointer()
00020231  493bc1                cmp  rax, r9                    ; r9 = 0x7FFFFFFEFFFD
00020234  0f87ec030000          ja   0x20626                    ; 不合格 → return -1
0002023A  448b7128              mov  r14d, dword ptr [rcx + 0x28]  ; <=== 崩溃：size = *(inv+0x28)
00020250  8b412c                mov  eax, dword ptr [rcx + 0x2c]   ; cap
0002027C  4c8b7930              mov  r15, qword ptr [rcx + 0x30]   ; data
```

### 4.3 现场

| 寄存器 | 值 | 说明 |
| --- | --- | --- |
| RCX | `0x1A486` | 从 `*(a_ref + g_invOff)` 读出的「库存指针」——**垃圾小整数、非 8 字节对齐** |
| R8 | `0x1CDA61C3CE0` | a_ref |
| 读地址 | `0x1A4AE` | = 0x1A486 + 0x28（与转储 param1 完全一致） |

**根因**：`IsPlausiblePointer()`（`AlwaysScan.cpp:1480`）只查
`> 0x10000 && < 0x7FFFFFFFFFFF`，`0x1A486` 轻松通过 ⇒ 直接解引用崩溃。

### 4.4 建议

1. `IsPlausiblePointer` 至少加 **8 字节对齐**（`(p & 7) == 0`），可挡掉本类垃圾值；
2. 判空链路的解引用统一走 `SafeReadMem` / `IsReadable`（SAS 已有这些工具；
   本处 4426/4442/4443/4453 及 `LootProbe`/`ContProbe` 同类位置都是裸读）；
3. 复核「a_ref 处于销毁/复用过渡态」的可能（该崩溃发生在传送/cell 切换完成后约 1 秒）。

### 9.2 崩溃 A（`+0x4098A`）—— 真实，但**是「退出时」崩的**，不是传送/菜单

**证据链（转储 24876，09:07 那一份）**：

```
python tools\re\dmpdeep.py "%LOCALAPPDATA%\CrashDumps\Starfield.exe.24876.dmp" --stack SAS_AlwaysScan
```

故障线程栈上落进 SAS 的返回地址，逐个 `pdbsym.py` 符号化后是**一条完整的卸载链**：

| 栈上地址（RVA） | 符号化结果 | 说明 |
| --- | --- | --- |
| `+0x4098A` | `REL/IDDB.cpp:457`（`m_v5[a_id]`） | 崩溃点（读已 unmap 的映射） |
| `+0x29B1E` | `REL/ID.h:27` | `REL::ID::address()` → 查表 |
| `+0x18826` | `RE/T/TESForm.h:158` | `TESForm::DecRefCount()` 里那个 **`static REL::Relocation` 首次初始化** |
| `+0x12865` | `xhash:256`（`~_Hash_vec::_Tidy`） | 正在析构一个 `std::unordered_map` |
| `+0x12A51` | `list:1061`（`~list::_Tidy`） | 同一个 map 内部链表（逐节点析构 ⇒ 调 `NiPointer` 析构） |
| `+0x5EDE6` | `vcstartup\dll_dllmain.cpp:182` | `DllMain` |
| `+0x5EF2D` | `dll_dllmain.cpp:293` | `dllmain_crt_process_detach` |
| `+0x5EF80` | `dll_dllmain.cpp:324` | 同上 |
| `+0x5EFC0` | `tlsdtor.cpp:109` | CRT 退出表（静态析构）正在跑 |
| 栈底 | `kernel32!BaseThreadInitThunk` / `ntdll!RtlExitUserThread` | 线程退出路径（`peexport.py` 定性） |

**结论**：10 份 `+0x4098A` 转储全是**进程退出 / DLL 卸载**时崩的（用户在那几个时间点退的游戏），
机制是**析构顺序**：

```
DLL 加载   → 命名空间静态对象（Config/State…）构造 ⇒ 析构登记在退出表**最前** ⇒ 最后析构
首次 REL::ID → IDDB（TSingleton 的**函数内静态**）构造 ⇒ 登记在**后** ⇒ **先**析构
                ⇒ ~FMemoryMap → UnmapViewOfFile（地址库映射没了）
退出时     → g_state.outlined（unordered_map<TESObjectREFR*, OutlineEntry>）析构
            → OutlineEntry::ref（NiPointer）析构 → TESForm::DecRefCount()
            → 该函数里 static REL::Relocation 首次查表 → m_v5[38742] ⇒ 读已 unmap 的映射 ⇒ AV
```

**为什么"每次都是同一个 ID 38742"**：只有它需要**第一次**查表；
其余引擎调用（如 `RefGet3D` 里的 `NiPointer<NiAVObject>`）走的是 `NiRefObject::DecRefCount`（内联、无查表），
所以那 10 局里只有 `TESForm::DecRefCount` 是"退出时才第一次用"，10 次全崩在同一条指令。

**报告 §3.5 的 5 条建议，逐条答复**：

| §3.5 建议 | 复核结果 |
| --- | --- |
| ① 查询处加诊断 / SEH 包住读取 | **不需要** —— 根因不在"读法"，而在"退出时还在跑引擎代码" |
| ② 找出谁持有 `SAS+0xA5910` 的 IDDB、谁重建映射 | 就是 `REL::IDDB` 的静态实例（`REX::TSingleton`）；映射**没人重建**，只有析构 |
| ③ 把 38742 反查成符号 | **= `REL::ID::TESForm::DecRefCount`** ✓（`entry[38742] = RVA 0x384600`，反汇编是 `lock xadd [rcx+8]` 引用计数递减） |
| ④ 复核 commonlibsf 与地址库匹配 | 匹配 ✓（读地址 = 文件内 `0x60 + 4*38742`，落在 5 099 968 B 的文件里） |
| ⑤ 上游给 v5 分支补边界检查 | 可选；**本项目不需要**（不是越界，是映射已 unmap） |

### 9.3 崩溃 B（`+0x2023A`）—— 真实，根因是「陈旧的引用」而不是「判空判据太松」

**证据链（`Starfield_09-21-01-50.dmp`）**：

1. 栈上 SAS 帧符号化：`Tick`(6324) ← `DcTickWatch`(4327) ← `RefLootState`(4442) —— 
   也就是说，真正调用的这条链是 **每帧的展示柜观察**（Tick 里的 `DcTickWatch()`），
   而**不是在扫描/判空的主路径上**；且 `DcTickWatch` 排在 Tick 的"载入画面早退"**之前**，
   所以**载入 / 换场景期间它照样在读**（这正是最容易碰到"已释放引用"的时刻）。
2. `R8`（那个"引用"）的内存 dump：

```
python tools\re\dmpdeep.py "...\Starfield_09-21-01-50.dmp" --field 0x1CDA61C3CE0
  +0x000  0x27C0000333C00003     ← 不是 vtable 指针（游戏对象的 vtable 一定在 Starfield.exe 里）
  +0x010  0xC3037A284399B33F     ← 通篇是浮点 / 小整数（0x3F800000 = 1.0f 之类）
  +0x080  0x0001A4870014645E     ← 与"垃圾库存指针 0x1A486"同一族的小整数
```

   ⇒ **`R8` 指向的根本不是 `TESObjectREFR`**：那个引用已经被销毁，内存被别的数据（浮点数组）复用。
   `IsReadable` 判不出来（堆内存仍然 mapped），于是 `*(ref + 0xA0)` 拿到 `0x1A486`，
   `IsPlausiblePointer`（只查 `> 0x10000`）放行 ⇒ 裸读 `*(inv + 0x28)` ⇒ AV。
3. 报告的 §4.4 三条建议**部分成立**：加对齐能挡住 `0x1A486` 这一例，但挡不住"对齐的垃圾"；
   真正的硬保证必须是**读内存本身不会抛异常**（`ReadProcessMemory`）+ **对象存活判据**。

### 9.4 顺手订正的一处工具 bug：`versionlib.py` 索引差一条

复核 38742 时发现旧口径自相矛盾：

* 文件头第 0 条 `entry[0] = 0`（占位），`entry[1] = 0x1000`；
* commonlibsf：`m_v5 = span(mmap + sizeof(HEADER_V5) /*0x60*/, count)`、`offset(id) = m_v5[id]`
  ⇒ **ID 即下标**（`entry[0]` 是 0 占位，所以 `m_v5[38742]` 正好是 ID 38742）；
* 而旧 `versionlib.py` 写的是 `table[i+1] = entry[i]` ⇒ **整体差一条**（查 ID 83006 得到的是 entry[83005]）。

已订正为 `table[i] = entry[i]`（文件头注释里记了三重依据）。
⇒ **以前用本工具记下的「ID → RVA」数字都要 +1 才对**（本仓库文档里只在开发推导中用过，不影响发布产物）。
