# 04 · 任务引导路径（地上那条线）调研

> 2026-09-16 建立。起因：v2 实测「高亮对了，但地上没有任务引导线」。
> 游戏版本：Starfield 1.16.244.0。

## 一、它不是 outline 高亮系统的一部分

v2 把描边拉起来了（`docs/03`），但引导路径**完全没有出现**，因为它是另一套东西：

- outline 高亮 = 「引用 → 状态 → HighlightManager → 渲染器」；
- 引导路径 = **挂在玩家身上的一个魔法效果**，由它自己算路径、自己画線。

## 二、★ 定位到的具体形态（这次的关键产出）

手段：直接在 `Starfield.esm` 里搜 EDID 明文（`tools/re/esmstrings.py`），
再用「EDID 子记录 → 往前 24 字节的记录头」反查 FormID（`tools/re/esmformid.py`）。

| EDID | 签名 | FormID | 备注 |
| --- | --- | --- | --- |
| `ScannerGuideEffect` | MGEF | **0x0003CC95** | ★ 画路径的那个魔法效果 |
| `SpellScannerGuide` | SPEL | **0x0003CC96** | ★ 装着上面那条 MGEF 的法术（两个记录紧挨着） |
| `ArtifactPowerPrecognition_GuideEffect` | MGEF | - | 「预知」能力的同类效果，说明 GuideEffect 是通用能力 |
| `HandscannerGuideSpellDO` | DFOB | **0x00112B0B** | 引擎用来取到 `SpellScannerGuide` 的默认对象 |
| `ScannerGuideHazard` | - | - | 危险物路径（另一支） |

相关的 **INI / GMST**（都在 `:Magic` / `:Interface` 分类，另有 `Guide*` 短名版本）：

```
fMagicGuideSpacing / GuideSpacing
iMagicGuideWaypoints / GuideWaypoints
sMagicGuideNoPath    / GuideNoPath        ← 置 1 大概就是「不画路径」
sMagicGuideNoMarker  / GuideNoMarker
fMagicGuideUpdateFrequency / GuideUpdateFrequency
GuideTargetRadius / GuideEffectPathingRadiusMult / GuideEffectAllowIncompletePaths
GuideAlignmentRayLength / GuideAlignmentZOffset / GuideHazardsPerUpdate
GuideEffect_SecsUntilFadeOut:Interface
```

**没有任何 Papyrus 脚本引用它**（把 `Data\Scripts\Source\**` 全搜了一遍
`ScannerGuide` / `HandscannerGuide` / `GuideSpell` = 0 命中）⇒ 加/摘法术这件事
**是引擎 C++ 侧做的**（扫描期间从 `HandscannerGuideSpellDO` 取法术加到玩家身上，
不扫描就摘掉）。这正是「不装备扫描仪就没有路径」的原因。

## 三、本 MOD 的做法（v2.1 已实现）

既然路径的渲染是那条 MGEF 自己的事、**不需要扫描模式**，那就自己把法术加上：

- `scripts/SAS_Bridge.psc` 新增 `SyncGuideSpell()`，在既有的 0.25 秒心跳里调用：
  - 玩家没有 `0x0003CC96` → `AddSpell`；
  - 有法术但 `HasMagicEffect(0x0003CC95)` 为假（说明它是「发射即忘」型且已过期）→
    `RemoveSpell` + `AddSpell` 重新点火；
  - 是 Ability 型的话第二个分支永远不触发，加一次就一直在。
- 没有改 ESM、没有加新属性 —— `Game.GetForm(formID)` 直接取原版形态，
  所以这条链路只要 Papyrus 编译通过就能跑。

**已知取舍**：

- 目前**与 F8 开关无关**（F8 只管描边）。做成联动需要 DLL 写一个状态 GLOB
  （最省事的做法是给 ESM 加一个 GLOB，走和「引导路径」一样的 `SyncGuideSpell`
  读取 —— 见下面 TODO）；
- 只要存在「正在追踪的任务目标」，路径就会一直画（原版是只有举着扫描仪才画）。
  这正是本 MOD「一直开扫描仪」的定位；如果嫌吵，可以把它做成 INI 开关。

## 六、v2.2 第二次调研（2026-09-16）—— 法术到底是什么型的？

v2.1 上线后实测：**地上还是没有线**。这次改用 `tools/re/esmrec.py` 直接读原始记录
（不再依赖 xEdit），把三个形态的字段挖了出来：

### 6.1 `SPEL 0003CC96 SpellScannerGuide`

| 子记录 | 值 | 解读 |
| --- | --- | --- |
| `ODTY` | `0` | **是「Spell」不是「Ability」**（Ability 一般是 2） |
| `ETYP` | `0x00013F44` | 装备类型关键词 |
| `SPIT` | 27 B：`00 00 00 00 / 00 00 00 00 / 04 00 00 00 / ...` | 施法参数（cost=0.0、flags=0、…） |
| `EFID` → `EFIT` | `95 CC 03 00` / `{0, 0, 5}` | 效果 = `MGEF 0x3CC95`；**duration = 5** |
| `EFIF` / `MUID` | `0` / `1` | |

### 6.2 `MGEF 0003CC95 ScannerGuideEffect`

- `DATA` 首 4 字节 = `0x0010BCD3`（flags）；
- `DATA + 0x54` = **`19 00 00 00` = 25 = `EffectArchetypes::kGuide`** ⇒ 确认它就是
  「画路径」的那条效果（commonlibsf 里 `kGuide = 25`）；
- `DNAM` = 0。

### 6.3 `DFOB 00112B0B HandscannerGuideSpellDO`

- `DATA` = `96 CC 03 00` = **0x0003CC96** ⇒ 引擎从它取到的就是 `SpellScannerGuide`（docs 之前的推断得到原始字节确认）。

### 6.4 ★ 结论：v2.1 的用法错在「只 AddSpell 没 Cast」

- `Spell` 型（不是 Ability）+ 有 duration ⇒ 它属于**发射即忘**型；
- 原版 Papyrus 里这类法术的用法是 **`Spell.Cast(施法者, 目标)`**
  （`Spell.psc` 里就写着 `Cast(ObjectReference akSource, ObjectReference akTarget)`；
  游戏自带的 `ENV_PeriodicEffectScript.psc` 甚至有 `CastOrAddSpell()` 专门按
  「AddSpell 型 / Cast 型」分流），`AddSpell` 只会把它记进法术书、效果不生效；
- 所以 v2.2 的 `SyncGuideSpell()` 改成：
  1. 没有就 `AddSpell`；`HasMagicEffect` 仍然为假说明是 Cast 型；
  2. **再 `s.Cast(p, p)`**（限频 4 秒一次，别每 0.25 秒真施法一次）。

### 6.5 ★ 新增「脚本 → DLL」诊断通道（不再靠猜）

光看游戏里有没有线，判断不出「脚本没跑 / 法术没装上 / 装了但渲染被门控」这三件事。
所以 v2.2 给 ESM 加了两个 GLOB（**0x807 `SAS_GuideHb` / 0x808 `SAS_GuideState`**），
`SyncGuideSpell` 每次跑都写入，**由 DLL 打在自己的日志里**：

```
  papyrus: guideHb=NNN guideState=S
```

| 现象 | 结论 |
| --- | --- |
| `guideHb` 一直是 0（且不涨） | Papyrus 脚本没跑（VMAD/属性绑定问题），不是引导路径本身的问题 |
| `guideState=1` | `Game.GetForm(0x3CC96)` 取不到（ESM 没加载？） |
| `guideState=2` | 法术在玩家身上，但 `HasMagicEffect(0x3CC95)` 仍为假（正在按 4 秒间隔 Cast） |
| `guideState=3` | 法术 + 效果都生效了 ⇒ **如果还是没有线，那就是渲染被门控**（下一步查渲染侧） |

### 6.6 还没做完的

- [ ] 实测 `guideState`：若是 3 但无线 → 查渲染门控（`GuideEffect` 类只能拿到 RTTI 名，
      vtable 没找到，`rtti_vtable.py GuideEffect` 卡在「没有槽引用 COL」，
      下次可以改用「找 `.*AVGuideEffect@@` 的 COL 的全部候选」再逐个查引用）；
- [ ] 若是 2 → 说明 `Cast` 也没让效果生效，要查是不是需要「扫描模式」这个前置状态；
- [ ] 引导路径与 F8 联动（加 `SAS_On` GLOB，DLL 在 `SetOn` 里写，脚本读它决定加/摘）。

## 七、v2.3 实测判定 + 第三次调研（2026-09-16 夜）

### 7.1 实测结果：脚本与法术这两半**都正常**了

v2.2 部署后的日志：

```
  papyrus: guideHb=13  guideState=3      ← 第一次统计
  papyrus: guideHb=445 guideState=3      ← 走了 5 分钟，心跳一直在涨
```

- `guideHb` 从 13 一路涨到 445（≈4 次/秒）⇒ **Papyrus 桥脚本在跑**，不是 VMAD/属性问题；
- `guideState = 3` ⇒ **`SpellScannerGuide` 在玩家身上、`ScannerGuideEffect` 也确实生效**。

也就是说「脚本没跑 / 法术没装上 / 装了但没生效」这三种可能**全部排除**，
剩下的只有一件事：**效果生效了，但没人画那条线。**

（顺带一个现象：中间有一处 `guideHb` 从 82 掉回 5，那是存档/场景重载把 GLOB 重置
到 pex 默认值了 —— 心跳本来就不需要跨载入保持单调，不影响判断。）

### 7.2 ★ 第三次调研：路径的「渲染」不在魔法效果里

这次从 exe 里能直接查到的证据（`tools/re/rtti.py` + 字符串表）：

| 找到的东西 | 说明 |
| --- | --- |
| `GuideEffect`（有 RTTI，**但没有任何 vtable 引用它的 COL**） | 非多态/工具类，只管算 |
| `GroundPathPathingNodeGenerator` | ★ **算地面路径节点**（走 NavMesh 铺点） |
| `GroundPathRayValidator` | ★ 验证路径点落在地面上 |
| `BGSScannerGuideEffectStatusUpdateEvent`（`BSTGlobalEvent`） | ★ 把「路径状态」**广播出去**（名字里就是 StatusUpdate） |
| `GuideSpacing` / `GuideWaypoints` / `GuideTargetRadius` / `GuideNoPath` / `GuideNoMarker` / `GuideEffect_SecsUntilFadeOut:Interface` / `GuideEffectAllowIncompletePaths:Magic` / `GuideAlignmentRayLength:Magic` … | 一整套「画路径」的 GMST/INI，全在 `:Magic` / `:Interface` 分类下 |

⇒ 结构已经很清楚：

```
MGEF(kGuide)  →  GuideEffect（用 GroundPath* 算出路径点）
                        ↓ 发 BGSScannerGuideEffectStatusUpdateEvent
                  监听者 = 扫描仪 HUD（Monocle）侧的组件  → 才把它画到地上
```

**所以地上那条线是「扫描仪 HUD」的渲染，不是魔法效果自带的。** 不装备扫描仪时
Monocle HUD 根本没建，事件发了也没人接 —— 这正是「`guideState=3` 但地上什么都没有」。

### 7.3 下一步的三个选项（按可行性排序）

1. **确认门控（最省事的下一步）**：把 `BGSScannerGuideEffectStatusUpdateEvent` 的
   EventSource 单例找出来（RTTI `UBGSScannerGuideEffectStatusUpdateEvent::?$BSTEventSource`
   已知），再用 `func.py rip` 反查谁引用它 —— 那是「发事件的人」（GuideEffect 侧），
   顺着它能找到监听者注册的地方，从而100% 确认是不是 HUD。
   可以用 commonlibsf 现成的 `RE::BGSScannerGuideEffectStatusUpdateEvent::GetEventSource()`
   （`IDs.h` 里有条目）在自己的 DLL 里挂一个 sink，看**不举扫描仪时到底有没有事件**：
   有事件但没线 = 监听者不在；没事件 = GuideEffect 没跑（那就还有别的门控）。
2. **只打开「扫描仪的地面路径」这一层**：如果 Monocle HUD 是整块开关，那这条就与本
   MOD 的定位冲突（打开就等于举着扫描仪）。但可以查一下 HUD 里画路径的组件是否
   单独受某个 flag/GMST 控制（`GuideNoPath` 这种看起来就像）。**先试控制台**：
   `setgs GuideNoPath 0` / `setgs GuideNoMarker 0`，成本几乎为零。
3. **自己画（兜底方案）**：既然路径点只是「地上一串点」，可以自己按同样的规则
   在玩家与追踪目标之间铺一串可见引用（或给一条 `EffectShader`），完全不依赖 HUD。
   代价是要自己做寻路/贴地，最笨的版本（直线 + 高度采样）观感也够用。

### 7.4 与本 MOD 定位的关系（要跟用户确认的点）

原版「地上有引导线」= 举着扫描仪。本 MOD 的目标恰恰是**不举扫描仪**。
所以「导航线」这条需求天然地和引擎实现相冲：要么接受「线画不出来」，
要么走 7.3 的第 3 条（自己画）。下一轮先把 1/2 两条便宜的路走完再决定。

## 八、v2.4 第四次调研（2026-09-16 夜）—— 「线为什么必然不在」的三条硬证据

这一轮不再猜，全部是可复现的证据。

### 8.1 ★ 决定性证据：扫描仪 = `MonocleMenu`（B 社自己的脚本这么写的）

`Data\Scripts\Source\Base\ScanTempleScript.psc`：

```papyrus
bool usingHandscanner = false  ; this isn't going to work for real - we'll need
                               ; a way to check if you have the scanner up or not
...
RegisterForMenuOpenCloseEvent("MonocleMenu")
Event OnMenuOpenCloseEvent(string asMenuName, bool abOpening)
    If asMenuName == "MonocleMenu"
        usingHandscanner = abOpening          ; ← 菜单开着 == 举着扫描仪
```

`MQ_Temple_SubScript.psc` 里有一字不差的同款注释。也就是说：

- **原版「举着扫描仪」在引擎里的表现就是 `MonocleMenu` 处于 open 状态**；
- 不举扫描仪 ⇒ `MonocleMenu` 是关的 ⇒ 扫描仪那套 HUD（包括地上那条线）**根本不存在**；
- 顺带一个对我们的彩蛋：脚本侧可以用 **`RegisterForMenuOpenCloseEvent("MonocleMenu")`**
  精确知道「玩家此刻有没有举着扫描仪」（这是 B 社脚本自己用的办法，比任何 flag 都可靠）。

### 8.2 排除 7.3 的第 2 条：`GuideNoPath` 不是开关

直接在 `Starfield.esm` 里搜 EDID（`tools/re/esmstrings.py MagicGuide`）：

```
fMagicGuideSpacing          （f = float）
iMagicGuideWaypoints        （i = int）
fMagicGuideUpdateFrequency  （f = float）
sMagicGuideNoPath           （s = ★字符串★）
sMagicGuideNoMarker         （s = ★字符串★）
```

`s` 前缀 = **字符串型 GMST**（UI 文案），不是布尔开关。
⇒ 「控制台 `setgs GuideNoPath 0`」**不是一条路**。（exe 里那些
`MagicGuideHazardsPerUpdate:Magic` 之类是 INI 项名，不是 GMST 开关。）

### 8.3 引导路径的形态（exe 静态确认）

| 项 | 值 | 说明 |
| --- | --- | --- |
| `GuideEffect` | RTTI 有、**无 vtable** | 非多态工具类，只管算 |
| `GroundPathPathingNodeGenerator` | RTTI=`?AU`（**struct**），vtable=`0x4D98B90` | 方法在 `0x2777xxx`；内部按 **0x58 字节步长**的节点数组做向量/高度运算 = 算地面路径点 |
| `GroundPathRayValidator` / `WaterPathPathingNodeGenerator` / `IPathingNodeGenerator` | RTTI 有 | 地面射线校验 / 水面路径 / 接口 |
| `BGSScannerGuideEffectStatusUpdateEvent` | RTTI=`?AU?$BSTEventSource@U…`，**只有 RTTI、无 vtable** | 状态广播事件；`BSTGlobalEvent::EventSource<T>` 同 |
| MGEF `0003CC95` 全部子记录 | `EDID/FULL/DATA/DNAM` | **没有任何 `CTDA` 条件**、没有 VMAD、没有关键词 ⇒ 效果本身**不**门控扫描模式，门控在渲染侧 |

★ 一个坑：commonlibsf 里 `BGSScannerGuideEffectStatusUpdateEvent::GetEventSource{ 0 }; // 138080`
的 ID **是过期的** —— 地址库 ID 138080 → RVA `0x2825D30` 只是个 `jmp` thunk，
指向一个有 **60+ 调用者**的通用函数（看入口就知道是某种 variant 析构/分发），不可能是 getter。
所以**目前拿不到事件源单例地址，没法在 DLL 里直接挂 sink**（这条路暂时封死）。

### 8.4 结论（把 7.4 的「可能」升级为「确定」）

```
持扫描仪 → MonocleMenu.open → 扫描仪 HUD 存在 → 监听 BGSScannerGuideEffectStatusUpdateEvent
                                              → 把 GuideEffect 算出的地面路径点画到地上
不持扫描仪 → MonocleMenu 关 → 没有监听者 → 事件（即使发了）没人画 → 地上什么都没有
```

- `guideState=3`（7.1 实测）说明**效果确实在跑**，但**渲染 HUD 不在**，两者不矛盾；
- 引导路径与「不举扫描仪」在引擎实现上**确实互斥**（不是我们没找对 API）；
- 另外：`PathMarker*` 在 ESM 里全是**任务专用**的 escort 标记（`FFNewHomesteadZ01_*PathMarker*`），
  **没有可复用的「引导线路径点」通用形态**；`GuideMarker` 一个都没有。

## 九、v2.4 实现：自绘「面包屑引导路径」（用户选定 B 方案）

### 9.1 结论先行：原版那条线**拿不回来**，所以自己铺

见第八节。既然「线」是扫描仪 HUD 画的、不举扫描仪就不存在，那唯一能兼顾
「不举扫描仪」和「地上有路标」的办法就是自己画。这里选的是**沿玩家→引导目标
铺一串地面光点**（面包屑），观感与原版同源（都是「发光的路标」）。

### 9.2 关键 API —— 全部是 Papyrus 现成的，**一行 RE 都不用**

| API | 用途 |
| --- | --- |
| `ObjectReference.PlaceAtMe(Form, count, forcePersist, initiallyDisabled, deleteWhenAble)` | 铺标记 |
| `ObjectReference.MoveToNearestNavmeshLocation()` | ★ **贴地**。「把物体移到 navmesh 上最近的位置」——**不需要射线**，B 社自己的 `TestNPCArenaScript.psc` 就是用这句把路径标记放到 navmesh 上的（原注释：*Put the marker on the navmesh near its new position*） |
| `ObjectReference.SetPosition / Enable / Disable / BlockActivation / GetParentCell / MoveTo` | 摆放与控制 |
| `Quest.GetCurrentStageTargets()` + `Game.GetPlayerActiveQuests()` | 引导目标 |
| `Math.sqrt` | 距离 |
| `RegisterForMenuOpenCloseEvent("MonocleMenu")` | ★ 玩家**自己**举着扫描仪时让位给原版，不画两条 |

### 9.3 标记形态：为什么用原版 `LIGH`

标记用的是 **`LIGH 0x00012E5A GenPointFlare1`**（一个点光源）。

- 选它的理由：**不需要自造网格**。LIGH 放在地上就是一摊光，
  和原版那条线一样是「发光的路标」，观感同源；
- 想换观感（或换成带网格的小物件）**只改 `CfgGuideMarkerFormID()`**，不用动代码；
- 每个标记都 `BlockActivation(True, True)` —— **绝不抢玩家的交互**（AGENTS.md 红线）。

### 9.4 数据流 / 新增两个 GLOB

| FormID | EDID | 方向 | 含义 |
| --- | --- | --- | --- |
| `0x809` | `SAS_On` | DLL → 脚本 | F8 开关状态（1/0）。脚本据此决定画不画面包屑 |
| `0x80A` | `SAS_GuideMarkers` | 脚本 → DLL | 当前点亮的标记数；**-1 = 开着但找不到引导目标**（看这个数就知道是「没目标」还是「脚本没跑」） |

`SAS_On` 必须在 DLL 里写：脚本侧**没有任何**「高亮开关是否打开」的查询接口
（连「扫描仪是否举着」都得自己用菜单事件记，见 8.1）。

### 9.5 实现要点（`scripts/SAS_Bridge.psc`）

- `UpdateGuidePath()` 挂在既有的 0.25 秒心跳里，但**自己限频**：
  最短 0.5 秒一次，且**玩家移动超过 1.5 米**才重算
  （`MoveToNearestNavmeshLocation` 是 navmesh 查询，别白跑）；
- 引导目标**缓存 2 秒**（`FindGuideTarget` 要遍历所有 active quest，别太频），
  目标失效（被打掉/关掉/换 cell）立刻重查；
- 目标距离 ≤ 起始距离+一个间距时收掉（太近没必要画）；
- 玩家举着扫描仪（`MonocleMenu` 打开）时**主动收掉**，让原版画；
- 读档（`OnPlayerLoadGame`）清掉目标与时间戳，强制重算。

### 9.6 ★ 已知局限（如实记录，不假装）

**Papyrus 没有「玩家正在追踪哪一个目标」的查询接口**
（`Game.GetPlayerActiveQuests()` 只有 active quest 列表，`Quest` 上没有 IsTracked）。
所以引导目标取的是：

> 所有 active quest 的 `GetCurrentStageTargets()` 里、**同一 cell 内距离最近**的那个

这在大多数情况下就是玩家要去的那个，但**不是严格意义的「追踪目标」**。
要精确到「追踪中的那一个」需要 hooks/RE（引擎里那个状态由指南针/任务系统持有），
列在 `docs/99` 的待办里。

### 9.7 v2.4 游戏内实测判据

日志（`SAS_AlwaysScan.log`）里：
```
  papyrus: guideHb=NNN guideState=3 guideMarkers=M
```
- 启动期**不应**出现 `BindForms: guide 诊断 GLOB 缺失` 或
  `BindForms: 引导路径 GLOB 缺失（3305 / 3306）`；
- `guideMarkers = -1` ⇒ 脚本在跑但**同一 cell 里找不到任务目标**（正常：没追踪任务/目标在别的 cell）；
- `guideMarkers = 0` ⇒ 有目标但太近（≤ 约 8 米），或玩家正举着扫描仪，或 F8 关着；
- `guideMarkers = 8` ⇒ 8 个面包屑全亮；
- 有远处目标（>8 米）却仍然恒为 `0` ⇒ **`PlaceAtMe` 没造出来**（形态不可放置），
  换 `CfgGuideMarkerFormID()`；有数但地上什么都没有 ⇒ 造出来了但**这个 LIGH 看不见**，
  同样换形态（见 9.7 第 2 条）；
- 按 **F8** → `guideMarkers` 立刻变 0 且地上光点全灭；再按 → 回来。

观感：
1. 接一个任务、把目标点标出来（追踪），不举扫描仪 → 身前地面上出现一串**光点**，指向目标；
2. 走动时光点会**跟着贴地**更新（不会悬空/埋地）；
3. 举着扫描仪时自己的光点消失，只有原版那条线（不重叠）；
4. 走近到 10 米内光点自动收掉（不糊在脚下）。

## 十一、v2.6（2026-09-16 深夜）—— 实测定位 + 「代理目标」

### 11.1 v2.5 诊断实测（Papyrus 日志原文）

```
[SAS] guide/diag: activeQuests=2 myCell=00227BA5
[SAS] guide/diag:  q=0000D773 stage=0  targets=0 tracked=true
[SAS] guide/diag:  q=0024EF9C stage=61 targets=1 tracked=true
[SAS] guide/diag:    t=FF01E9CB d=605m same=false dead=false cell=FF01D4DE
[SAS] guide/diag:  -> sameCell=None trackedSame=None anyCell=FF01E9CB anyD=605M
[SAS] guide: 没有同 cell 的目标（markers=-2 otherCell=FF01E9CB otherD=605m）
```

读法：

- `activeQuests=2`：一个是系统任务 **`SQ_Followers`**（`0x0000D773`，`targets=0` 正常），
  另一个 **`0x0024EF9C` = `MQ305`「一大步」**（主线终局；用户的任务菜单截图确认了名字）；
- `targets=1` ⇒ **QSTA 这条路是通的** —— 10.2 里「QSTA 缺失」的嫌疑**被排除**；
- 但 `same=false`、`cell=FF01D4DE` ⇒ 目标在**另一个 interior cell**（`FF` 前缀 = 运行时
  生成的 cell，这里就是**飞船内部**）。两个 interior cell 的局部坐标不可比，
  **`d=605m` 是个无意义的差值**；
- ⇒ 恒 `-2`：地上永远不会有东西。这就是「任务引导线仍然没有」的全部原因。

### 11.2 做法：目标不在同一坐标空间时，画「代理目标」（`FindGuideDoor`）

| 优先级 | 代理 | 依据 / 说明 |
| --- | --- | --- |
| ① | **`Cell.GetParentRef()`** | B 社注释原文：*the ship if this is a ship interior/exterior cell*。目标 cell 是飞船内部时它就是**世界里的那艘船**；玩家与它在同一坐标空间（比如都在室外）时直接指过去 —— 比找门准得多 |
| ② | **通往目标 cell 的门** | `FindAllReferencesOfType(FormList, radius)`（注释：*objects in the given list* ⇒ 接受 FormList）+ `GetTeleportCell()` 精确匹配（飞船的登机舱门） |
| ③ | 通往室外的门 | **只在玩家自己在室内时**兜底（先出去）。走出门换了 cell 会自动重算 ⇒ 自然形成**多跳指引**（The Rock 出口 → 外面的船） |

**新增 `0x80B FLST SAS_DoorBases`** = master 里全部 **339** 个 DOOR base
（`build_sas.pas` 的 `CollectDoorEntries` 递归遍历 DOOR 组打包；构建日志 `doors=339/339`）。

**坑**：Papyrus **不允许把变量命名为 `door`**（"Door" 是已知类型名）——
`variable door cannot have the same name as a known type or script`，改 `dr` 即过。

### 11.3 判据（v2.6 实测）

1. 在 The Rock 里（`myCell=00227BA5`）：光点指向**出口门**（日志 `isProxy=true`）；
2. 走到室外（Akila City）：飞船在 60 米内 ⇒ 指向**船体**（`GetParentRef()`，
   仍是 `isProxy=true`）；更远时可能 `-2`，走近停机坪应恢复；
3. 上船后（与目标同 cell）⇒ `isProxy=false`，光点直接指向目标本身；
4. `guideMarkers` 不再是 `-2` / `-1`，而是 `1..8`。
