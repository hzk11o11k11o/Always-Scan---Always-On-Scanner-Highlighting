# 37 · 「静态场景正常、动态场景卡顿」—— 热路径去内核化 + 判空缓存（DLL v5.1.0 订正 R4 / 公开版仍 2.0）

> 建立：2026-09-27（深夜）。
> 触发：用户报告（原文）——
>
> ```
> 再静态场景下帧数看上去正常，但动态场景下会产生卡顿，比如战斗场景，或是玩家移动时扫描新的高亮物品。检查一下
> ```
>
> 承接 `docs/36`（v5.1-R3：环内 cell 分片遍历）。
> **一句话结论**：R3 的假设（「耗时 = 遍历量 × 常数」）**被它自己的日志证伪** ——
> 同一局里 **同样 1540 个引用**，静止时 `loop=10ms`、走动时 `loop=63ms`。
> 真正的变量是**单次操作的墙钟成本**：而热路径上唯一会「进制内核」的两件事
> （`SafeReadMem` → `ReadProcessMemory`、`IsReadable` → `VirtualQuery`）都要拿
> **进程地址空间锁** —— 游戏流式加载（走动 / 战斗 = 大量 commit / decommit）时
> 那把锁被抢，单次从 ~10µs 涨到几百 µs ⇒ 一轮几百次 = 几十毫秒。
> 治法 = **① 安全读改 SEH 直读（零内核调用）② 容器 / 尸体判空按引用缓存
> （事件失效）③ 计时精度 ms → µs + 卡顿检测 + 最慢一轮快照（把结论钉死）**。

## 一、证据链（用户 2026-09-27 08:32~08:48 那一局日志）

### 1.1 ★ 决定性的一条：同样的遍历量，墙钟差 6 倍

| 窗口（UTC+8） | 玩家在干什么 | 遍历引用（cur+ring） | `loop avg` | `walk` | `sync` |
| --- | --- | --- | --- | --- | --- |
| 08:37:52 | **站着不动**（`move=0.0m`） | 353 + 1185 = **1538** | **10ms** | 10ms | 7ms |
| 08:47:30 | **走动**（`move=7.1m`） | 741 + 804 = **1545** | **63ms** | 63ms | 11ms |
| 08:48:32 | **走动**（`move=2.5m`） | 251 + 1036 = **1287** | **64ms** | 64ms | 7ms |
| 08:48:44 | 走动 | 178 + 757 = **935** | **45ms** | 45ms | 3ms |

* 遍历量几乎一样，墙钟差 **6 倍** ⇒ 不是「做了多少事」，而是「每件事多贵」；
* `sync`（引擎调用，`outline` 挂 / 摘 / 3D 复检）两边都是 **7ms**、
  `3D复检 probes` 都在 700~800 次/窗口 ⇒ **引擎调用没有变慢**；
* 候选数（`cand`）、判空次数（`搜空: empty+notEmpty` ≈ 30 次/轮）、
  被拒的 STAT 数（`ft=41x27150`）两边**也几乎一样** ⇒ 与这些无关；
* 时间形态是**尖峰**：`loop avg=64ms max=157ms`、`scan avg=76ms max=171ms`
  —— 少数几轮 150ms+ 的停顿就是用户感觉到的「卡顿」。

### 1.2 R3 的假设为什么不成立（以及它为什么一行都没生效）

* R3 的推理是 `环总量上限 60000 × 0.9µs ≈ 54ms`，但那一局的真实遍历量只有
  **935~1545**（环内各 cell 都 ≤ 2000 引用）⇒
  `分片推迟=0`、`RingSliceMaxRounds` **一次都没派上用场**（细片只在 >2000 引用的
  cell 上生效）。也就是说 R3 的改动在用户抱怨的场景里**是空操作**。
* 「每引用 ~1µs」这个常数也是错的：静止时实测 ~6.5µs/引用、走动时 ~40µs/引用。

### 1.3 计时本身在骗人（R3 那行 `loot=0ms flora=2ms` 是假象）

所有分段计时原来是 `NowMs() - t0`（**毫秒整数，按次取整**）——
热路径里的判空 / 分类 / 植物判据恰好全是「单次几百 µs、一轮几十次」的形态，
**每次都被取整成 0** ⇒ 真实开销全部躲在 `walk` 里看不见。
本轮把计时换成 `QueryPerformanceCounter` 的 **µs**（`NowUs`），
并新增 `timing3` 行（见 §二）。

### 1.4 主因候选：进程地址空间锁（`ReadProcessMemory` / `VirtualQuery`）

* 一轮扫描要跑 **30+ 次判空**（每个容器 / 尸体一次），每次 `RefLootState` 里
  `SafeReadMem`（= `ReadProcessMemory`）**5~15 次** ⇒ 一轮 **~170~400 次内核调用**；
* 加上形状校验 / 探针的 `VirtualQuery`（`vq=3~12/轮`）；
* 反推：64ms ÷ ~170 次 ≈ **380µs/次** —— 而正常情况下这两个 API 是 ~1~10µs。
  唯一能解释「10~30 倍慢」的就是**锁竞争**（流式加载在改页表 / VAD），
  这与「走动 / 战斗时才卡」精确对应（静止时没有任何人抢那把锁）。
* ★ 旁证：`shape`（正是 VirtualQuery 集中的那一段）在静止时 `0ms / vq=3`、
  走动时 `1~3ms / vq=9~12` —— 同样次数、更贵。

**行为变化（给用户的三句话）**：

1. **动态场景的卡顿应当消失**（或大幅减轻）：一轮扫描里那几百次「进制内核」的读
   变成纯用户态直读；判空从「每轮 30+ 次」降到个位数（缓存命中）；
2. **观感不变**：拿空即灭 / 展示柜 / 自愈 / 配色 / 植物全部不回归
   —— 判空缓存的失效靠**事件**（拿 / 放物品、界面开关），延迟与旧版逐帧一致；
3. **可回退**：`FastReadMem=0`（退回内核读）、`LootCacheTtlMs=0`（每轮实时判空）。

   本次修复的主要收益就没有了）。
2. ★★ **动态场景帧数**：走动 / 战斗时 `timing: scan avg` 与 `timing2: loop avg`

3. ★★ **`timing3` 行**（新格式）出现，且：

   * `其它=`（纯指针遍历 + 距离）占大头 ⇒ 下一步做「按引用的位置 / 分类缓存 + 分片刷新」。

6. 判空延迟感受：**打开容器拿空并关掉** ⇒ 高亮应和以前一样在 ~1.5s 内熄灭
   （缓存不是靠 TTL 生效，而是靠事件作废 ⇒ 不应变慢）。

## 五、经验（写给下一轮）

1. **「优化」的前提假设必须能被自己的日志证伪**：R3 把「耗时 = 遍历量 × 常数」
   写进了代码注释，却没在日志里留一个「遍历量 ↔ 耗时的对照组」——
   本轮靠**同一局里的静止 / 走动窗口**一眼看穿（1538 vs 1545 引用、10ms vs 63ms）。
   **改完要顺手加一条能推翻自己的判据**（本轮 = `timing3` 的 `卡顿` 与 `最慢一轮 cpu=`）。
2. **计时精度就是诊断能力**：`NowMs() - t0` 这种「按次取整」的 ms 计时，
   对「单次几百 µs × 几十次」的操作**恒为 0** —— R3 的 `loot=0ms flora=2ms`
   是假象，真相躲在 `walk` 里。改动很小（`NowUs`），但它是本轮能定位的前提。
3. **平均值的分母要对**：早退轮（形状没过 / 等稳定 / 静置期）在旧口径里也进分母，
   把平均值整体稀释；本轮引入 `scanFullSamples`（只有真跑完遍历的轮才进平均）。
4. **★ 危险操作要先「换算成次数 × 单价」再看**：`SafeReadMem` 单次看是「一条
   API 调用」，一轮几百次、每次几百 µs 就是几十毫秒 ——
   和 R3 的 `60000 × 0.9µs = 54ms` 是同一个算法，**只是这次算的是内核调用**。
   推论：**进程内的安全读永远不要用 `ReadProcessMemory` / `VirtualQuery` 做热路径**
   （它们要拿地址空间锁）；SEH 直读的语义等价、成本差 1000 倍。
5. **自检要测「失败路径」**：`SehReadMem` 的风险不在「读得到」，而在「读不到时
   能不能安全返回」—— 所以自检专门 reserve 一页不可读内存去读它。
   这把「万一有别的模块吞掉访问违例」这种致命情况留在**启动日志**里，
   而不是留到游戏里崩 / 卡。
6. **「性能开关」与「行为开关」都要有**：`FastReadMem` / `LootCacheTtlMs`
   各自都能一行 INI 回到旧行为 —— 出问题时用户能自救，我们也能对照。
