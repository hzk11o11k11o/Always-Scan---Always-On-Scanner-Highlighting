## 三、新发现：日志第二列是「线程 ID」不是 PID（多线程回调的日志实证）

**现象**：1234 行里有 **29 行**第二列不是 `11444`，而是 11 个其它数字
（`37832`×6 / `2892`×5 / `26200`×4 / `34148`×3 / `26388` / `33444` / `35592` / `37568` /
`12488` / `32088` / `37000`）；这 29 行**全部是 `menu event:`**
（MonocleMenu / FaderMenu / FanfareMenu / ScopeMenu / HUDMenu / HUDMessagesMenu）。

**查证（两处都读了代码）**：

* 该列是 spdlog 的 `%t`（线程 ID）—— `plugin/src/main.cpp` 的
  `spdlog::set_pattern("[%T.%e] [%=5t] [%L] %v")`（**不是 `%P`**）⇒
  `11444` = 主线程（Windows 主线程 TID 恰好等于进程 ID），其余 = **引擎的 UI / 工作线程**。
* `OnMenuEvent`（`AlwaysScan.cpp` 3278 行起）的注释早就写着
  「**可能来自 UI 线程 ⇒ 只做「记状态 + 少量日志」，绝不做引擎调用**」；实现确实线程安全：
  `g_state.menuEvtLock` 互斥保护共享数组、计数用 `fetch_add`、唯一给主线程的交接是
  atomic（`menuEvtOpen`）；日志 sink `SizeLimitedFileSink : base_sink<std::mutex>` 自带锁。
* 「MonocleMenu 关闭 → 待重申」自愈**不在事件回调里做** —— 主线程每帧轮询
  `IsMonocleMenuOpen()`（`DetectEngineOutlineLoss`）；10 条 `引擎侧高亮疑似丢失` 全部由
  `11444` 打印 ✓。

⇒ **不是缺陷**：v4.11 起就按「多线程回调」预防设计的，本局日志第一次给出实证
（29/1234 ≈ 2.4%）。**记录它的价值 = 纠正一个读日志的默认假设**
（「第二列 = PID」会让「多个数字」看起来像多个进程在写同一份日志）。

## 五、经验

1. **读日志前先读一遍日志的 pattern**：这一列到底是 `%P`（PID）还是 `%t`（TID）要查代码 ——
   本项目的 `set_pattern("[%T.%e] [%=5t] [%L] %v")` 决定了它是**线程 ID**；
   不查就会把 29 行「陌生数字」误读成「多个进程」。
2. **注释里的「可能」要拿日志去证**：v4.11 写「可能来自 UI 线程」是预防性设计，
   本局日志第一次实证（2.4% 的事件确实来自非主线程）；
   **预防性线程安全（锁 + atomics + 「不调引擎」）经得起实证** —— 当时多花十分钟、现在省一次事故。
3. **验收点的最强证据 = 病根场景复现成功**：R12 的病根（额度被 3 个 base 用光 ⇒ 零日志）
   在本局**原样发生**（前 8 条判绿额度 14:21:27 用光），而第 9~12 条仍打出 ⇒
   这比「看到有日志」强得多。
4. **数字先对账、再下结论**：`兜底K1=137 == 73+64`、`满=73 == 问=73`、
   `10 组缓存作废 == 10 次举放扫描仪` —— 全部对上后才说「没有遗漏」。
