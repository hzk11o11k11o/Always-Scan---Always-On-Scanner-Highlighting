## 二、配色：为什么必须「覆盖颜色」

### 2.1 11 个状态的**实测**原生配色（游戏日志直读，不是猜的）

`SAS_AlwaysScan.log` 里 `outline colors[world-ready]:` 那 11 行（2026-09-25 那一局）：

```

state= 1 Scanned         ref=#B3C1EF (179,193,239)   淡蓝白
state= 2 FullyScanned    ref=#1F8EE2 ( 31,142,226)   蓝
state= 3 Tracked         ref=#1F8EE2 ( 31,142,226)   蓝   ← 与 2 完全相同

state= 5 Social          ref=#27C684 ( 39,198,132)   绿   ← 与 4 完全相同

state= 7 TargetScannable ref=#000000 (  0,  0,  0)   黑   ← ref 表为 0，画不出来
state= 8 TargetScanned   ref=#000000 (  0,  0,  0)   黑
state= 9 TargetFullyScanned ref=#FFAA00 (255,170,0)  橙

```

⇒ 原生可区分的颜色只有 **6 种**（青 / 淡蓝白 / 蓝 / 绿 / 橙 / 红），
而本轮要 6 个物品组 **外加** 容器、尸体、设备、门、植物各一种 ⇒ **不够**。
所以「笔记」「资源」两组改成 **覆盖颜色**（`ColorNote` / `ColorResource`）。

### 2.2 引擎自己会写哪些状态（决定「覆盖哪一个」的代价）

`func.py callers 0x17D52B0`（「写 outline 状态」的唯一函数）：

```
RVA 0x159F325 (func 0x159ED90, +0x595)
RVA 0x159F654 (func 0x159ED90, +0x8C4)
```

⇒ 全镜像只有**一个**写入方（原版扫描仪的逐引用求值函数 `0x159ED90`），
反汇编它写状态的那一段（`0x159F604`~`0x159F654`）：

```
0159F60C  movzx eax, byte ptr [rbp + 0xe8]   ; 某个「已扫描」标志
0159F61E  add edx, 7                         ; ⇒ 状态 7 / 8
0159F63C  add edx, 2                         ; ⇒ 状态 2 / 3
0159F643  setne dl                           ; ⇒ 状态 0 / 1
0159F31B  mov edx, 9                         ; 另一处：状态 9（追踪）
```

⇒ 引擎只会产出 **0/1、2/3、7/8、9**（外加 12 = 清除）。
**4 / 5 / 6 / 10 全镜像没有任何代码写** ⇒ 这四个状态是「本 MOD 专用」的。
（这也解释了为什么 4/5/6/10 的 mgr 参数看着像没初始化。）

### 2.3 颜色 dword 的格式与「谁才是画出来的颜色」

两处反汇编实证：

**(a) 静态初始化函数**（`0x1AFC70`，唯一引用配色表 RVA 的代码）：

```
001AFC9D  mov word ptr [rbp + 0x21], 0x3ead   ; 低字节序：+0x21=0xAD, +0x22=0x3E
001AFCA3  mov byte ptr [rbp + 0x20], 0xf2
001AFCA7  mov byte ptr [rbp + 0x23], 0xff     ; alpha
001AFCAB  mov eax, dword ptr [rbp + 0x20]     ; = 0xFF3EADF2
001AFCAE  mov dword ptr [rip + …], eax        ; 写进表
```

⇒ dword 布局 = **`0xAARRGGBB`**（state 0 = 0xFF3EADF2 = 青 + 不透明；
另一条写入的 alpha 是 0x80 = 「Low」那一半，脉冲用）。

**(b) 挂引用时**（`0x17D4CD0`）：

```
017D4E2C  lea rax, [rbx + rbx*4]
017D4E30  shl rax, 5                         ; state × 0xA0
017D4E34  vmovd xmm0, [rax + r15 + 0x5919B08] ; ★ 引用参数表 +0x00
017D4E3E  vpshufd / vpand with {00FF0000,0000FF00,000000FF,FF000000}
017D4E53  vcvtdq2ps … vmulps {…,1/255,…}
```

⇒ **画出来的颜色 = 「引用参数表」（RVA `0x5919B08`）+0x00 那个 dword**，
挂引用时被拆成 4 个 float 分量；表里 state 7/8 = `0x00000000` ⇒ 这两个状态
**原生永远画不出来**（原版也不靠它们画描边）。

⇒ 结论（本轮的改动依据）：
1. 覆盖颜色**必须写 ref 表**（原来的代码两张表都写，保留）；
2. **alpha = 0 的槽要补成 0xFF**，否则覆盖了 RGB 也看不见（state 7 就是这种）；
3. 管理器参数表（`0x591E088`）+0x00/+0x20 是**脉冲插值**用的颜色，实测 alpha 是 0，
   只改 RGB、alpha 原样即可。

## 三、实现（`plugin/src/AlwaysScan.cpp`）

| 项 | 内容 |
| --- | --- |
| `Category` | 原来的 `kLoot` 后面插入 `kLootWeapon / kLootApparel / kLootAmmoAid / kLootNote / kLootResource`（共 12 类）——**`kLoot` 仍是下标 0，INI 老键名 `StateLoot/EnableLoot/ColorLoot` 不变含义变成「杂项」** |
| `ClassifyBase` | 按 formType 分派：WEAP→武器 / ARMO→服饰 / AMMO+ALCH→弹药救援 / BOOK+NOTE→笔记 / MISC→（资源 ∨ 杂项）/ 其余→杂项。**每个引用的分类仍是一次纯 switch**，只有 MISC 多一次关键词读 |
| 资源判据 | `IsResourceBaseRaw()`：读 `TESObjectMISC` 的 `BGSKeywordForm::keywords`（**base + 0x208**），逐层形状校验（data 可读 ∧ 1≤size≤64 ∧ capacity≥size ∧ 每个元素是指向 **KYWD** 的指针），命中 28 个 `ResourceType*` FormID 之一 ⇒ 资源。**任何一步不过就返回 false（= 杂项）**，失败方向永远是安全的那一边 |
| 启动自检 | `ResourceKeywordSelfTest()`：用 `InorgCommonIron`(0x5556E) 必须命中、`Digipick`(0xA) / `Credits`(0xF) 必须不命中来验判据；数据没就绪就下一轮再来（**永不放弃**，与库存标定同套路）。不通过 ⇒ 资源归杂项 + 一条 WARN |
| 颜色覆盖 | `ApplyColorOverrides()` 现在会：① 只对非 `kColorUnset` 的类别动手；② ref 表 **alpha=0 时补 0xFF**；③ 日志里打 ref 原值（便于核对） |
| INI 新键 | `StateWeapon / StateApparel / StateAmmoAid / StateNote / StateResource`、`EnableWeapon / …`、`ColorNote=FFD700 / ColorResource=AA6EFF`、`ResourceByKeyword=1` |
| 诊断 | 启动日志：`config: stateByCategory: loot=2, weapon=0, …`、`config: colorOverride（实际生效）: note=#FFD700, resource=#AA6EFF`、`resource keyword: 判据自检**通过**/失败`；运行日志：`category (本轮选中): loot=…, weapon=…, resource=…` 自动多出 5 列 |

**二进制级验证**（本项目的惯例，`tools/re/symfind.py` + `disasm.py` 对 DLL 反汇编）：

```
0001AB60  add rcx, 0x208            ; base + 0x208（IsReadable(base+0x208, 16)）
0001AB74  mov esi, [rbx + 0x210]    ; size
0001AB7D  cmp eax, 0x3f             ; size ≤ 64
0001AB86  cmp [rbx + 0x214], esi    ; capacity ≥ size
0001AB92  mov r14, [rbx + 0x208]    ; data
0001AB99  movabs r15, 0x7ffffffefffd / lea rax,[r14-0x10001] / cmp / ja  ; 指针合理性
0001ABC7  lea r12, [rip + …]        ; = kResourceKeywords 首
0001ABCE  lea rbp, [rip + …]        ; = kResourceKeywords 尾
0001ABE0  mov rbx, [r14 + rdi*8]    ; 逐个关键词
```

⇒ 偏移、形状校验、关键词表比较**都按设计生成了**（不是「写了但被优化掉」）。

## 五、MO2 版本号（同一轮的用户要求）

用户反馈（附截图）：
- MO2 的 mod 列表里显示 `4.16`，要求**改成 1.6**（= N 网公开版号）；
- 更新提示里 `installed version: "4.16.0", newest version: ""` —— **读不到 N 网版本**。

排查与结论：

| 项 | 结论 | 依据 |
| --- | --- | --- |
| 为什么 newest version 是空 | **`meta.ini` 里 `modid=0`** ⇒ MO2 根本不知道去查哪个 mod 页 | 部署目录 `meta.ini`（改前）；MO2 2.5.2 的二进制里有 `https://api.nexusmods.com/v1`、`newestVersion`、`Manual Nexus API Key` 等字符串 ⇒ 它走 **Nexus API** 读 mod 页的 `version` 字段 |
| 修法 ① | `tools/build-sas.ps1` 部署时写 **`modid=18268`**（N 网 mod 页 ID，用户提供） | 已改，部署后的 `meta.ini` 实测 = `modid=18268` |
| 修法 ② | 部署时写 **`version=1.6`**（N 网公开版号，不是 DLL 内部 4.17.0） | 已改；MO2 列表从此显示 1.6 |
| 还需要用户做的 | ① 在 N 网把 1.6 的文件版本填对（mod 页 Version 通常取最新文件的版本号）；② MO2 → Settings → Nexus 里**完成 API key 连接**（`Connected`），否则 API 读不到；③ 重启 MO2 后用右键 **Check for updates** | 二进制字符串 `Not connected/Connected/Manual Nexus API Key/Received user account information` |

★ 注意：`meta.ini` 的 `version` 与 DLL 内部版本是**两套号**——
发布版 1.6 = DLL 4.17.0（README / 描述里写 `Version 1.6 (plugin build 4.17.0)` 对账）。

## 七、可复用经验

1. **「物品栏分类」在数据里不是 formType 一个维度** —— 游戏自己用
   `InventoryCategory*` 关键词标记（武器/服饰/救援子类），而「资源」用的是
   `ResourceType*` 关键词、**不是**独立的记录类型（`IRES` 是另一回事：那是星球生成
   数据用的 `BGSResource`，332 条，不在物品栏里）。
2. **「同一个签名里再分流」要挑判据，不要挑名字**：`Inorg*` 这种 EDID 前缀能对上，
   但真判据是关键词（第三方 mod 加的资源同样带官方关键词 ⇒ 自动覆盖）。
3. **读结构体前先自检**：commonlibsf 的偏移错过不止一次（`TESObjectCELL` +8），
   所以这次给「资源判据」配了**用已知答案样本的启动自检**（Iron 命中 / Digipick、Credits
   不命中）—— 偏移一变，日志立刻有一行 WARN，而不是静默按杂项处理。
4. **覆盖颜色时别忘了 alpha**：`0xAARRGGBB` 里 alpha=0 的槽（state 7/8）改了 RGB
   也画不出来 —— 而且「哪个表才是画出来的颜色」要靠反汇编确认（ref 表 +0x00），
   不能只看「两张表都写了一遍」。
5. **改配色前先数「引擎到底会写哪些状态」**（`func.py callers`）：引擎只写
   0/1、2/3、7/8、9 ⇒ 4/5/6/10 是安全的「自留地」，覆盖它们对原版零影响。
6. **★ 写进表 ≠ 生效（v4.18）**：颜色只是「参数表的静态数据」，真正落地要经过
   「管理器创建 → 把参数交给渲染侧」。**管理器只在创建那一刻读表**（已存在的不刷新），
   所以覆盖必须在**创建之前**写；否则表里全是新值、画面全是老色，而日志看起来一切正常。
   详见 `docs/17`。
