# 01 · 原版扫描仪高亮机制调研

> 2026-09-16。本文件记录「原版怎么做到高亮」的逆向结论，以及为此写的工具。
> **结论对 MOD 的直接影响**：v1 用 EFSH 实现视觉；「直接驱动引擎自带 outline」
> 这条路已经定位到入口，但需要深度逆向渲染层，留作后续。

游戏版本：**Starfield 1.16.244.0**（Steam），SFSE 0.2.21。

## 一、工具（`tools/re/`，全部无第三方重依赖，只用 `pefile` + `capstone`）

| 工具 | 用途 |
| --- | --- |
| `versionlib.py` | 解析 SFSE Address Library（`versionlib-1-16-244-0.bin`）→ `REL::ID` 转 RVA；反汇编；E8/E9 xref；dump 数据段 |
| `xref.py` | **本项目新增**。三种交叉引用：`--rip`（RIP 相对，x64 上找全局变量/vtable 的唯一办法）、`--abs`（8 字节绝对指针）、`--call`（直接 call/jmp） |
| `rtti.py` | **本项目新增**。扫 `Starfield.exe` 里的 RTTI 类型名（`.?AV...@@`），按正则过滤 —— 用来「先确认引擎里到底有哪些相关类」 |
| `rtti_vtable.py` | **本项目新增**。按 RTTI 类名找回 vtable 与虚函数地址；也给 `--vtable <RVA>` 反查「这个 vtable 属于哪个类」（它的逆运算） |
| `efsh_dump.py` | 直接按字节解出插件里 EFSH 的 DNAM 载荷（不需要 xEdit） |
| `minidump.py` / `symaddr.py` | 崩溃转储解析与符号化（上一代项目留下的） |
| `scan_disp.py` | 按「成员偏移」反查引擎指令，用来验证某个偏移读法对不对 |

### 踩坑（写工具时真栽过的）

1. **RIP 相对引用必须做形状校验**。算法本身很简单（`disp 字段所在 RVA + 4 + disp32 == 目标`），
   但**随便 4 个字节都可能碰巧等于所需的 disp32** —— 第一版没校验，把
   `mov rcx,[rax+0x48]` 的后半截当成了 RIP 引用，白追了一条线。
   修法：从 `p-3 ~ p-10` 逐个候选起点反汇编，要求**恰好一条指令**结束在 `p+4`，
   且操作数里有一个 `X86_REG_RIP` 的 mem。
2. **`getsymbol`/`std::min` 之外，`VK_*`/`GetAsyncKeyState` 需要 `NOMINMAX`**（见 `plugin/src/PCH.h`）。
3. **`pefile.get_memory_mapped_image()` 是按 RVA 索引的**，不能拿 `get_offset_from_rva()` 的结果去索引它。

## 二、结论 1：扫描仪的内部代号是 **Monocle**

`Starfield.exe` 的 RTTI 里有：

```
MonocleMenu / MonocleMenu_Bioscan / MonocleMenu_Harvest / MonocleMenu_OpenDoor
MonocleMenu_ZoomIn / MonocleMenu_ZoomOut / MonocleMenu_SurfaceMap ...
MonocleUIDataModel / MonocleUIDataModel::PickRefData / ResourceArcData ...
PlayerControls::MonocleHandler
nsMonocle::MonocleFastTravelConfirmFunc
```

→ 手持扫描仪在引擎里叫 **Monocle**。所有与它相关的配置项在 GMST 里归在 `:Monocle` 分类。

## 三、结论 2：扫描仪高亮 = 引擎自带的 **outline 高亮系统**，而且是数据驱动的

`Starfield.exe` 的字符串表里有整套 `名字:分类` 的 GMST（Bethesda 用这种形式登记
INI/设置）。挑重点：

**基础（通用高亮，工坊模式也在用）**
```
fOpticalDepthThreshold:Highlight
uDefaultHighlightFillColor:Highlight
uDefaultHighlightOutlineColor:Highlight
fDefaultHighlightOutlineThickness:Highlight
fDefaultHighlightOutlineHardness:Highlight
fHighlightOutlineThickness:Workshop / fHighlightOutlineHardness:Workshop
fHighlightFoodOutlineThickness:Crafting / fHighlightWeaponsOutlineThickness:Crafting ...
```

**扫描仪（Monocle）专用 —— 按「状态」分别配色/配粗细/配脉冲**
```
aHighlightScannableOutlineColorHigh/Low :Monocle     ← 描边色（高/低）
aHighlightScannableFillColor            :Monocle     ← 填充色
fHighlightScannableOutlineThickness     :Monocle     ← 描边粗细
fHighlightOutlineColorPulseTime         :Monocle     ← 颜色脉冲周期
```
并且每个都有 `_Generic` / `_Scanned` / `_FullyScanned` / `_Tracked` / `_Bounty` /
`_Social` / `_TargetScanned` / `_TargetScannable` / `_TargetGeneric` / `_TargetFullyScanned` 变体。

**扫描仪的「圆圈」和「范围」也是 GMST**
```
fHandScannerScanRange          (Starfield.esm 的 GMST 000DF135，实测默认值 = 10.0)
fHandScannerScanRangeSkillMult (GMST 0002B3AE)
fScanHighlightDotAngle:Interface        ← ★ 这就是「中央那个圆圈」：只有视线夹角够小才高亮
fScannablePickRadius:Interface
iMaxViewCasterHandscannerPicksHavok:Interface
bShowScannerParticles / fScannerZoom*   :Interface
```

**引擎侧的类**
```
HighlightManager                                  ← 只有 RTTI 名，commonlibsf 没有
CreationRendererPrivate::GatherHighlightsRenderPass
CreationRendererPrivate::HighlightPrepareRenderPass / HighlightRenderPass / HighlightMaskRenderPass
```

### `HighlightManager` 挖到的部分

- 定位：RTTI 名 → TypeDescriptor `RVA 0x5A04748` → COL `0x4FBDC30` → vtable `0x4B2FA50`
  → 唯一的虚函数 = 析构 `RVA 0x653400`；ctor 在 `RVA 0x6532F0`。
- ctor 被 **5 个静态初始化点**调用（每个都 `mov rbx,[全局] ; mov [同一全局], rax`），
  说明它在引擎里是**按用途各建一个实例**（工坊 / 制作 / 扫描仪各一个），不是单例。
- 实例里挂着一套**以 formID 为键的表**（元素 12 字节，`+4` 是 0xFFFFFFFF 作空标记），
  插入函数在 `RVA 0x6535B0`（只有 1 个直接调用者 `0x653F96`）。
- 但 `0x653F60` 这个「把 formID 插进表里」的函数**没有直接调用者**，
  它所在的 vtable（`0x4B2FA00`/`0x4B2FA18`/`0x4B2FA30`）反查出来是
  `stl::local_function_detail::LocalFunctionImpl<lambda_..., BSVisitControl BSVisit::..., NiAVObject&>`
  → **它是 `BSVisit` 遍历场景图时用的 lambda 访问器**。
  也就是说：**高亮是在「画的时候」按 `NiAVObject` 逐个判定的**，不在 ref 层面。

### 为什么 v1 不走这条路

要在 v1 里用上它，得同时做到：找到正确的 `HighlightManager` 实例（5 选 1）、
反出「加/删」的公开入口、并且让 `GatherHighlightsRenderPass` 在**非扫描模式**下也被调用
（它很可能被 Monocle 的状态门控）。这属于深度渲染层逆向，不是一轮能交付的。
所以 v1 用 EFSH（原版自己的机制，见下）。

## 四、结论 3：EFSH 就是原版自己的「发光」机制

- 原版脚本 `glowingLootDropSCRIPT.psc` + 记录 `CargoDropGlowFXS(0001C06E)` 证明：
  官方发光 = `EffectShader.Play`。
- `EffectShader` 的两个颜色字段（用 `efsh_dump.py` 解 44 条原版记录得到）：
  - **`DNAM+4`（具名成员 `Color`）是唯一逐条变化的颜色**，而且变化得有意义：
    火焰 = 红 249,0,6 / `ReconTargetingFXS` = 橙 255,128,64 /
    `GhostFXS` = 淡蓝 152,204,224 / 粉 252,177,252 / 白 255,255,255 …
  - `DNAM+44` 在**全部 44 条记录里恒为浮点 255.0**（字节 `00 00 7F 43`）—— 一个字段在
    44 条不同作者、不同用途的记录里完全相等 ⇒ 它是浮点常量，**不是颜色**。
    （曾经误把它当「Edge Color」按字节补写，等于把 255.0 改成 511.75，是把数据写坏。）
- 因此本 MOD 的 ESM 只写 `DNAM\Color\Red/Green/Blue` 三个具名成员，
  第 4 个字节（xEdit 叫 `Unused`）**绝不寻址** —— 寻址它会让整个 xEdit 脚本静默中断。

## 五、可以直接拿来用的「纯数据」增强（尚未启用，随时可开）

在 `tools/xedit-scripts/build_sas.pas` 里加一段 GMST override 即可，不需要任何代码：

| 设置 | 效果 |
| --- | --- |
| `fHandScannerScanRange` 10 → 100 | 原版扫描仪的探测/高亮半径从 10 米放大到 100 米 |
| `fScanHighlightDotAngle` 调大 | 取消「必须盯着中央圆圈」的限制 |

⚠️ 注意副作用：`fHandScannerScanRange` 同时影响**资源/动植物调查扫描**的距离，
会让调查变得过于容易。所以本 MOD 默认**不改**它 —— 我们自己的高亮是独立半径，
天然不受那个圆圈限制。

## 六、下一步（如果要把视觉层换成原生 outline）

1. 先确认 `HighlightRenderPass` 的调用是否被 Monocle 状态门控
   （在 `GatherHighlightsRenderPass` 的虚函数上下断点，分别在有/无扫描仪时看是否进入）。
2. 若未被门控 → 找到 `HighlightManager` 实例的判定办法（例如按被调用的静态初始化点区分），
   把它「加一条 formID」的入口抄出来，直接调用。
3. 若被门控 → 找到那个门控变量（很可能是某个 `PlayerControls::MonocleHandler` 的状态字节），
   只翻转「要高亮」这一位，不动「锁定武器」那部分。
