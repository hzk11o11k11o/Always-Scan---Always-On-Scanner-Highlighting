# 17 · 「分类分色不生效」的根因与修复（DLL v4.18.0 / 发布版 1.7）

> 建立：2026-09-25。触发：用户实测报告（附截图）——
> **「地上放了武器、太空服（那个箱子）和笔记（数据板），很明显，颜色没有什么别」**
> （= 三样东西的描边颜色看不出区别，全是青/蓝色系）。
>
> 用户同轮的追加要求：**「笔记类物品有书籍、技能杂志、数据板、音频日志，不要只处理书籍」**。

## 一、先分清两层：分类（谁该用什么色）与颜色（这个色画没画出来）

  category (本轮选中): loot=4200, weapon=96, apparel=72, ammoaid=816, note=312, resource=0, ...

⇒ 分类真的在跑（weapon / apparel / ammoaid / note 都有非 0 计数），表也真的被写了
（两行「覆盖 …」）。**问题只能出在「写进去的颜色有没有被引擎拿去画」。**

## 二、真根因：**配色覆盖写得太晚**（管理器只在「创建那一刻」读表）

### 2.1 反汇编 0x17D47B0（引擎的「确保 11 个 HighlightManager」）

```
017D4883  lea r14, [rip + …]         ; r14 = mgr 参数表（RVA 0x591E088，stride 0xA0）
017D48FE  vmovd xmm1, [r14 - 0x60]   ; 表 +0x00（High 颜色）
017D492D  vmovd xmm0, [r14 - 0x40]   ; 表 +0x20（Low 颜色）
017D495C…017D49F9  插值 → 打包成 dword → 参数块 [rsp+0x40]
017D49FF  mov rcx, [rdi]             ; managers[i]
017D4A05  jne 0x17d4aac              ; ★ 已存在 ⇒ 走「已存在分支」
   （不存在）017D4A2A-017D4A5C  分配 + `0x6532F0`（构造函数，参数块）
             017D4A7F-017D4A8C  替换数组槽 + 析构/释放旧对象
017D4AAC  mov eax, [rcx + 0x28]      ; ★ 已存在分支
017D4AAF  cmp eax, [rcx + 0x30]
017D4AB2  je 0x17d4ad3               ; ★★ 两个版本字段**相等 ⇒ 整段跳过**（不重算颜色）
017D4AB4  mov eax, [rcx + 0x40]      ; 管理器的 ID
017D4ACE  call 0x653850              ; 把参数块写到渲染侧（按 ID）
```

构造函数 `0x6532F0`：
```
006533C2  mov dword [rdi+0x40], 0xFFFFFF     ; +0x40 = ID 槽
006533CD  call 0x7CB120                      ; 生成真实 ID
006533E1  call 0x653850                      ; ★ 把参数块（含颜色）交给渲染侧
```
`0x653850` 内部：`and edi,0xffffff` → `[rsi+0x2c8]` 表 → `[ID]` → `shl rcx,5` →
`vmovups ymmword [rcx+rax], ymm0`（把 32 字节参数块写进渲染侧参数表）。

### 2.2 反汇编 0x17D52B0（SetOutlineState）→ 0x17D4CD0（挂引用）

```
017D531F  call 0x17d4cd0             ; Set 内部就是「挂引用」
…
017D4E2C  lea rax, [rbx + rbx*4]; shl rax, 5      ; state × 0xA0
017D4E34  vmovd xmm0, [rax + r15 + 0x5919B08]     ; 读 ref 参数表
017D4E3E…017D4E67  拆成 4 个 float（[rsp+0x70..0x7F]）
017D4E95  vmovss xmm0, [rsp + 0x7c]                ; ★ 只取**第 4 个分量**（alpha）
017D4EC5-017D4ECA  visitor（载荷 = {alpha; 0}）遍历 3D 图 → 写到节点上
```

⇒ **订正 `docs/16` §2.3 的结论**：`ref` 参数表在「挂引用」这一步**只被取用 alpha 分量**；
描边的 RGB（脉冲 High/Low）是**管理器创建时**由 `0x653850` 写进渲染侧参数表的。
（`0x6532F0` 的构造函数里没有写 `+0x28`/`+0x30`，两个字段保持分配时的值 ⇒ 相等 ⇒
「已存在分支」永远不会刷新 —— 引擎侧唯一的换色途径就是**创建**。）

### 2.3 于是 v4.17 的顺序恰好是反的

`RefreshOutlineParamsOnce()`（v4.17）：

```cpp
LogOutlineColors("world-ready");
g_outlineEnsure(nullptr);   // ★ 先建管理器（此时表还是**原生**值 ⇒ 管理器带原生色出生）
ApplyColorOverrides();      // ★ 后写表（管理器已存在 ⇒ 引擎不再读表 ⇒ 写了个寂寞）
```

**这一局的活证据**：`category (本轮选中)` 里 weapon/apparel/note 都有计数、
`outline colors: 覆盖 note/resource …` 也打了，但用户看到的仍是
枪（青 #3EADF2）、太空服箱子（淡蓝白 #B3C1EF）、数据板（蓝 #1F8EE2）——
**全是原生色**。

## 三、修复（`plugin/src/AlwaysScan.cpp`，DLL 4.17.0 → 4.18.0）

| # | 改动 | 说明 |
| --- | --- | --- |
| ① | 拆函数：`WriteColorOverrides(tag)`（只写两张表）/ `ApplyColorOverrides(tag)`（写表 → ensure → 已挂的整批重挂） | 把「写表」与「让引擎用上」分开，才可能在正确时机写表 |
| ② | **install 阶段就写表**（`ResolveNativeOutline()` 末尾，`LogOutlineColors("install")` 之后） | 此刻管理器是 **0/11**（下一行日志会打出这个数）⇒ 之后无论引擎（玩家举扫描仪）还是我们（autoEnsure）创建管理器，用的都是覆盖后的颜色 —— **正解** |
| ③ | `RefreshOutlineParamsOnce()` 改为 `LogOutlineColors("world-ready")` → `ApplyColorOverrides("world-ready")` | 先写表、后 ensure（幂等第二次；兜住「引擎中途改表」） |
| ④ | 资源自检加诊断：每 5 秒最多一条 WARN、最多 6 条，含三个样本的 `LookupByID` 结果与尝试次数 | v4.17 是**静默重试**（这一局日志里既没有「通过」也没有「失败」，只有统计行 `resource=0`），无从定位 |

## 五、待实测验收点（下一次进游戏）

1. 启动日志出现 **`outline colors[install]: 已在管理器创建之前写入 2 个类别的覆盖色（管理器 alive=0/11 …）`**
   —— 其中 `alive=0/11` 证明「写表发生在管理器创建之前」（这是本次修复的关键证据）；
2. 进世界后（world-ready）应再出现一行 `outline colors[world-ready]: 已覆盖 2 个类别 …`，
   且其中 `覆盖 note 的颜色 …（ref 原值 0xFFFFD700）` —— 原值已是我们的黄 ⇒ 幂等 ✓；
3. ★ **肉眼对照（本轮核心）**：
   * 枪 / 手雷 ⇒ 青；太空服 / 头盔 / 背包 / 衣服 ⇒ 淡蓝白；
   * 弹药 / 药 / 食物 ⇒ 绿；**便条 / 数据板 / 杂志 / 音频日志 / 书 ⇒ 黄**（四类都是 BOOK）；
   * 铁矿 / 铝 / 氦-3 这类资源 ⇒ 紫；**Digipick / Credits / 玩具 ⇒ 蓝（不变）**；
   * 箱子 ⇒ 橙、电脑 ⇒ 绿、门 ⇒ 红（不变）；
4. 若「资源仍是蓝」⇒ 看日志里有没有 `resource keyword: …` 那行：
   * `判据自检**通过**` + 仍然蓝 ⇒ 颜色层还有问题（把 world-ready 那几行发出来）；
   * **新的 WARN（`自检样本还没进内存（iron=… pick=… cred=…）`）** ⇒ `LookupByID` 拿不到这三个样本
     （FormID 已离线核对无误），把它发出来 —— 这是 v4.17 静默失败的那条路；
5. ★ **举一次原版扫描仪、再放下** ⇒ 分色**保持**（这条走的是「管理器被引擎销毁 → 重建」的路径）：
   此时日志应出现 `[post-clear] outline colors: 覆盖 note 的颜色 -> …` 两行；
   若放下后颜色退回单一蓝色 ⇒ 这条兜底没接上（把 post-clear 相关日志发出来）；
6. 不回归：F8 / 扫描仪自愈（用完扫描仪 1 秒内重挂）/ 展示柜拿空熄灭 / 换场景不崩 / 活人一个都不亮。

## 六、可复用经验

1. **「写进引擎的表」不等于「引擎会用它」** —— 一定要找到「表被消费」的那条路，并确认**消费时机**
   （本次：颜色只在管理器**创建**时被消费，已存在的管理器不刷新）。
   验证手段就是「反汇编消费点 + 看有没有『版本/哈希相等就跳过』这类短路」。
2. **初始化顺序本身就是功能的一部分**：同一个写表动作，放在「管理器创建前」有效、放在「之后」无效。
   凡是「写配置 → 消费方初始化」的链路，都要问一句「谁先谁后」，并让日志把顺序写下来（`alive=0/11`）。
3. **静默重试 = 无法定位的失败**：任何「等条件就绪再试」的判据，都要有一条**限流日志**
   （本次：每 5 秒最多 1 条、最多 6 条），否则用户日志里只剩一个 `resource=0`，既不是通过也不是失败。
4. **反汇编「读表 → 拆分量 → 存栈」时，要往后追到「哪几个分量真的被用了」**：
   本次 ref 表读了 4 个 float，实际只用第 4 个（alpha）—— 只看「读了这张表」会得出错误结论
   （v4.17 就误记成「ref 表是可见色」）。
