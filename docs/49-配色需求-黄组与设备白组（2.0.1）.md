## 零、一句话结论

按 `颜色分类.md` 的更新版，**新增第 7 个物品子类「黄 = 开锁器 / 信用币」**、
并把**设备（电脑 / 终端 / 按钮）并入「白」组与门同色**；两者都**只在自建通道模式
（默认）下表达**，旧路径（`ChannelMode=0`）没有空闲槽位 ⇒ 明确退回「与杂项同蓝 /
与门共槽」而**不污染引擎**的 NPC / 星球目标槽位。

## 二、离线取证：开锁器 / 信用币到底有几条记录、能不能用关键词判

脚本：`tools/re/esm_pickcredit_probe.py`（新增，单遍扫 Starfield.esm）。

```
MISC 记录总数 = 1319                      ← 与 docs/16 的 1319 条口径一致
MISC 里 EDID 命中 digipick/credit 的 = 3 条

=== MISC 0x0000000A  Digipick            KWDA n=1: NotJunkJetAmmo
=== MISC 0x0000000F  Credits             KWDA n=1: NotJunkJetAmmo
=== MISC 0x000A7312  FFNeonZ03_Credits  KWDA n=1: NotJunkJetAmmo
```

**结论**：
1. 「开锁器 / 信用币」在数据里**只有 3 条 MISC**（`Digipick` / `Credits` /
   `FFNeonZ03_Credits`，最后一条是霓虹城任务里的一笔钱）；
2. 三者的关键词**只有共用的 `NotJunkJetAmmo`**（很多杂物都有）⇒
   **没有可用的专用关键词**，判据只能按 **FormID** —— 与「资源」按
   `ResourceType*` 关键词判不同；
3. 其它签名里 EDID 命中 credit 的有 233 条（GLOB / LVLI / CELL / INFO …），
   与「玩家能捡起来的信用币物品」无关（LVLI 抽出来的仍是 `Credits` 0xF）。

实现（`plugin/src/AlwaysScan.cpp`）：

```cpp
constexpr std::uint32_t kFormIDDigipick    = 0x0000000A; // 开锁器 Digipick
constexpr std::uint32_t kFormIDCredits     = 0x0000000F; // 信用币 Credits
constexpr std::uint32_t kFormIDCreditsNeon = 0x000A7312; // 信用币 FFNeonZ03_Credits
```

`ClassifyBase()` 的 MISC 分支里放在「资源判据」**之前**（一次整数比较，最省；
三条本来就不带 `ResourceType*` ⇒ 先后无歧义）。

★ 这三个常量同时是**资源自检的负样本**（它们必须不是资源）—— 常量共用，两处语义都写上注释。

## 三、两个模式的行为矩阵（本轮最重要的设计取舍）

| 类别 | 通道模式（默认 `ChannelMode=1`） | 旧路径（`ChannelMode=0` / 通道自动回退） |
| --- | --- | --- |
| 开锁器 / 信用币 | 独立通道 **#FFE100** | `state 2` + 不覆盖 = **与杂项同蓝** |
| 设备 / 电脑 / 按钮 | 独立通道 **#FFFFFF** | `state 6`（与门共槽）⇒ 读到的就是门写的**白** |
| state 4 | **完全不占用**（v4.24 起本就不覆盖，现在连挂都不挂） | 同左 |

**为什么旧路径的黄组要「退回杂项蓝」而不是硬塞一个黄色**：
引擎只有 11 个 state，其中 0/1（通用引用，含活人 NPC）、4/5（已扫描的星球目标）、
7/8（未扫描的星球目标）由引擎自己写，**一个字节都不能动**（v4.24 / v4.30 的两次
实测血案）；2/3/6/9/10 已经被杂项 / 笔记+资源 / 门+设备 / 容器+尸体 / 武器+服饰占满。
⇒ 想在旧路径给黄组一个独立颜色，**只能**去抢引擎的槽位 = 让行人或星球目标变色。
本 MOD 的选择是：**宁可旧路径少一个颜色，也不污染引擎**（与 v4.24 的结论一脉相承）。

**为什么设备可以放心并入 6**：`state 6` 是 v4.24 整函数反汇编后确认的
「**引擎唯一不写**的槽位」，门从 v4.31 起就住在这里；设备搬进来 = 门与设备**共槽同色**，
正好就是需求要的「白 = 门、电脑、按钮等所有可互动物品」。副产品是 state 4 被完全释放。

**选色理由（0xFFE100）**：容器橙是 `#FF9500`（hue ≈ 35°），黄组取 `#FFE100`

比 `#FFD700`（金，51°）更偏纯黄、更容易与橙分开。

## 五、验收判据（下一次进游戏）

1. **启动日志**：
   - `config: categoryEnabled: loot=1, …, corpse=1, pickcredit=1`
   - `config: 配色分组(2026-09-28) -> …「门 / 电脑 / 按钮」= 6（白 #FFFFFF）、
     「开锁器 / 信用币」= 2（黄 #FFE100，仅通道模式）…`
   - `channel: ✅ 已创建 14 个自建颜色通道 … | colors: … device=#FFFFFF … pickcredit=#FFE100`
   - 统计行 `channel (自建颜色通道): 状态=已就绪 通道=14/14 已挂=N`
2. **★ 肉眼（核心）**：
   - 开锁器 / 信用币 = **黄**（地面上的开锁器、尸体 / 容器里的信用币都算）；
   - 电脑 / 终端 / 按钮 / 开关 = **白**（与门一致）；
   - 门 = 白、容器 / 尸体 = 橙、装备 = 红、笔记 / 资源 = 紫、弹药 / 救援 = 绿、
     杂项（玩具 / 杯子…）= 蓝、星球资源 = 原版青 ↔ 原版绿 —— **全部不回归**。
3. **原版零污染**：举着扫描仪 ⇒ NPC 青 / 亮青、星球目标青 ↔ 绿与 2.0 一致。
4. **回退路径**（可选）：`ChannelMode=0` ⇒ 黄组变回杂项蓝、设备仍白
   （与门共槽），控制台 / 日志无撞色 WARN。

## 六、可复用经验

1. **「没有专用关键词」本身要证**：先全量扫一遍 EDID（`esm_pickcredit_probe.py`），
   确认候选记录条数与关键词表，**再决定判据形态**（关键词 vs FormID）——
   否则很容易写出一个「看起来通用、实际永远不命中」的判据（v4.17 资源判据就是这么翻车的）。
2. **新类别先问「旧路径怎么办」**：自建通道让「加颜色」变便宜，但**回退路径的槽位
   预算没有变**（仍然只有 2/3/6/9/10）。新类别的默认 state 必须显式给出**安全兜底**，
   并在注释里写清「为什么不是想要的那个颜色」。
3. **共槽 = 共色：有时候是需求，不是将就**：设备并入 6（门）不是妥协，而是需求
   （「白 = 门 / 电脑 / 按钮」）与安全（6 = 引擎唯一不写的槽位）的交点
   —— 顺手把 state 4 彻底释放，等于把 v4.24 的收益再往前推一步。
