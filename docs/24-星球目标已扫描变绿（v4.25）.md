# 24 · 放下扫描仪之后也认「已扫描」：星球目标扫过的变绿（DLL v4.26.0 / 发布版 1.7.7）

> ★★★ **2026-09-26 追加：v4.25 的判据实测失败，v4.26 改成「两条证据来源」** ——
> 失败现场、离线核对与改动见 **§六**（v4.25 的部分保留在下面作为推导记录）。

> 建立：2026-09-26。触发：用户实测反馈（原文）——
>
> ```
> 矿石、气体、液体、植物、动物现在扫描后，在扫描仪里的颜色是原版颜色了，
> 但是收起扫描以后，在mod的高亮颜色里还是扫描前的原版蓝色，

> 这一轮修的是「放下扫描仪之后」那一半** —— MOD 自己重挂高亮时只会用
> `StateFlora`（7 = 原版青色脉冲）一个状态，所以「扫过的」和「没扫过的」看起来
> 一模一样。修法 = **直接调引擎自己的判据函数**（RVA `0x1597A50`）问出
> 「这个资源已经在勘测数据里了吗」，扫过的挂 **state 5（原生绿 `#27C684`）**、

## 一、证据链（本机 1.16.244.0 重新反汇编复核）

### 1.1 v4.24 已经有了「已扫描 ⇒ 4/5」这条链，但只在引擎自己上色时生效

`0x159ED90`（原版扫描仪的逐引用求值函数）里那段（`0x159F4C2`~`0x159F569`）
本轮**逐条重新反汇编核对**（`python tools/re/disasm.py <Starfield.exe> 0x159F4B0 0x40 0xC0`）：

```
0159F4C2  mov rdi,[rsp+0x20]          ; rdi = 被求值的引用
0159F4C7  mov rax,[rdi+0x98]          ; rax = 引用的 base
0159F4CE  test rax,rax / je 0x159F57F
0159F4D7  cmp byte [rax+0x2e], 0x2e   ; ★ formType == kFLOR (0x2E)
0159F4E1  mov rax,[rax+0x260]         ; ★ FLOR+0x260 = TESProduceForm::produceItem
0159F4E8  test rax,rax / je
0159F4F1  cmp byte [rax+0x2e], 0x3f   ; ★ formType == kLVLI (0x3F)
0159F4FB  cmp byte [rax+0x13a], 0     ; ★ 条目数（byte @+0x13A）> 0
0159F504  mov rax,[rax+0x120]         ; ★ 首个条目指针（@+0x120）
0159F50B  mov rcx,[rax]               ; 条目的 form
0159F513  cmp byte [rcx+0x2e], 0x28   ; ★ formType == kMISC (0x28)
0159F519  mov rbx,[rcx+0x238]         ; ★ MISC+0x238 = 资源数组对象（指针）
0159F520  test rbx,rbx / je
0159F525  mov eax,[rbx]               ; size（BSTArray size@+0）
0159F527  test eax,eax / je
0159F52B  mov rbx,[rbx+8]             ; data（★ data@+8，与 docs/22 的订正一致）
0159F52F  lea rcx,[rax+rax*2]         ; 3 * size
0159F533  lea rsi,[rbx+rcx*8]         ; 结束地址 = data + size*24
0159F540  mov rcx,[rbx]               ; 元素 [0]（首个字段 = TESForm*）
0159F548  cmp byte [rcx+0x2e], 0x9f   ; ★ formType == kIRES (0x9F) = BGSResource
0159F54E  call 0x1597A50              ; ★★「这个资源已经扫描过（进了勘测数据）？」
0159F553  test al,al / je <next>
0159F557  xor eax,eax
0159F559  cmp byte [rbp+0xe8], al     ; 「在扫描范围内？」
0159F55F  setne al
0159F562  add eax,4                   ; ⇒ ★ state 4（远）/ 5（近）
0159F569  add rbx,0x18                ; 下一个元素（stride = 0x18 = 24 字节）
```

⇒ v4.24 的结论仍然成立：**引擎把「已扫描」的星球目标写进 state 4/5，原生色 = 绿**。
但那条链只在**引擎自己上色**时跑 —— 玩家举起扫描仪的时候。

### 1.2 真正缺的那一半：MOD 放下扫描仪后自己重挂时没有这个信息

v4.23 起「植物 / 矿脉 / 气泉 / 液池」（FLOR）类别在**放下扫描仪**后由 MOD 重挂，
状态固定是 `StateFlora`（默认 7 = 原版 `TargetScannable` = 青色脉冲轮廓）。
⇒ 用户看到的现象完全对得上：

| 时刻 | 谁在画 | 扫过的目标 | 没扫过的目标 |
| --- | --- | --- | --- |
| 举着扫描仪 | **引擎**（MOD 让位，v4.23） | **绿**（4/5，v4.24 修好） | 青（7/8） |
| 放下扫描仪 | **MOD**（始终 state 7） | ❌ 青（**本轮修的就是它**） | 青 ✅ |

### 1.3 修法：照抄同一条链 + 调同一个函数（而不是自己猜「扫描状态存在哪」）

`0x1597A50` 的实现（本轮也反汇编核对了函数首）是一个纯粹的**查询**：

```
01597A50  48 89 5C 24 10   mov [rsp+0x10],rbx      ; ← 本 MOD 硬核对的签名起点
01597A55  48 89 6C 24 18   mov [rsp+0x18],rbp
01597A5A  48 89 74 24 20   mov [rsp+0x20],rsi
01597A5F  57               push rdi
01597A60  41 54            push r12
01597A62  41 55            push r13
01597A64  41 56            push r14
01597A66  41 57            push r15
01597A68  48 83 EC 40      sub rsp,0x40
01597A6C  48 8B F1         mov rsi,rcx             ; rcx = BGSResource*
01597A6F  48 85 C9         test rcx,rcx / je …
01597A78  48 8B 2D …       mov rbp,[rip+…]         ; 全局单例
01597A81  48 8B 8D C8 00 00 00   mov rcx,[rbp+0xc8]
01597AA7  8B 5A 28         mov ebx,[rdx+0x28]      ; FormID
01597AD2  48 8B 0D …       mov rcx,[rip+…]
01597AD9  E8 82 02 22 FF   call 0x7B7D60           ; map find（勘测数据）
01597ADE  84 C0            test al,al
01597AE0  0F 95 C1         setne cl
01597AE5  0F 85 CE 02 00 00 jne → 返回 true
```

⇒ 它就是一个「**这个 BGSResource 在不在玩家的勘测/已知数据里**」的查询
（全局单例 + `map.find(formID)`）。参数只有一个：`BGSResource*`（rcx），返回值在 `al`。

**所以 MOD 侧的做法是「同一条链 + 同一个函数」，不引入任何我们自己的猜测**：

```
FLOR base +0x260 (produceItem, LVLI)
  → LVLI +0x120（首个条目）→ 条目 [0]（MISC）
  → MISC +0x238（资源数组 {size@+0, data@+8}，元素 stride 0x18）
  → 元素 [0] 若 formType == kIRES(0x9F)
      ⇒ 调 0x1597A50(irES)   ← 「已扫描？」
  任一元素命中 ⇒ 已扫描
```

## 四、验收判据（下一次进游戏）

1. 启动日志（可 grep）：
   ```
   config: floraScannedByResource=1 stateFloraScanned=5 -> 「植物 / 矿脉 / 气泉 / 液池」放下扫描仪后：
           **已扫描过的**用 state 5（原版「已扫描」绿 #27C684）、没扫描过的用 state 7（原版青色脉冲）；
           判据 = 引擎自己的 0x1597A50 —— 日志里搜 `flora scan:` 可核对
   flora scanned: 引擎判据就绪（RVA 0x1597A50，签名核对通过）-> …
   ```
   ＋ 覆盖行仍然是 **7 条**（0/1/2/3/6/9/10）——**不该出现 `state=4` / `state=5`**
   （否则就是有 INI 又给这两个槽位写了颜色：`ColorAmmoAid` / `ColorDevice`）。
2. ★★ 肉眼（核心）：
   * 先**不举扫描仪**对着一个**扫过的**矿脉 / 植物 ⇒ **绿色**；没扫过的 ⇒ **青色脉冲**；
   * 举着扫描仪扫完一处 ⇒ 放下 ⇒ **约 0.2 秒内由青转绿**；
   * 走远再回来 / 换场景回来 ⇒ 扫过的仍然是绿色（判据是存档里的勘测数据，不是内存猜测）。
3. ★ 诊断：
   * `flora scan: base=… produceItem=…(LVLI) misc=…(MISC) irES=…(IRES) -> 已扫描=1/0 ⇒ 用状态 …`
     —— 每个 base 一行（≤8 条），`已扫描=1` 出现 = 引擎确认该资源扫过了；
   * 统计行 `planet targets (窗口内): 未扫描=… 已扫描=… | 判据: 查询=… 命中=… 链失败=… 缓存=… ready=1`
     —— `已扫描 > 0` 且 `链失败` 不涨 = 分流在正常工作。
4. 回退开关（都**不用换 DLL**）：
   * `FloraScannedByResource=0` ⇒ 退回 v4.24（整个类别只用一个状态，扫没扫过看起来一样）；
   * `StateFloraScanned=7` ⇒ 等效关闭（两种状态同值）；
   * `FloraScanProbeMax=0` ⇒ 关掉 `flora scan:` 探针。
5. 不回归：F8 / 扫描仪自愈（放下扫描仪后整批重挂）/ 展示柜拿空熄灭 / 换场景不崩 /
   活人一个都不亮 / 笔记仍黄 / 资源仍紫 / 杂项仍蓝 / 容器·尸体仍橙 / 门仍白 /
   弹药·救援与设备仍是原版绿。

## 五、可复用经验（写给下一轮）

1. **「归还槽位」只解决「谁写状态」，不解决「谁在什么条件下写」** ——
   v4.24 把 4/5 还给了引擎，但放下扫描仪后是 MOD 在写，而 MOD 并不知道
   「已扫描」这件事 ⇒ 同一个症状只是换了一个时刻出现。
   下一轮遇到「某个原版特性 MOD 复现不出来」时，先问：**这个信息 MOD 有没有？**
2. **能调引擎的判据函数就别自己猜** —— `0x1597A50` 只吃一个 `BGSResource*`、
   返回 `al`，是纯查询；比「自己去找勘测数据存在哪个全局里」稳得多。
   代价只是**几层指针链 + 每一步 formType 断言**（这一轮把整条链都反汇编出来了）。
3. **反汇编里的每个 formType 断言都是免费的形状校验** ——
   `0x2E(FLOR) → 0x3F(LVLI) → 0x28(MISC) → 0x9F(IRES)` 直接抄进运行期校验，
   偏移猜错时会在第一层就失败（失败方向永远是「保持原样」）。
4. **默认 `ReassertMs=0` 时 `reassertMs` 是 `UINT64_MAX`** ——
   任何「按时间判断要不要重挂」的逻辑都永远不会触发；
   状态类变化必须**单独判**（本轮就是漏了这条 ⇒ 「青 → 绿」永远不会被应用）。
5. **让位 / 保护类逻辑不要绑在「状态数字」上** ——
   一个类别一旦可能用两个槽位，按状态判断就会漏掉一半（本轮把让位改成按类别）。

## 六、★ v4.26：v4.25 判据实测失败 → 两条证据来源（取或）

### 6.1 失败现场（用户那一局日志，2026-09-26 15:00）

```
[15:00:54.175] flora scan: base=0x75CAD produceItem=0x0(LVLI) misc=0x0(MISC) irES=0x0(IRES) -> 已扫描=0
[15:01:49.511] planet targets (窗口内): 未扫描=520 已扫描=0 | 判据: 查询=166 命中=0 链失败=166 缓存=10 ready=1
[15:01:00.457] [W] flora scanned: base=0x18547F 判据链形状校验没过（produce=0x0 misc=0x0）
```

⇒ 签名核对通过（`引擎判据就绪` 打出来了）、引擎函数没问题，**但链的第一步就读不到东西**
（`produce=0x0`），而且连 **Starfield.esm 的原版矿脉**（`0x75CAD`）也一样。

### 6.2 离线核对（新工具 `out/scan_flor_pfig.py`，直接扫 Starfield.esm）

| base FormID | 记录 | PFIG（产出物品） |
| --- | --- | --- |
| `0x00075CAD` | FLOR `MineralDepositCommonWaterLiquid01` | **LVLI** `0x00163A11` |
| `0x0025232B` | FLOR `MineralDepositCommonLead01` | **LVLI** `0x00163A0E` |
| `0x00383287` | FLOR `ResourceRockLiquid01` | 无（这类不走「已扫描」） |

⇒ ESM 里这些矿脉的产出物品**确实是 LVLI**（与引擎 `0x159ED90` 的假设一致），
所以失败只可能是**内存里那个字段的位置/类型与我们的假设不同**。

### 6.3 反汇编里的关键旁证：引擎自己对这个字段有两种用法

`tools/re/findbytes.py "80 7? 2E 2E"`（= `cmp byte ptr [reg+0x2E], 0x2E`，FLOR 判定）
把所有「FLOR 分支」都列了出来，其中**两个相邻函数**（`0x1479549` / `0x1479AC9`）：

```
01479549  cmp byte ptr [rcx + 0x2e], 0x2e     ; FLOR
0147954F  mov rdx, qword ptr [rcx + 0x260]    ; ← 同一个 +0x260
0147955B  cmp byte ptr [rdx + 0x2e], 0x28     ; ★ 这里要求的是 **MISC(0x28)**
01479579  mov rdx, qword ptr [rdx + 0x238]    ; MISC+0x238
01479584  call 0x147b370                      ; 该函数里逐元素（stride 0x18）筛 `formType==0x9F`(IRES)
```

而扫描求值函数（`0x159ED90`）对同一个 `+0x260` 要求的是 **LVLI(0x3F)**。
⇒ **同一字段运行期可以装 MISC 也可以装 LVLI**，而且内存偏移必须实测确认
（commonlibsf 与引擎在这几个类上差 8 字节，本项目已多次撞上）。

### 6.4 v4.26 的两条证据来源（取或）

| # | 来源 | 做法 | 强度 |
| --- | --- | --- | --- |
| ① | **引擎亲手画的颜色** | 举着扫描仪时（MOD 让位中）读一眼**引擎给这个引用写的 outline 状态**：`4/5` = 已扫描（绿）、`7/8` = 未扫描（青）—— 读的是引擎的「引用→状态」表（`g_outlineLookupOrAdd`，纯查询）。「已扫描」**单向**（勘测数据不会退回）⇒ 学到就本会话有效，与链判据取或 | ★★★ 零逆向、就是原版那一刻画出来的颜色 |
| ② | **资源链判据（自适应偏移）** | 先试引擎/文档记录的 `+0x260` / `+0x258`；不成就在 `0x180~0x380` 里逐 8 字节找「能把整条链走通」的指针：`MISC` 或 `LVLI`（取其首条目，必须是 MISC）→ `MISC+0x238` 资源数组（`{size@0,data@8}`，元素 stride `0x18`，**必须真有 IRES(0x9F)**）→ 调 `0x1597A50`。标定结果写会话级变量并打日志 | ★★ 形状校验极强（垃圾指针不可能同时过）；覆盖「还没扫过的地方」 |

失败时的取证（前 3 个 base）：
`flora probe (链没走通): base=… vtblRva=… | 窗口 0x180~0x380 里的 form 指针: +0x1C0:28/0x1234 …`
—— 外加 `0x298` / `0x2A0` 两个 dword 的 produceChance 交叉校验（水矿的 `PFPC` 是
`100/100/100/100` ⇒ 记录里某处必然出现 `64 64 64 64`，可用来确认「读的就是那条记录」）。

### 6.7 验收判据（v4.26）

1. 启动日志：`flora scanned: 引擎判据就绪（RVA 0x1597A50，签名核对通过）`；
2. ★★ 肉眼：**举着扫描仪**对着一个扫过的矿脉/植物（它显示绿色）⇒ **放下** ⇒
   该目标应在约 0.2 秒内变绿；同一位置没扫过的仍是青色；
3. ★ 日志（任一出现即说明判定在干活）：
   * `flora scan: 引擎把 base=0x… 画成了绿色（outline state 4/5）-> 记下「已扫描」`
     （= 证据①生效，零逆向那条）；
   * `flora scan: 「产出物品」字段标定 = base+0x…` / `资源数组字段标定 = MISC+0x…`
     （= 证据②标定成功；这两行还顺带告诉下一轮「真实偏移到底是多少」）；
   * 统计行 `planet targets … | 引擎学到: 绿=N base …`，`已扫描 > 0`、`链失败` 不涨；
4. 若仍不变绿：把 `flora probe (链没走通): …` 那几行 + 统计行发出来 ——
   指针窗口会直接暴露「产出物品字段到底在哪个偏移 / 是不是 MISC」，
   下一轮就能一次改对（不再猜）。
5. 回退开关不变：`FloraScannedByResource=0` / `StateFloraScanned=7` / `FloraScanProbeMax=0`。
