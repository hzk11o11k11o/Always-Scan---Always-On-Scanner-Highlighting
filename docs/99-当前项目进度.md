### v3.1 追加验证（2026-09-17）—— 与「玩家举扫描仪」的冲突面：全镜像实证

**问题**（用户）：开着 MOD、同时又用扫描仪扫描，会不会冲突？

**做法**：用新工具 `tools/re/findrefs.py`（按**数据地址**查全部 RIP 相对引用：
REX+opcode 前缀表 + ModRM `mod=00/rm=101` 筛 + capstone 复核）把引擎侧
「谁写 outline 状态、谁清空整张表」全查了一遍。完整推导见 `docs/03` 第十二节。

**★ 关键事实（全部实证，不是推测）**：

| 事实 | 证据 |
| --- | --- |
| 引擎写 outline 状态只有**一条路**：`0x17D52B0`（Set），且它的直接调用者**只有 `0x159ED90`** | `func.py callers 0x17D52B0` |
| `0x159ED90` 是「取单个引用 + 位置 → 算状态 → 写表」的**逐引用评估函数**（距离平方 + 点积 + 视角判定），不遍历全表、不写 12 兜底 | 反汇编 `0x159ED90`（0x40 起、0x470 的 Set 点） |
| 「销毁 11 个管理器 + 清空整张状态表」的 `0x17D4B30` **只有一个调用者 `0x1598910`**（Monocle HUD 对象的析构路径） | `func.py callers 0x17D4B30` |
| Monocle HUD 对象全局指针（RVA `0x61EEA28`）**全镜像 21 处引用 = 4 写 + 17 读**；4 写 = 构造 1 处（`0x1597E80`）+ 析构/摘除 3 处（`0x1598910` / `0x15F86A0` / `0x15F8490`） | `findrefs.py`（字节级 disp 校验 + capstone 复核） |
| 清空写入所在函数都只由 Monocle 生命周期工厂 `0x15FD710` 区段调用；该工厂是**懒创建单例**（`if (global) teardown; alloc(0x140); ctor; global=obj`）⇒**不是收扫描仪就会清** | 反汇编 `0x15FD710` |

**结论**：

1. **不举扫描仪时零冲突** —— 引擎那条写入路根本不在跑；
2. **举着扫描仪时**：原版只对它自己范围内（约 10 米 + 中央圆圈判定）的物品按原版规则写状态，
   MOD 挂的 50 米范围内其余物品**不受影响**；重叠的那一小块会被原版按「已扫描」覆盖颜色
   —— 这正是原版自己的行为，且 **F8 / 走远时 MOD 仍能摘干净**（`UnoutlineRef` 先读状态表里
   记的真实状态再摘，不是硬编码 `OutlineState`）；
3. **唯一的低概率风险**：若发生「整表清空」（只有 UI/相机大重建、回主菜单、读另一个存档这类
   时点才会走），MOD 的 `outlined` 表会变成悬空记录 ⇒ 高亮集体消失一阵，默认
   `ReassertMs=0` 不会自愈。**正常开关扫描仪不触发**（与用户 v2.3 起多次实测一致）。

**新增工具**：`tools/re/findrefs.py`（数据地址 → 全部 RIP 引用，附 capstone 形状校验）。

**待办里加了防御项**（未实现，等实测定夺）：① 管理器数量从满编跌落 ⇒ `MarkAllForRemoval`
并分批重挂（零额外引擎调用，治第 3 条）；② `OutlineRef` 幂等化（写前先读状态表）；
③ 可选：用 `MonocleMenu` 菜单事件让位原版。

### v3.0（2026-09-16 深夜）—— ★★ 引导线两个真根因：`SetPosition` 是延迟函数 + 一帧重摆整条链

`kEnable=3 / kDisable=4 / kSetPosition=6 / kSetScale=11 / kMoveToNearestNavmeshLoc=26 / kWaitFor3D=24`
—— **这些 Papyrus 调用在 Starfield 里全是「延迟函数」**，被塞进 `GameVM` 的
renderSafe/postRender 队列、等 3D 就绪后由引擎执行。⇒ **调用之后立刻读坐标拿到的是旧值**。
v2.8 的 `SetPosition(贴地) → MoveToNearestNavmeshLocation() → SetPosition(GetPositionZ()+lift)`
读到的正是吸附**之前**的 Z（玩家头顶 2 米）⇒ 球飘在「头顶 2.25 米」，
而且 8 颗全在飘 —— 这就是「只看得到一个」（其他在头顶/墙里）与截图那颗的来源。

**★ 根因二**：v2.8 是「每 0.5 秒 + 玩家移动 1.5 米 ⇒ 一帧内 8 颗 x 3 次引擎调用」，
其中 8 次是 navmesh 查询（毫秒级主线程工作）⇒ 周期性硬卡顿；
而 1.5 米的移动阈值又让整条链**一次跳 1.5 米** ⇒ 「不连续」。

**v3.0 做法（全部在 `scripts/SAS_Bridge.psc`，DLL / ESM 未动）**：

| 项 | 改动 |
| --- | --- |
| 珠子 | `CfgGuideBeadCount()` = **20**，间距 **0.55 米**，缩放 **4.0**（0.4 米球）⇒ 11 米连续光带（v2.8 是 8 颗 x 3 米 = 一堆散点） |
| ★ 世界锚定 | 珠子铺好后**不再随玩家移动**：玩家每前进一个间距，只把「环头那颗」回收去队尾（`GuideHead` 环形推进）⇒ 走动时是光带从脚边流过，不是整条线跟着跳 |
| ★ 限流 | `CfgGuideBudget()` = **每 tick 最多动 3 颗**（重铺/回收/修剪共用预算）⇒ 彻底消灭「一帧铺满整条链」 |
| 重铺 | 方向变化 > 8°、横漂 > 2 米、倒退 > 2 米 ⇒ 重铺，且**分批**（3 颗/次）+ 两次之间至少隔 1.5 秒（防抖） |
| 链长 | `间距_eff = min(0.55 米, (目标距离 - 余量)/20)` ⇒ 目标近时自动压密，**永不越过目标**（v2.8 的 `reach` 截断会让近目标只剩 1~2 颗） |
| 停用 | 越过目标的珠子**不调 `Disable()`**，直接 `SetPosition` 到地下 4000 单位（少一组延迟函数、不来回切 3D） |
| ★ 贴地 | 只调 `SetPosition(离地 0.2 米)` → `MoveToNearestNavmeshLocation()`，**不读回、不二次抬升**（见根因一） |
| 节流 | 删掉「移动 1.5 米才重算」的判定（那正是「一格一格跳」的根源）；现在每 tick（0.25 秒）都过一遍，但判断全是纯数学 |

| ★ 珠子不被高亮 | `AlwaysScan.cpp` 的 `IsHighlightableBase()` 里按 FormID 排除「Glow*」家族（`0x98105/0x98106/0x9811C/0x1760F`）—— 否则 20 颗珠子会白占 `MaxTargets` 配额、还会被描上一圈（观感怪 + 开关光带时一批挂/摘描边的 churn） |

### v2.3（2026-09-16 夜）—— ★ 修掉「摘不掉高亮」的真正根因 + 治「扫描本身的假卡顿」

**实测反馈（v2.2）**：① F8 有作用，但**新区域不再高亮、已高亮的不会熄灭**；
② 卡顿仍在，**已高亮区域也卡**，像在重复高亮已高亮的物品；
③ 走很远物体**还亮着**；④ 任务导航线还是没有。

**①③ 的根因（详见 `docs/03` 第十一节）**：v2.2 走的是引擎自己的 `0x653F60`，
但**它的第二个参数是「引用 3D 图里的一个节点」，不是 `TESObjectREFR`**。

日志证据：`outline remove: rmOk=0 unhMiss=3694 removeMiss=3694 unhighlightReady=1`
—— 连引擎自己的摘除函数都一次没命中。

把 `0x17D4CD0`（`Set` 内部真正干活的函数）整段读完后链条就通了：
它先用 `call [ref->vtable + 0x560]` 取 **3D 根节点**（commonlibsf 里第 `0xAC` 号虚函数
注释正是 `Get3D(NiPointer<NiAVObject>&)`，`0xAC*8 = 0x560`），再调
**`0x24181E0(visitor, 节点)`** —— 那是个**递归遍历 3D 图**的访问器：
有子节点就递归、是叶子才回调 `visitor->vtable[0x10](visitor, node)`。
摘除 visitor 的 vtable 是 **`0x4B2F9F0`**（`+0x08` / `+0x10` 两个槽都 = `0x653F60`），
数据就是 `&g_outlineManagers[state]`。而 `0x653F60` 内部是
`node->vtable[0x50]()` → `[那个对象+0x1F0]` 当 id → `Remove(map,&id)` → 删到才 `Deactivate(id)`。

⇒ 我们塞进去的是引用，取出来的「id」根本不是管理器表里的键，
`Remove` 永远 false、`Deactivate` 永远不执行 ⇒ **描边永远摘不掉**。
F8 关不掉、走远了还亮、管理器哈希表只增不减（渲染器每帧过一遍 → 越玩越卡）
三条症状同一个根因。

**② 的第二个根因**：`timing: scan avg=47ms max=146ms ops=0`，
甚至第 1 轮「什么都没干」（`cand=0 sel=0`）就花了 **31ms**。
那一段唯一的重活是 `ValidateCellRefs` 里的 6~7 次 `VirtualQuery`
（要走内核对 VAD 树，这种几 GB 的进程里单次毫秒级）。已加
**「已验证可读区间」缓存**（8 槽 + 3 秒 TTL，cell 变化/读档作废）治它。

| 项 | 改动（`plugin/src/AlwaysScan.cpp`） |
| --- | --- |
| 摘除 | **改成引擎自己的姿势**：`Get3D(vtable[0xAC])` → `visitor{vtbl=0x4B2F9F0, &managers[state]}` → `0x24181E0(visitor, 3D根)`（三个符号都带校验：签名 / vtable 两槽必须都指向 `0x653F60` / 取出的函数地址必须落在主模块内） |

### v2（2026-09-16）—— ★ 视觉层换成引擎原生 outline（详见 docs/03）

**起因**：v1.1 实测「有高亮效果，但和原版相差甚远」。原因是它沿用了上一代 mod
（`高亮物品`）的做法 —— 给对象 `EffectShader.Play`，只在对象身上叠一层**发光**；
而原版扫描仪画的是**轮廓描边**。用户明确表示这不是想要的。

**结论**：引擎里有一整套「引用 → outline 状态 → HighlightManager → 渲染器」的原生高亮
管线（任务追踪 / 工坊 / 制作台用的都是它）。本 MOD 不再自己造视觉，改成**只决定
"哪些引用、用什么状态"**，描边由引擎自己画。

**逆向结果**（全部记录在 `docs/03`，含逐条推导）：

| 项 | RVA / 地址 |
| --- | --- |
| `LookupOrAdd`：查/插入「引用→状态」槽（`rdx`=引用指针的地址），返回状态字段地址 | `0x17D5BE0` |
| `SetOutlineState(slot=rcx, state=edx)` | `0x17D52B0` |
| `ClearOutlineState(slot=rdx)` | `0x17D4F10` |
| 引擎自己的「建立/刷新 12 个管理器」函数（幂等，`rcx` 未用） | `0x17D47B0` |
| 12 个 `HighlightManager*` 的数组 | `.data 0x5F39CF0` |
| 「引用→状态」红黑树树头 | `.data 0x5F39CE0` |
| 管理器内嵌哈希表插入（键＝24 位 FormID） | `0x6535B0` |
| 把某个 id 的高亮参数写进渲染器 StorageTable | `0x653850` |

**关键正确顺序**（与引擎自己完全一致）：

```cpp
auto* p = LookupOrAdd(nullptr, &ref);   // SetOutlineState 找不到引用会直接返回
*p = state;                             // 0..11；12 = 无
SetOutlineState(&ref, state);
```

**唯一崩溃风险已封堵**：`SetOutlineState` 内部会直接解引用
`g_outlineManagers[state]`，为 0 就是 0xC0000005。而引擎**只在进入扫描模式时**才建这些
管理器 —— 正好是本 MOD 要绕开的场景。所以：

1. 挂高亮前先读管理器数组，为 0 绝不调 `Set`；
2. 为 0 时调用引擎自己的重建函数 `0x17D47B0`（`AutoEnsureManagers=1`）再复查；
3. 每个引擎函数的**首 16 字节签名**都在启动时校验，不匹配就整块禁用并
   打 `signature mismatch` 警告（避免换版本后拿着旧 RVA 乱调）。

**代码改动（全部在 `plugin/src/AlwaysScan.cpp`）**：
- 新增 ~250 行「原生 outline」小节：函数解析/签名校验/管理器守卫/挂摘/重申；
- `SyncNativeOutline()`：新目标或距上次重申超过 `ReassertMs` 才动手，掉队的写回 12 并 `Clear`；
- `HighlightMode`（1=原生描边【默认】，0=旧 EFSH 方案）——旧代码完整保留可对照；
- 原生模式下**不再需要令牌桶 / FormList 信箱 / Papyrus 桥**；
- `OnlyInFront` / `FrontFovDeg`：把身后的目标排除（默认关，符号约定待实测确认）；
- 统计日志新增 `outline=<已挂>/<nativeReady>/<存活管理器数>`。

**新增逆向工具**：`tools/re/func.py`（`at` / `callers` / `qword` / `rip` / `strings` / `vtable`）、
`tools/re/colname.py`（COL RVA → 类名）。

### v1.1（2026-09-16）—— ★ 修掉「载入存档必崩」（详见 docs/02）

**症状**：v1 部署后两次启动游戏，载入存档后不久必崩；游戏根目录留下
`Starfield_09-16-09-54.dmp` / `-09-55.dmp` 两个转储。

**铁证**：第一次崩溃的异常地址 = `SAS_AlwaysScan.dll+0x10E20`，
用 PDB 符号化后是 **`AlwaysScan.cpp:515` = `cell->ForEachReference(...)`**，
异常码 `0xC0000005`、访问地址 `0x0`。
反汇编现场显示编译器按 **`references@0x88` / `lock@0x128`** 取成员，
读出来的 BSTArray 是 `size=0x467E0000` 且 `data=nullptr`（自相矛盾的垃圾）。

**根因**：**commonlibsf 声明的 `TESObjectCELL` 成员偏移整体比真实游戏大 8 字节**
（真实 `references@0x80` / `lock@0x120`）。因为现有断言只有
`sizeof(TESObjectCELL) == 0x150`，而整体位移后最后一个成员刚好落在 0x148、尺寸仍然自洽，
**所以 static_assert 完全抓不到**。这与本项目已修过的
`BGSListForm::arrayOfForms(0x30→0x38)`、`TESGlobal::value(0x40→0x48)` 是同一类问题。
（上一代项目 `高亮物品` v20 就踩过这个坑并写进了代码注释，v1 漏掉了。）

**修复**（全在 `plugin/src/AlwaysScan.cpp`）：
1. **弃用 `cell->ForEachReference()` / `cell->IsAttached()`**（两者都按声明偏移取成员）；
2. **候选偏移 + 形状校验自适应**：`{0x80, 0x88}` 逐个试，判据 = BSTArray 头自洽
   （`size<=200000 && capacity>=size && capacity<=1<<20` 且 data 可读）
   + 抽查前 4 个元素的 `formType(+0x2E) ∈ {REFR, ACHR}`；都不过就本轮不扫描；
3. `cell` 指针本身先过 `IsReadable`；

## 踩坑记录（本轮新增）

1. **`.pas` 必须纯 ASCII** —— UTF-8 中文注释被按 GBK 解码后字节撞进语法，
   报 `Error in unit 'SAS_BuildPlugin' on line 224 : = expected but '(' found`。
   浪费了一整轮 5 分钟构建。`build-sas.ps1` 现在会**预检并拒绝**含 `>127` 字节的 .pas。
2. **`.pas` 里不能出现花括号** —— Pascal 的 `{ }` 注释在**第一个** `}` 处结束，
   在注释里写一个 `}` 会把后半句当代码解析，报 `Declaration expected but '...' found`。
   又浪费一轮。现在改成一律用 `//`，并且构建脚本**预检花括号**。
3. **`std::min/std::max` 与 `Windows.h` 的 `min/max` 宏冲突**（`error C2589`）→
   在 `PCH.h` 最顶部定义 `NOMINMAX`。
4. **`tools/re/xref.py` 的第一版有误报**：只按「4 字节等于所需 disp32」匹配，
   把 `mov rcx,[rax+0x48]` 的后半截当成 RIP 引用。已加「反汇编形状校验」。
5. 上一代项目那条「**不能缓存 `BSTArray` 的 data()/capacity()**」
   （否则延迟 `HEAP_CORRUPTION` 崩溃）在本项目里从一开始就守住了：本插件**运行期零缓存**。
6. **★ commonlibsf 的 `TESObjectCELL` 偏移是错的（整体 +8）** —— 见 v1.1 段与 docs/02。
   教训：**头文件注释里的偏移 ≠ 编译器算出来的偏移**，而 `static_assert(sizeof(...))`
   只保证尺寸、**保证不了成员位置**。凡是「信头文件偏移去解引用指针」的地方都要先校验。
7. **「形状校验」比「猜偏移」可靠**：v1.1 起对候选偏移做 BSTArray 头 + 元素 formType
   双重校验，谁通过用谁 —— 这样即使偏移假设变了对错，最坏结果也只是「不发光」，
   而不是崩游戏。
8. **解析 minidump 的两个坑**（已在 `tools/re/dmpinfo.py` 修好）：
   `MINIDUMP_EXCEPTION_STREAM.ThreadContext` 是 `{DataSize, Rva}`（写反 ⇒ 读到全 0 寄存器，
   会误判「上下文没保存」）；`MINIDUMP_THREAD.Stack` 在 **+24**（+16 是 `Teb`，
   写错就会「扫」到一段根本不是栈的内存）。

**B. 运行时**（每 5 秒）
```
[info] scan#N cell=XXXXXXXX off=0x80 refs=NNNN cand=NNN sel=NN outline=A/1/11 ... on=1
[info]   outline remove: rmOk=NN unhMiss=NN removeMiss=NN removeReady=1 unhighlightReady=1
[info]   timing: scan avg=Nms max=Nms ops=N deferred=N loading=0
[info]   papyrus: guideHb=NNN guideState=S
[info]   rejTypes (…): ft=…x…
[info] manager map[runtime] state=0 : mgr=0x… cap=… count18=… count20=… data=0x…

```
判据：
- **`timing: scan max` 应是个位数毫秒**（换场景那几轮可能高一些，但几轮内要落回来）；
- **`ops` 稳态接近 0**（站着不动时宽限期应当把目标抖动全部吃掉）；

- **`papyrus: guideHb` 每次统计都该比上一次大**（4 次/秒 × 5 秒 ≈ +20）；
  `guideState` 期望 3（法术 + 效果都在）；
- `manager map[…].count18` 与 `前 N 个非空键` 是「键到底是什么」的最终答案，把这行发我。

1. **卡顿消失**（走动、转身、进出建筑都不该有周期性 hitch）；

### v1 游戏内实测判据

日志：`<我的文档>\My Games\Starfield\SFSE\Logs\SAS_AlwaysScan.log`

**A. 基本功能**
1. 进游戏后**不装备扫描仪**，眼前 50 米内的可拾取/可交互物品应亮起来（原版橙色或青白色描边）；
2. 按 **F8** → 高亮**立刻**全灭；再按 → 重新亮起；
3. 走进新房间/新区域，物品在 1~2 秒内亮起，**不跟随**（不会出现「要等很久才亮」）。

**B. 日志期望**
```
[info] SAS_AlwaysScan installed (main thread NNNN)
[info] config: radius=50.0m duration=90s targets=160 hotkeyVK=0x77 startEnabled=True
[info] forms bound: prefix=XX000000 quest=XX000806 arrayOfForms@0x38 ...
[info] reset (first cell) play=0 stop=0 glow=0
[info] scan#N cell=XXXXXXXX off=0x80 refs=NNNN cand=NNN sel=NN lit=NN played=N stopped=0
       play=a/b stop=0/0 tok=I bp=0 rej=0 on=1 retired=0
[info] AlwaysScan OFF (hotkey)      ← 按 F8 时出现
[info] pending stop queued: NN
```
判据：
- `forms bound` 必须出现（不出现 = ESM 没被加载，或 FormID 顺序和 DLL 常量不一致）；
- **`off=0x80`**：引用数组偏移自适应选中的值。**期望是 0x80**；若稳定在 `0x88`
  说明本轮对 `TESObjectCELL` 的 +8 判断反了，需要回看 docs/02；
- **`refs`** 是当前 cell 的引用数，应该是几千这种量级（不可能是几亿）；
- **`rej`** 是「数组校验没通过而跳过」的累计次数。刚进游戏的头一两秒会有几次
  （世界还在稳定），之后**必须不再增长**；持续增长 = 数组一直校验不过 → 查 docs/02；
- `cand`/`sel` 随场景变化，`sel` ≤ `MaxTargets`；
- `played` 增长很慢（稳态 ≈8 条/秒以内），**站着不动时 `played` 基本不涨**；
- `stop=0/0` 常态（只有关开关时才会有内容）;
- `bp=0`（背压计数，长期非 0 说明脚本没跟上）。

**C. 不回归红线**
- **活着的 NPC / 生物一个都不亮**；
- 换场景 / 读档**不崩溃**；读档后身边的东西**还会亮**（`Epoch` 自愈生效）；
- 无「卡顿」（`GET` 掉的日志里不出现 VM 相关的冻结记录 —— 本项目没有开 Papyrus 日志，
  以主观流畅度为准）。

**D. 如果 `forms bound` 不出现**
1. 确认 MO2 里 `Starfield Always Scan (SFSE)` 已启用、`StarfieldAlwaysScan.esm` 已激活；
2. 确认进游戏前 MO2 是**重启过的**（MO2 开着的时候改 profile，它会把文件写回去）；
3. 看 `SFSE\Logs\` 下是否有 `SAS_AlwaysScan.log` 与 `sfse.log` 里那一行 `loaded correctly`。
