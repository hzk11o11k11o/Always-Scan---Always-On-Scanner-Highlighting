## 2026-10-15 · 订正 R19：室外高亮延迟（矿石、植物）

公开版仍 **2.0.1**，DLL build 仍 **5.1.0**；未提升版本号，未推送远程。

### 原因核查

- 室内当前 cell 每轮全扫；室外近期 cell 超过 2000 引用时按默认 5 片、每 200ms 一片遍历。但 `cands` 每轮重建，只含本片，上一片尚未挂上的目标直接失去处理机会；已有目标的重申、换色和模型复检也随片进出。默认需等约 1 秒才能再次参与，预算不足时可反复延后。宽限期只保留账本，不能保留待办或保证复检公平。
- `MaxTargets` 在检查模型前就选满；通道挂载遇到无 3D 返回失败，但调用前已扣 `MaxOutlineOpsPerScan`。例如前 64 个近处引用无模型，就能每轮用光 64 条预算，后面的可绘制目标一直等待。室外流式加载的矿石、植物更易暴露此问题。
- 原复检每轮仅查当前候选的 32 个下标，预算最后使用；分片与游标可能锁相。例如 5 片、160 个候选、每轮 32 个，同一片总是只查到同一段；预算耗尽还会跳过完整步长。稳定列表下 256/32×200ms≈1.6s 不是原实现的延迟上界。
- 换色失败撤账后，同轮新挂循环还会再试一次、再扣预算。
- 现有日志没有足够的当次地表模型就绪数据，不能给出游戏内前后耗时结论。历史窗口可见 `cells=7 cand=63 outline=232` 等跨片候选不连续形态；以上因果由真实代码及可重复回归场景验证，不把日志中的 `0ms` 当作无延迟证明。

## 踩坑记录（精选 —— 完整版见 git 历史）

1. **`.pas` 必须纯 ASCII，且不能出现花括号** —— UTF-8 中文注释会被按 GBK 解码、字节撞进语法；
   Pascal 的 `{ }` 注释在**第一个** `}` 处结束。`build-sas.ps1` 现在**预检并拒绝**
   （含 `>127` 字节 / 花括号的 `.pas` 直接报错）。
2. **`std::min/std::max` 与 `Windows.h` 的 min/max 宏冲突**（`error C2589`）
   → 在 `PCH.h` 最顶部定义 `NOMINMAX`。
3. **commonlibsf 的 `TESObjectCELL` 偏移是错的（整体 +8）** —— 头文件注释里的偏移
   ≠ 编译器算出来的偏移；`static_assert(sizeof(...))` 只保证尺寸、**保证不了成员位置**。
   凡是「信头文件偏移去解引用指针」的地方都要先校验。
4. **「形状校验」比「猜偏移」可靠**：最坏结果也只是「不发光」，而不是崩游戏。
5. **RTTI 的 `REL::ID` 查出来的是 TypeDescriptor，不是 vtable**（v4.11 栽过）——
   正确求法只有 `COL → TypeDescriptor` 链或「构造函数里写这个指针的那条指令」；
   已固化为 `tools/re/vtable_owner.py`。附带：多重继承里同一个类的所有 vtable 的
   COL 都指向同一个 TD ⇒ **对象偏移才是判据**（再用「首槽析构 thunk」交叉校验）。
6. **「安全阀」的阈值本身也要被核对，并且阀要留「阀自己错了」的日志**
   （v4.11 就是 40 条 WARN 破的案）。
7. **取证日志的额度要「按名字均摊」**：全局 48 条在长会话里必然烧光 ⇒ 改成
   「每个名字头 3 条必记」，任何一局都能看到全貌。
8. **★ 写进表 ≠ 生效**（v4.18）：颜色是「参数表的静态数据」，落地要经过
   「管理器创建 → 交给渲染侧」；管理器只在创建那一刻读表 ⇒ 覆盖必须写在创建之前。
