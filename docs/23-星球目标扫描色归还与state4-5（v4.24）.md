# 23 · 星球目标「扫描后变绿」的真根因：state 4/5 被 MOD 覆盖（DLL v4.24.0 / 发布版 1.7.6）

> 建立：2026-09-26。触发：用户实测反馈（原文）——
>
> ```
> 矿石、气体、液体、植物、动物现在颜色扫描前是原版颜色，
> 但是举起扫描仪扫描的颜色不是原版，而且扫描后，没有变成原版扫描后的绿色
> ```
>
> 一句话结论：**原版「扫描后变绿」用的是 state 4 / 5（原生绿 `#27C684`），
> 而 v4.19~v4.23 把它们覆盖成了「设备 青 `#00E5FF`」和「弹药救援 亮绿 `#00FF66`」**
> ⇒ 举着扫描仪时，已扫描的星球目标显示成青色（远）/ 亮绿（近），永远看不到原版绿。
> 修法 = **state 4/5 的颜色一个字节都不写**（与 v4.22 归还 7/8 同一个道理）。

---

## 一、证据链（反汇编 0x159ED90 + 用户日志 + 原生色表）

### 1.1 引擎的扫描求值函数会写哪些状态 —— 上一轮的结论漏了两个

`0x159ED90` 是原版扫描仪的**逐引用求值函数**（唯一会写 outline 状态的地方，
`func.py callers 0x17D52B0` 只有它的两个调用点）。v4.17~v4.23 的注释一直写着
「引擎只会产出 **0/1、2/3、7/8、9**」——那句话**只看了函数尾部
（`0x159F604`~`0x159F654`）**，漏了前面两段。本轮把整个函数
（`0x159ED90`，约 0x960 字节）反汇编了一遍，**全部写状态的位置**：

| RVA | 指令 | 产生 | 条件（反汇编原文） |
| --- | --- | --- | --- |
| `0x159F31B` | `mov edx, 9` | **9** | `call 0x17FCAB0(ref)` 为真 ∧ `[ref+0xF67] != 0` |
| `0x159F4AF` | `add edx, 4` | **4 / 5** | 见 §1.2（该条可能是编译器产物/另一入口，真正生效的是下一条） |
| `0x159F562` | `add eax, 4` | **4 / 5** | `[rbp+0xe8]`（在范围内）= 1 ⇒ **5**；否则 **4**（见 §1.2） |
| `0x159F601` | `mov edx, 0xa` | **10** | `call 0x5129d0([ref+0xC8])` 非空 |
| `0x159F61E` | `add edx, 7` | **7 / 8** | `bl != 0`：在范围内 ⇒ 8，否则 7 |
| `0x159F63C` | `add edx, 2` | **2 / 3** | `bl == 0` ∧ 原状态 = 12 ∧ `r13b != 0` |
| `0x159F643` | `setne dl` | **0 / 1** | `bl == 0` ∧ 原状态 = 12 ∧ `r13b == 0` |

⇒ **11 个槽位里，引擎不写的只有 state 6**（这一点与 INI / 文档里
「4/5/6/10 是 MOD 专用」的旧说法**矛盾，以本节为准**；旧说法只反汇编了尾部一段）。

### 1.2 ★ 4/5 是怎么来的：星球目标「已扫描 ⇒ 绿」

`0x159F4C2` 开始的这一段（`0x159F4C2`~`0x159F565`）逐层解引用，
每一层都做了 formType 断言（formType 在 `TESForm+0x2E`）：

```
0159F4C2  mov rdi,[rsp+0x20]          ; rdi = 被求值的引用
0159F4C7  mov rax,[rdi+0x98]          ; rax = 引用的 base 记录
0159F4D7  cmp byte [rax+0x2e], 0x2e   ; ★ base formType == kFLOR (0x2E) ?
0159F4E1  mov rax,[rax+0x260]         ; FLOR+0x260 = TESProduceForm::produceItem
0159F4F1  cmp byte [rax+0x2e], 0x3f   ; ★ formType == kLVLI (0x3F) ?
0159F4FB  cmp byte [rax+0x13a], 0     ; 条目数 > 0 ?
0159F504  mov rax,[rax+0x120]         ; 第一个条目
0159F513  cmp byte [rcx+0x2e], 0x28   ; ★ formType == kMISC (0x28) ?
0159F519  mov rbx,[rcx+0x238]         ; MISC+0x238 = BGSCraftingResourceOwner 的
                                      ;   24 字节三元组数组（BSTArray<BSTTuple3<…>>）
0159F525  mov eax,[rbx]               ; size（BSTArray size@+0）
0159F52B  mov rbx,[rbx+8]             ; data（★ data@+8，与 v4.23 的订正一致）
   for each 24 字节元素:
     0159F548  cmp byte [rcx+0x2e], 0x9f   ; ★ formType == kIRES (0x9F) = BGSResource
     0159F54E  call 0x1597A50              ; 「这个资源已经扫描过（进了勘测数据）？」
     0159F557..562  state = 4 + (在范围内 ? 1 : 0)   ; ⇒ ★★ 4 / 5
```

* `0x1597A50(irES)` 的实现里是一串「全局单例 + `map.find(formID)`」（`call 0x7b7d60`），
  返回真表示**这个 BGSResource 已经在玩家的勘测/已知数据里**；
* 也就是说：**矿脉 / 气泉 / 液池 / 植物（FLOR）只要它产出的资源已经扫描过，
  引擎就写 state 4/5** —— 近处 = 5、远处 = 4；
* 状态 7/8 与 4/5 的分工（与用户描述一一对应）：
  * **未扫描** ⇒ 走尾部 `add edx,7` 分支 ⇒ **7/8**（原生 = 青色脉冲轮廓）；
  * **已扫描** ⇒ 走本段 ⇒ **4/5**（原生 = **绿色 `#27C684`**）。

### 1.3 原生色表（用户那一局日志 `outline colors[install]`，11 行直读）

```
state= 4 Bounty 基色=#27C684 a=20 ( 39,198,132) 脉冲High=#27C684 a=FF 脉冲Low=#27C684 a=80
state= 5 Social 基色=#27C684 a=40 ( 39,198,132) 脉冲High=#27C684 a=FF 脉冲Low=#27C684 a=80
```

⇒ 整个 11 个状态里**只有 4/5 是绿色**。用户说的「原版扫描后的绿色」只能是它们。

而 v4.19~v4.23 的 MOD 覆盖（同一份日志的覆盖行）：

```
[install] outline colors: state=4 覆盖为 #00E5FF <- device   （青）
[install] outline colors: state=5 覆盖为 #00FF66 <- ammoaid  （亮绿）
```

⇒ 已经把「绿」改掉了。`ManagerProbe` 那一行的 `outline colors[install]` 里
state=4/5 就是被 MOD 写过的值（青 / 亮绿），这也是为什么之前几轮没人发现：
**日志里那两个槽位早就不是原生色了**。

### 1.4 用户那一局日志的旁证（让位本身是好的）

```
[10:15:03] scan#186 … cand=0 sel=0 … monocle=1
           skip (窗口内): off=0 throttle=247 … yield=44      ← 举着扫描仪：FLOR 全部让位
[10:16:35] scan#543 … cand=58 sel=58 … monocle=0
           skip (窗口内): off=0 throttle=408 … yield=623     ← 放下扫描仪：整批重挂
```

⇒ v4.23 的「让位」链路**工作正常**（举着扫描仪时 FLOR 不进候选），
所以问题不在「让位没生效」，而在**让位之后引擎画出来的颜色被 MOD 改过**
（state 4/5 的颜色是全局的，改一次影响所有用它的目标）。

**行为变化（给用户的三句话）**：

1. 举着扫描仪扫描星球上的矿石 / 气体 / 液体 / 植物：**扫描前 = 原版青色脉冲**（不变）、
   **扫描完成后 = 原版绿色 `#27C684`**（本轮修好的就是这个）；
2. 「设备」（ACTI / TERM）与「弹药、救援」继续用 state 4/5，颜色变成**原版绿**：
   * 弹药 / 救援：仍是「绿」这一组（由亮绿 `#00FF66` → 原版绿 `#27C684`，观感变化最小）；
   * 设备：由青 `#00E5FF` → 绿（v4.19 的「电脑青」取消）；
   * 想恢复这两个自定义色 ⇒ INI 写 `ColorAmmoAid=00FF66` / `ColorDevice=00E5FF`
     （**代价**：原版「扫描后变绿」会被盖掉：远的变 `ColorDevice`、近的变 `ColorAmmoAid`）；
3. 「笔记」仍用 state 6（引擎唯一从不写的槽位）⇒ 不受任何影响。

## 四、验收判据（下一次进游戏）

1. 启动日志：
   ```
   config: state4_5 归还引擎 -> 「设备」(state 4) / 「弹药救援」(state 5) 的颜色不再覆盖
   （= 引擎原生绿 #27C684）：引擎用这两个槽位画「已扫描的星球目标」（近 = 5 / 远 = 4）…
   config: managerOccupancyProbe=1 -> …
   outline colors[install]:  state= 4 Bounty 基色=#27C684 … / state= 5 Social 基色=#27C684 …
   ```
   ＋ 覆盖行从 9 条降到 **7 条**（0/1/2/3/6/9/10）——**不该再出现 `state=4` / `state=5`**。
2. ★★ 肉眼（核心）：拿扫描仪对着**已经扫描过**的矿脉 / 气泉 / 液池 / 植物
   * 近处 ⇒ **绿色**；远处 ⇒ **绿色**（`#27C684`，就是原版那个绿）；
   * 没扫描过的 ⇒ 青色脉冲（7/8，原版色，不变）；
   * 扫描完成那一刻 ⇒ 由青转绿（原版的「扫描前 → 扫描后」）。
3. ★ 诊断：`manager occupancy[举着扫描仪]: …` 一行出现（≤6 次），
   且**举着扫描仪时 4/5 两个槽位的计数应该 > 0**（= 引擎真的在用它们画绿色）；
   7/8 也应 > 0（未扫描的目标）。
4. 顺带核对（本轮的行为变化）：地上的**弹药 / 医疗包 / 食物**是原版绿（不是亮绿）、
   **终端 / 开关**（设备）是原版绿（不再是青色）——想改回 ⇒ INI 写
   `ColorAmmoAid=00FF66` / `ColorDevice=00E5FF`（改完重进游戏，不用换 DLL）。
5. 不回归：F8 / 扫描仪自愈（放下扫描仪后约 0.8 秒铺回青色）/ 展示柜拿空熄灭 /
   换场景不崩 / 活人一个都不亮 / 笔记仍是黄 / 资源仍是紫 / 杂项仍是蓝 / 容器·尸体仍是橙 /
   门仍是白。

## 五、可复用经验（写给下一轮）

1. **「引擎不写某个状态」这种结论，必须把整个函数反汇编完再下**。
   v4.17 只看了 `0x159F604`~`0x159F654` 那 80 个字节就得出「4/5/6/10 是 MOD 专用」，
   而 4/5 的写入点（`0x159F562`）在它前面 0x100 字节处 —— **一个错误的省略
   在四个版本里没人发现，直到用户把扫描仪举到星球上**。
   本轮的判据：**11 个槽位里只有 state 6 是引擎不写的**（0/1、2/3、4/5、7/8、9、10 全会写）。
2. **「让位」不等于「颜色对」**：让位解决的是「谁写状态」，**颜色是每状态全局的**。
   只要 MOD 覆盖了引擎在用的槽位，让位之后引擎画出来的仍然是 MOD 的颜色。
   ⇒ 借引擎状态之前先问两句：**「引擎会不会写它」**（v4.17 的账本）+
   **「引擎写它的时候是什么语义」**（本轮的账本：4/5 = 已扫描的目标 = 绿）。
3. **`outline colors[install]` 那 11 行是「MOD 覆盖后」的实况**，不能当原生色用：
   本轮就是靠它把「state 4 原生到底是不是青」这个问题定死的（改前 = `#00E5FF`）。
   要把原生色记下来的话，得在**写覆盖之前**读一次（或看更早的日志）。
4. **观测工具先于结论**：新加的 `manager occupancy[...]`（11 个管理器元素数）
   是「引擎在写哪些槽位」的唯一直接证据。以后再遇到「原版颜色不对」，
   先看这一行 —— 比猜「引擎是不是没写」快得多。
5. **反汇编的 formType 断言是定位语义的捷径**：本轮那串
   `0x2E(FLOR) → 0x3F(LVLI) → 0x28(MISC) → 0x9F(BGSResource)` 把「矿石 / 气体 / 液体 /
   植物」与「已扫描 ⇒ 绿」两件事一次串了起来（`RE/F/FormTypes.h` 的注释就是字典）。
