# 00 · 项目总览与技术方案

> 2026-09-16 建立。项目代号 **Always Scan**。

## 一、要解决的问题

原版《Starfield》里，玩家必须**切到手持扫描仪**才能看到物品高亮；而切到扫描仪时
不能开枪、不能用别的工具，很不方便。而且原版只有**屏幕中央那个圆圈里**的东西才会亮。

本 MOD 要做三件事：

1. **不装备扫描仪也能有高亮效果**（核心）；
2. **不受中央圆圈限制** —— 改成玩家周围一个半径（默认 50 米，可配）；
3. **一个快捷键**开关。

## 三、架构

```
┌────────────────────────────────────┐        ┌────────────────────────────────┐
│ SAS_AlwaysScan.dll (C++ / SFSE)    │        │ SAS_Bridge.psc (Papyrus)       │
│                                    │        │                                │
│ 每帧 Tick()（SFSE 永久任务）        │  FLST  │ 每 0.25s Drain()               │
│  ├ 每 200ms 遍历玩家所在 cell       │ ─────► │  ├ 读 OpList / StopList        │
│  │   TESObjectCELL::ForEachReference│ 信箱   │  ├ EffectShader.Play(ref, 90s)  │
│  ├ 距离 + base form 类型白名单过滤   │        │  └ EffectShader.Stop(ref)      │
│  ├ 距离分档挑选（不挤在脚边）        │ ◄──── │                                │
│  ├ 令牌桶限流（稳态 8 条/秒）        │  GLOB  │  └ 进度**只存一份真源**＝GLOB  │
│  └ 差异 → 追加 Play/Stop 请求        │ 游标   │                                │
└────────────────────────────────────┘        └────────────────────────────────┘
```

**为什么「找目标」必须在 C++ 侧**：Papyrus 找东西只能靠
`FindAllReferencesWithKeyword`（实测单次 0.13~0.6 秒、只能覆盖带特定关键词的
base form、结果上限被 Papyrus 数组卡在 128）。原生侧直接遍历 cell 的引用数组，
几千个引用一轮只有微秒级，**无关键词、无上限、无脚本开销**。

**为什么「点亮」也在 C++ 侧**（v2 起）：引擎自带一张「引用 → outline 状态」表 +
11 个 `HighlightManager`，`SetOutlineState` 进去之后渲染器自己画**原版描边** ——
不需要 EFSH、不需要 Papyrus（详见 `docs/03`）。

> ★ **v4.0 现状**：上图里那条「FLST 信箱 + Papyrus Play/Stop」的通道**已经不存在了**，
> `SAS_Bridge.psc` 现在只剩「老存档面包屑一次性清理 + 弹一条 HUD 提示」两件事。
> DLL 自己找目标、自己挂/摘引擎原生 outline。

## 四、跨语言通道（v4.0：只剩一个 GLOB）

| 表单 | 方向 | 说明 |
| --- | --- | --- |
| `SAS_Notify` (GLOB, 0x807) | DLL → 脚本 | DLL 写 1（刚开）/ 2（刚关），脚本读完**立刻归零**并弹一条 HUD 提示 |

就这一个，而且**只服务于「游戏内提示」**：绑不上只是没提示，高亮不受任何影响。

> 历史：v1~v3 用过 `SAS_OpList` / `SAS_OpCursor` / `SAS_StopList` / `SAS_StopCursor`
> （FormList 信箱 + 游标）与 `SAS_Epoch`（读档计数），全部在 v4.0 删除。当时的两条设计要点
> ——「**读档后 GLOB 会回滚成陈旧值 ⇒ 清表必须用 `cursor == size` 相等判定**」与
> 「**游标必须早于 `Play` 推进**」——随之作废，但对任何「游戏内计数器」类设计仍然成立。
> ESM 里那几条旧记录**刻意保留为 FormID 占位**，理由见 `docs/99` 的 v4.0 段。

## 五、视觉层：引擎原生 outline（v2 起，v4.0 加分类分色）

不再自己造视觉，也不再给对象叠 EFSH 发光 —— 直接复用引擎那套数据驱动的高亮：

```
ClassifyBase(base form)  →  Category（可拾取 / 容器 / 设备 / 门 / 植物 / 其它）
                         →  cfg.stateByCategory[Category]（0..11）
                         →  LookupOrAddOutlineState + SetOutlineState(ref, state)
```

引擎按状态取 GMST（`aHighlightScannableOutlineColorHigh/Low` 一族）里的配色与粗细，
和原版扫描仪看到 loot / 已扫描 / 追踪目标时**完全同一套**。
所以「分类分色」在这个架构下几乎是免费的：只要让不同类别用不同状态。

完整逆向推导见 `docs/03-原生outline高亮实现.md`（含 RVA、签名校验、摘除的正确姿势）。

> ★★★ **v5.0（发布版 2.0）起：默认走「完全自建颜色通道」** —— 上面那条
> 「借引擎状态」的路线（`LookupOrAddOutlineState + SetOutlineState`）降级为
> **回退路径**（`ChannelMode=0` 或自建通道不可用时自动回退）。默认路径：运行时
> **自己创建 13 个 `HighlightManager`**（引擎 ctor `0x6532F0`；id 由全局句柄池
> `0x7CB120` 分配、无 11 条上限），每个类别一条、各自一份 32 字节颜色参数；
> 挂 / 摘**复刻引擎自己那两个 3D 图 visitor**（`0x4B2FA10` / `0x4B2F9F0`
> + `0x24181E0`）。**不写引擎的「引用→状态」表、不覆盖引擎配色块** ⇒
> 原版扫描仪 / NPC / 星球目标颜色 100% 原版；类别配色互不干扰；引擎开关扫描仪
> （销毁它自己的 11 个管理器）也不会清掉 MOD 的高亮。完整逆向 / 方案 / 风险 /
> 验收见 **`docs/32-自建颜色通道可行性研究（v5.0）.md`**。

## 六、过滤规则（base form 类型白名单）

| 收 | 不收 |
| --- | --- |
| MISC / BOOK / ARMO / WEAP / AMMO / ALCH / INGR / KEYM / NOTE / SLGM（可拾取）<br>CONT / ACTI / DOOR / TERM / FLOR / MSTT（可交互） | **NPC_ / ACHR / LVLN（NPC 与生物）**<br>STAT（纯场景静态物）、FURN（椅床，太吵）<br>玩家自己、`IsDeleted()`、`IsDisabled()`、不属于本 cell 的 |

改动只需要动 `plugin/src/AlwaysScan.cpp` 的 `ClassifyBase()` 一个 switch
（★ v4.0 起它同时决定**类别**，类别再决定用哪个 outline 状态 = 哪种配色）。

## 七、快捷键

`plugin/src/AlwaysScan.cpp` **每帧轮询 `GetAsyncKeyState`**（只在游戏窗口处于前台时生效），
默认 **F8**，在 INI 里用虚拟键码配置。

> 为什么不用引擎的输入系统：Starfield 的 Papyrus 没有 `RegisterForKey`/`OnKeyDown`，
> 而 commonlibsf 里 `BSInputDeviceManager` 没有头文件、SFSE 的 `InputMap` 只有键码工具
> → 走引擎输入事件源属于「中等风险逆向」。轮询 `GetAsyncKeyState` 是等效且零风险的替代。

## 八、性能与稳定性设计（每条都有前一代项目的实测依据）

| 设计 | 原因 |
| --- | --- |
| 每 200ms 扫一轮，单轮纯内存读（零引擎调用） | 遍历 9000 个引用实测 `iter=0ms` |
| **绝不缓存 `BSTArray` 的 `data()/capacity()`** | 清表可能释放/搬移缓冲，缓存下来就是悬空指针，往那儿写 8 字节 → 延迟 `HEAP_CORRUPTION` 崩溃 |
| `outlined` 表存 `NiPointer`（保活） | 摘高亮要解引用取 3D，裸指针在引用被销毁后就是野指针 |
| 只管主线程（`GetCurrentThreadId` 比对） | SFSE 的 `AddPermanentTask` 挂在 `Command_Process` 上，读档期间加载线程也会调它 |
| **掉队宽限期**（`UnhighlightGraceMs`，默认 1500ms） | 走动时目标会在集合边缘反复进出；没有宽限期就是每 200ms 一轮的 Set/Remove 抖动，主线程被磨出 hitch |
| **单轮调用预算**（`MaxOutlineOpsPerScan`，默认 64） | 换场景/读档会积压几百条待办，一口气做完就是一个长卡顿帧（实测出现过 18 秒空档） |
| 载入画面期间**什么都不做** | 载入时主线程在跑加载，每条引擎调用都被拖慢几十毫秒 |
| 候选按距离排序、已在表里的 ×0.5（黏性） | 站着不动目标不抖；走动时近的新目标仍能顶掉远的旧目标 |
| 配置项只在启动时读一次 | 避免热路径上的文件 IO |
| 引用数组用**候选偏移 + 形状校验**自适应 | commonlibsf 的 `TESObjectCELL` 成员偏移整体 `+8`（见 `docs/02`），谁通过用谁，都不过就不扫 |
| ★ v4.7 **外景连续过渡 + 近期 cell 环** | 外景的 cell 只是「世界的一块」，跨边界走一步不是换场景；旧行为会整批熄灭 + 2 秒不扫描 + 只扫新 cell（`docs/13`）。环 = 玩家待过的 cell，每轮一起扫（形状 + `ref->parentCell` 自洽校验），边界对面也能亮 |
| ★ v4.7 **3D 复检自愈** | 引擎侧描边按 **3D 图节点**登记，外景 3D 流式重建即丢；账本只记「引用」看不到这种单条丢失 ⇒ 每轮复检 `Verify3DPerScan` 个已挂目标的 3D 根，地址变了就重挂（只比较、不解引用） |
| ★ v4.7 **流式变化容差** | 引用数轻微增删（走动时加载线程常态）不再触发「等稳定轮数」，否则每变一次就跳 ≈600ms |

## 九、构建

```powershell
# 全流程（xEdit 生成 ESM ≈ 4~5 分钟 + Papyrus + DLL + 部署 + MO2 profile）
pwsh -File tools\build-sas.ps1

# 只重编 DLL
pwsh -File tools\build-sas.ps1 -SkipPluginBuild -SkipPapyrusCompile

# 只重编脚本
pwsh -File tools\build-sas.ps1 -SkipPluginBuild -SkipDllBuild
```

★ **必须用 `pwsh`（PowerShell 7）**：`build-sas.ps1` 是 UTF-8 无 BOM，
Windows PowerShell 5.1 会按 GBK 解码，中文路径变成乱码。
