## 一、逆向证据链（1.16.244.0；全部反汇编实证，工具 `tools/re/func.py`）

### 1.1 起点：引擎给「已扫描」植物写 4/5 的那段（`0x159ED90`，逐引用求值）

`0x159ED90` 是原版扫描仪的逐引用求值函数（写 state 7/8/9/10 那个，**有写副作用，红线：不可调用**）。
其中 `0x159F32F~0x159F4B2` 段对**所有类型**共用，**植物就是在这里拿到 4/5 的**：

```
0159F33C  byte [rbp+0xe0] = 0                ; out_byte（进度）清零
0159F34B  call 0x1307180(ref)                ; key2 = "ref → 知识 ID"（纯查询）
0159F36B  call 0x7BCBD0(ref, &k1, &k2')      ; k1 = [0x81 组件 + 0x28]（物种/资源 ID）
0159F399  call 0x23FF640()                   ; TLS 单例（懒初始化）
0159F3A2  rcx = [rax + 0x8b0]                ; ★ 知识库 DB（PlayerKnowledge）
0159F3A9  call 0x130A270(db, {&k1,&out,&key2,&list})   ; ★ 查「进度」
…（0x159F3AE）r12b = [rbp+0xe0]
0159F3B6  cmp r12b, 0x64                     ; ★★ == 100（0x64）？
0159F3BA  sete al  → [rbp+0xf8]
…（列表检查，见 §1.4）
0159F4A4  state = 4 + ([rbp+0xe8] ? 1 : 0)   ; ★ 4/5 = 原生绿 #27C684
```

### 1.2 `0x130A270`：查「进度」的两级只读哈希（本实现复刻的正是这一段）

```
0130A2B7  rcx = [rsi]                        ; struct[0] = &k1
0130A2BA  r8d = word [rip+0x4ed7ad2]         ; 类型常量（key 高 16 位）
0130A2C6  edx = [rcx]                        ; k1
0130A2C8  r8 = ((常量<<32)|k1) << 16         ; key = 常量<<48 | k1<<16
0130A2EB  call 0x24105D0([mgr+0x268], &out, &key)   ; ① 主表查找（只读）
0130A2F0  rcx = out[+0x10]（桶）; r8 = out[+0x18]（索引）
0130A2F8  cmp r8, 0xfe0 / rcx==0 ⇒ 未找到
0130A30A  rax = [rsi+0x10]                   ; struct[2] = &key2
0130A31A  edi = word [rcx + r8*4 + 0x12]     ; 二级基址偏移
0130A320  base2 = rcx + edi
0130A32F  call 0x23467B0(base2+0x38, &key2)  ; ② 二级查找（只读，FNV-1a）
0130A334  iter == [base2+0x68]（容量）⇒ 未找到
0130A33A  elem = iter*0x30 + [base2+0x60]    ; 元素 stride 0x30
0130A346  r14d = byte [elem + 0x20]          ; ★★ 进度（0..100）
0130A34F  [out_byte] = r14b
```

### 1.3 只读性核对（每个被调函数都读过反汇编）

| 函数 | 角色 | 只读？ | 证据 |
| --- | --- | --- | --- |
| `0x1307180` | ref → 知识 ID（key2） | ✓ | 查 0x2A 组件（读锁）或查主表；只有引用计数 ++/-- 平衡 |
| `0x347170` | `GetComponent(ref+0xC8, id)` | ✓ | 读锁 `0x22CC350` → 遍历链表 → 释放；无写 |
| `0x24105D0` | 主表哈希查找 | ✓ | 初始化 out（{0,0xfc,0,0xfe0}）→ 哈希 → 桶内二分；无写 |
| `0x23467B0` | 二级哈希查找（FNV-1a） | ✓ | `0xcbf29ce484222325`/`0x100000001b3`，开放寻址只读 |
| `0x23FF640` | TLS 单例（懒初始化） | ✓ | `gs:[0x58]` + slot；返回静态对象 |

**不碰**：`0x159ED90`（写状态 + 登记 + 引用计数）、`0x130A270` 本身（它会写出一个 vector；本实现只复刻它的读表段）、`0x7BCBD0`（组件缺失时的兜底路径含 `lock xadd` + 表写）。

### 1.4 与旧主判据（`GetOutlineState` = `0x1306E80`）的区别 —— 这就是「植物恒答未扫描」的原因

`0x1306E80` 的三条分支（见 `out/dis_1306E80.txt`）：

- 有 0x2A 组件 + FormID 是**运行时临时引用**（`0xFF……`，外景星球目标）⇒
  `0x7BCBD0` + **`0x7B8260`**：查的是 `[base2+0x80]` 的**实例级红黑树**（键 = FormID 派生的
  三元组 {d0,d1,d2}）——**植物查不到**（用户实测「问=446 已扫描=0」）。
- 有 0x2A 组件 + 普通 FormID ⇒ `0x7B7D60`（另一条查询）。
- 无 0x2A 组件 ⇒ 查主表 `[rbp+0x268]`（与 0x1307180 同表，另一条路）。

而**本判据**查的是 `[base2+0x38]` 的**物种级哈希**（键 = 知识 ID）——**和引擎画 4/5 用的是同一份数据**。
⇒ 「进度查询」才是对植物（以及一切目标）都成立的「随时可问」判据。

## 二、实现映射（`plugin/src/AlwaysScan.cpp`）

### 2.1 常量与签名（v5.2 常量段）

```
kRvaFloraKnowledgeId   = 0x1307180   kSigFloraKnowledgeId[16]  = 48 89 5C 24 10 …
kRvaFloraGetComponent  = 0x347170    kSigFloraGetComponent[16] = 48 89 5C 24 08 …
kRvaFloraHashFind      = 0x24105D0   kSigFloraHashFind[16]     = 48 89 5C 24 08 …
kRvaFloraSubFind       = 0x23467B0   kSigFloraSubFind[16]      = 4C 8B 51 30 4D 8B CA …
kRvaFloraSingleton     = 0x23FF640   kSigFloraSingleton[16]    = 48 83 EC 28 BA B8 00 00 00 …
kRvaFloraKeyTypePatch  = 0x130A2BA   kPatFloraKeyType[4]       = 44 0F B7 05（movzx r8d, word [rip+disp]）
```

**key 类型常量**不硬编码：启动时验证 `0x130A2BA` 的指令模式，再从 `disp32` 算出常量地址读 word
（RVA 表一变也不会读错值）。

偏移（全部来自 §1.2 反汇编）：组件容器 `ref+0xC8`、组件 id `0x81`、key1 `[comp+0x28]`、
DB `[单例+0x8B0]`、主表 `DB+0x268`、查找输出 `+0x10`（桶）/`+0x18`（索引，哨兵 `0xFE0`）、
二级偏移 word `+0x12`、二级表 `+0x38`、元素数组 `+0x60`、容量 `+0x68`、元素 stride `0x30`、
进度 `[元素+0x20]`。

### 2.2 查询流程（`QueryFloraScanProgressDirect`，全 SEH + 逐层形状校验）

```
1. container = [ref+0xC8]，IsPlausiblePointer
2. comp = 0x347170(container, 0x81)；IsReadable(comp, 0x2C)
3. key1 = [comp+0x28]（0 ⇒ 这条链不适用，回退）
4. key2 = 0x1307180(ref)                     ← 纯查询
5. mgr = [0x23FF640() + 0x8B0]               ← TLS 单例
6. keyA = (keyType<<48) | (key1<<16)
   out[4] = {}; 0x24105D0(mgr+0x268, out, &keyA)
   out[+0x10]==0 && out[+0x18]==0xFE0 ⇒ 无记录（回退）
7. base2 = out[+0x10] + word[out[+0x10] + out[+0x18]*4 + 0x12]
8. iter = 0x23467B0(base2+0x38, &key2)
   cap = [base2+0x68]；iter >= cap ⇒ 无条目（回退）
9. prog = byte[[base2+0x60] + iter*0x30 + 0x20]
   prog > 100 ⇒ 形状不对（不采信）
10. prog == 100 ⇒ 已扫描
```

### 2.3 缓存与判定语义（`QueryFloraScanProgressCached`）

- **按 base（物种）缓存** —— 引擎数据本来就是 species 级 ⇒
  「扫一个实例 ⇒ 同 species 全绿」由**引擎数据**保证（替代 v5.1.2 的物种扩散表）。
- TTL：`percent == 100` ⇒ 10 分钟（`kFloraProgressFullTtlMs`）；`< 100` ⇒ `FloraUnscannedTtlMs`（默认 5 s）；
  查询失败 ⇒ 10 s（`kFloraProgressFailTtlMs`，避免每轮重撞）。
- 读档 / 换场景 / 放下扫描仪 ⇒ 随 `InvalidateFloraScannedCache` 一起清（进度是**存档级**数据）。
- 判定接入 `FloraTargetScanned` 的 **ⓠ（最高优先级）**：
  `ok && percent == 100` ⇒ 绿（短路）；`< 100` ⇒ **不短路**（继续走 ⓪.5 / ① / ②，宁可青）；
  失败 ⇒ 不短路（自动回退）。

### 2.4 记忆层总开关（`FloraUseMemory`，默认 0）

以下全部加 `if (!g_cfg.floraUseMemory) return …;`（默认**不参与任何判定、不学习、不落盘**）：

| 位置 | 行为 |
| --- | --- |
| `FloraRefKnown`（⓪） | 引用记忆不参与 |
| `FloraBaseKnown`（⓪.2） | 物种表不参与（「全绿」投诉的主嫌） |
| `RememberFloraRef` / `RememberFloraBase` | 不学习（含 ⓪.5 的动态激活） |
| `SeedFloraBaseFromRefMemory` | 不播种（R8 的落盘播种） |
| `LoadFloraLearnTable` / `AppendFloraLearnRecord` | 不读 / 不写 `SAS_AlwaysScan.flora-learn.txt`（文件原样保留） |
| 「沿用旧结论」（`noAuthoritative && hasPrev && prevScanned`） | 不粘滞（TTL 内的 `floraScannedCache` 性能缓存仍生效） |

保留的判据（全部是引擎自己的数据）：**ⓠ 进度直读** + ⓪.5 状态表只读探针（4/5）+
① `GetOutlineState` + ② 资源链（LVLI 矿脉）。

`ProbeFloraEngineState` 升级为**返回结论**（0 = 表里没有 / 1 = 引擎画青 / 2 = 引擎画绿）——
记忆层关闭时 ⓪.5 直接消费引擎结论，不再要求「先记进记忆表再查」。

## 五、经验

1. **「引擎的知识」有多个载体，要找对那一个**：同一件事（「这个物种扫过没」）在引擎里有
   实例级红黑树（`0x7B8260`）、物种级哈希（`0x130A270` 那条）两份记录 ——
   旧主判据查的是前者（对植物恒答未扫描），而引擎给植物画 4/5 用的是后者。
   **「名字像」≠「语义同」的第二次实证**（第一次是 v4.28 的 `GetOutlineState`）。
2. **复刻「写状态」函数的读表段，而不是调用它**：写状态函数（`0x159ED90`）里有登记 + 引用
   计数 + vector 写出；把它**读结论的那几行**原样搬过来（自己走两级只读哈希）就能拿到
   「随时可问」的判据，且零副作用。
3. **key 类型常量从指令里现取**（`44 0F B7 05 disp32`），比硬编码 RVA 更抗版本变化；
   签名校验失败时**整体禁用 + 回退**，绝不让「半残的查询」参与判定。
4. **「抛弃记忆」的正确姿势是关掉它的每一个入口**（读 / 写 / 播种 / 落盘 / 粘滞），
   而不是只关读取 —— 否则「学习」仍在后台积累，下一轮又会以别的形式回来
   （用户报的「全绿」就是播种+扩散的积累效应）。
5. **引擎数据的粒度就是缓存该用的粒度**：进度（percent）是物种级的 ⇒ 按 base 缓存
   就等于「同 species 扩散」，而且**数据源是引擎**（不用我们自己外推）。
6. **失败方向的选择**：`percent < 100` 与「查询失败」都**不短路为青**（继续走旧判据）；
   只有 `== 100` 才短路为绿 —— 假绿（用户最敏感）的风险被压到最小。
