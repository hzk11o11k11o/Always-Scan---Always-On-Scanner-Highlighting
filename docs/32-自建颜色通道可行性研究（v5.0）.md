# 32 · 完全自建颜色通道 —— 可行性研究（DLL v5.0.0 / 发布版 2.0）

> 建立：2026-09-26。触发（用户原文）：
>
> ```
> 之前说原版引擎颜色只有11条通道，这导致了很多限制以及不安全性，
> 现在开始研究完全自建颜色通道的可能性，且将版本号推进到2.0
> ```
>
> 本文是**研究结论 + 方案设计 + 实现映射**三合一。全部 RVA 取自本机
> Starfield 1.16.244.0 的 Starfield.exe（与 `docs/03` 同版本），
> 所有结论都有反汇编证据，**没有推测**。

---

## 零、一句话结论

**引擎的"11 条通道"只存在于"状态表 → 管理器"这一层路由上；真正画描边的渲染层
是一对按 id 动态增长的存储表（`ref_id → manager_id → 32 字节参数`），
容量上限与 11 无关。**

⇒ 只要**自己创建 HighlightManager**（引擎 ctor `0x6532F0`，id 由全局句柄池
`0x7CB120` 分配、无 11 限制），**绕过状态表直接挂载**（引擎自己挂引用的同一条
3D 图 visitor 路径），就能拿到任意多条、互不干扰、**完全不写引擎状态表、
不覆盖引擎任何颜色**的自建颜色通道。

---

## 一、为什么要做：11 个槽位的「三宗罪」

v4.22 ~ v4.33 的完整挣扎史（`docs/22` ~ `docs/31`）就是这三条限制的实证：

| # | 现象 | 根因 | 历史妥协 |
| --- | --- | --- | --- |
| ① | **槽位不够** | 引擎只有 state 0..10；0/1 通用（含活人 NPC）、4/5 已扫描星球目标、7/8 未扫描星球目标 —— 6 个槽位**不能借** | v4.32 把 12 个类别**并成 6 组**（服饰并进武器、笔记并进资源），配色自由被压缩 |
| ② | **覆盖即污染** | 配色块（RVA `0x5919A88 + state*0xA0`）与 ref 参数表（`+0x80`）是**引擎全局**：覆盖 state 的 RGB ⇒ 原版手持扫描仪在同状态上的描边颜色**一起变** | v4.19~v4.21 一直带着「原版扫描仪会变成我们的颜色」这个副作用；v4.30 因为 NPC 变红被迫把 0/1 归还 |
| ③ | **引擎一动就崩** | 引擎每次开关扫描仪会 `0x17D4B30` 销毁 11 个管理器 + 清空状态表 ⇒ MOD 的账本悬空（v3.2 起要专门做自愈） | `DetectEngineOutlineLoss` + 重挂预算（v3.2 / v4.29） |

**自建通道把三条全部消掉**：通道数任意（要多少建多少）、颜色只写自己的参数、
管理器不在引擎的 11 个里（引擎不销毁它）⇒ 连"让位 / 归还 / 并组"这些妥协都不再需要。

## 二、引擎高亮架构的完整逆向（本轮新证据）

### 2.1 三层结构总览

```
① 状态表（红黑树）            【引擎评估用；MOD 旧路径写这里】
   std::map<TESObjectREFR*, u32 state>   树头 RVA 0x5F39CE0
   · 引擎只经 0x17D5BE0(查/插) / 0x17D52B0(Set) / 0x17D4F10(建空条目) 写
   · state 0..10 = 11 种样式；12 = 无

② HighlightManager × 11       【逻辑分组：一组共享一份 32B 渲染参数】
   void* g_outlineManagers[12]  RVA 0x5F39CF0（第 12 槽恒 NULL）
   · 对象 0x48 字节，vtable 0x4B2FA50，内嵌哈希表 @ +0x18（键 = ref 的渲染 id）
   · +0x40 = 管理器的**全局句柄 id**（0x7CB120 分配，与 state 无关）

③ 渲染侧存储（宿主 H = [RVA 0x59751E8]）
   H+0xE8 → 存储 A：manager_id → 32 字节参数（颜色/脉冲/系数）  ★ 画出来的颜色
   H+0xF0 → 存储 B：ref_id     → manager_id（4 字节）          ★ 这个 ref 用哪套参数
   · 两个存储结构相同：+0x2C8 = u32 idTab（按 id 索引→槽号）、
     +0x3C8 = 数据数组（A 每槽 32B / B 每槽 4B）、+0x2D0 = 渲染实体表
```

**关键点：渲染层只认 ③ 的两张表。** ①② 是引擎自己的"记账/路由"，
它的唯一用途是"引擎评估 → 决定给谁挂、挂哪套参数"。

### 2.2 证明 ③ 是动态容量（"11 条上限"不在渲染层）

**存储构造**（`0x2972430` = 存储 A 的构造、`0x2970E20` = 存储 B 的构造，都是 0x440 字节分配）：

```
02972497  lea rbx, [r15 + 0x3C0]        ; 内嵌子对象
029724B6  call 0x2973C70                ; 初始化
029724C5  lea rcx, [r15 + 0x3F0]; call 0x8146B0
029724D2  lea rcx, [r15 + 0x3F8]; call 0x8146B0
029724DF  lea rcx, [r15 + 0x400]; call 0x814720
029724F2  [r15 + 0x2C8] = [r15 + 0x3F0] ; ★ idTab = 动态容器（vector 风格）
02972500  [r15 + 0x2D0] = [r15 + 0x400] ; ★ 实体表 = 动态容器
0297250E  [r15 + 0x40]  = [r15 + 0x3F8]
```

**槽分配**（`0x2936540` = 存储 A 的 EnsureSlot，`0x2910480` = 存储 B 的同款）：

```
029365CE  r10 = [r14]                   ; 槽池对象
029365DE  call 0x22CF620                ; 从自由列表取一个槽号（池化、可增长）
02936601  [rbx] 位域 = 槽号（22 位）
02936618  [idTab + id*4] = 槽号          ; ★ id → 槽号，按需分配
```

⇒ idTab / 参数数组 / 实体表**全是动态增长容器**，没有任何 11/12 项检查。
id 本身（句柄）上限 0xCBF00（`0x653040` 的校验常量），那是**全局句柄池**的
容量（83 万），与通道数无关。

### 2.3 管理器是"可组合"的独立对象（ctor 0x6532F0 全流程）

```
006532F0  HighlightManager*(rcx=mem, rdx=&params32)
00653309  [rdi+8] = 0
0065330C  [rdi]   = vtable（0x4B2FA50 段）
00653316  map 初始化（@ rdi+0x18：data/capacity=0x20/count/watermark）
006533C2  [rdi+0x40] = 0xFFFFFF
006533CD  call 0x7CB120(&mgr+0x40)      ; ★ 全局句柄池分配管理器 id（无 11 限制）
006533DC  rcx = &{id}; rdx = &params32
006533E1  call 0x653850                 ; ★ 把 32B 参数注册进存储 A（H+0xE8）
```

- `0x7CB120` 的调用者共 5 处：管理器 ctor、`0x17D47B0`（引擎建 11 个）、
  `0x6530A0`（批量建实体）、`0x4DE400`（通用高亮工厂）、`0x7A54C0`
  ⇒ 它就是**通用句柄分配器**，谁都可以拿 id。
- `0x653850(rcx=&id, rdx=&params32)`：`edi = id & 0xFFFFFF` →
  存储 A 的实体表查/建 → `0x2936540` 分槽 → `[存储A的数据 + 槽*32] = params32`。
- **参数块 32 字节布局**（`0x17D48A0` 段反汇编，逐字段）：
  ```
  +0x00  dword  基色（= 块 +0x80；★ 真正画出来的颜色）
  +0x04  dword  0
  +0x08  dword  脉冲色（High/Low 按相位插值一次的结果）
  +0x0C  float  块 +0x60 的原样透传
  +0x10  float  引擎全局
  +0x14  float  引擎全局
  +0x18  float  引擎全局（以上三个由 GMST/设置驱动）
  +0x1C  dword  0
  ```

### 2.4 挂载路径：引擎自己的 3D 图 visitor（我们照抄）

引擎 `Set(0x17D52B0)` → `0x17D4CD0` 里挂引用那一段（`0x17D4DD6` 起）：

```
017D4DF6  [rsp+0x40] = manager            ┐ data = {manager, manager->0x40}
017D4DFB  [rsp+0x48] = manager->0x40      ┘
017D4DFF  lea rax, [rip + 0x335ac0a]      ; vtable = 0x4B2FA10
017D4E06  [rsp+0x50] = rax
017D4E0B  rax = &[rsp+0x40]
017D4E10  [rsp+0x58] = rax                ; visitor = {vtable, &data}
017D4E18  rcx = &[rsp+0x50]
017D4E1D  call 0x24181E0                  ; 递归遍历整棵 3D 图
```

回调（vtable `0x4B2FA10` 的 +0x08/+0x10 = `0x653FC0 = add rcx,8; jmp 0x653DD0`）：

```
00653DD0  obj = node->vtbl[0x50](node)    ; 3D 节点 → 宿主对象
00653DF3  id  = [obj + 0x1F0]             ; ★ 渲染 id（挂/摘都用它，不是 FormID）
00653E33  eax = [data + 8] = manager id
00653E48  call 0x653A50(&id, &data+8)     ; ★ 存储 B：ref_id → manager_id
00653E67  call 0x3C7960(map, &key, ...)   ; ★ 管理器内嵌哈希表插入 id
00653E7D  [map.data + idx*12] = id
```

**摘除路径**（vtable `0x4B2F9F0`，`0x653F60`）：

```
00653F69  rdi = rcx                        ; rcx = &visitor
00653F87  rax = [rdi + 8]                  ; visitor[1] = data
00653F8F  rcx = [rax]                      ; ★ data 指向"存放管理器指针的内存"
00653F92  rcx += 0x18                      ; 管理器内嵌哈希表
00653F96  call 0x6535B0(Remove) → ok ⇒ call 0x653040(Deactivate)
```

> ★ **两个 visitor 的 data 语义不同**（v2.3 起代码里就是这么用的，本轮算彻底坐实）：
> - 挂上（`0x4B2FA10`）：data → `{manager指针, manager id}`（值本身）
> - 摘除（`0x4B2F9F0`）：data → **&manager指针**（先解引用一次才是管理器）

**"激活"就是写存储 B**（`0x653A50`），**"注销"就是清存储 B**（`0x653040` → `0x653920`）：

```
00653040  Deactivate(id)：
00653935  rbx = [[0x59751E8] + 0xF0]      ; ★ 操作的是存储 B
00653954  slot = [rbx+0x2C8][id]          ; 没有槽 ⇒ 直接返回
00653A09  [rbx+0x2C8][id] = 0             ; 清槽
```

⇒ 渲染层的完整闭环：**存储 B 有槽（= 挂载）→ 渲染遍历实体表 →
按 manager_id 到存储 A 取 32B 参数 → 画**。

### 2.5 引擎的 11 个限制只在①②层（列全）

| 位置 | 限制 | 自建通道受影响？ |
| --- | --- | --- |
| `0x17D4CD0` 开头 | `cmp ebp, 0xB; jae ret`（state < 11） | ❌ 不经这条路 |
| `0x17D47B0` | 建表循环 11 次（`mov r12d, 0xB`） | ❌ 不在数组里 |
| `0x17D4B30` | 销毁 11 个管理器 + 清状态表 | ❌ 管理器不在数组里，ref 不在状态表里 |
| `0x159ED90` | 引擎评估只写 0..10 | ❌ 我们不参与引擎评估 |
| 配色块 `0x5919A88` | 只有 11 块 | ❌ 我们用自己的 32B 参数 |

## 三、自建通道方案（v5.0 实现）

### 3.1 通道 = "一个自建 HighlightManager + 一份 32B 参数"

```
通道数 = 12 个类别 + 1（植物已扫描 = 绿）= 13
（每类别一个独立通道 ⇒ 颜色互不干扰、不再需要"并组 / 让位"）

struct ChannelSlot {
    void*         mgr   = nullptr;   // 自建 HighlightManager（插件静态内存，0x48B）
    std::uint32_t mgrId = 0xFFFFFF;  // 全局句柄 id（= mgr+0x40）
    bool          ready = false;
};
```

**管理器对象内存 = 插件 .data 里的静态数组**（0x48 × 13 = 936 字节）：
- 引擎只在 ctor / 挂载 / 摘除时写对象内部（全部 ≤ 0x48 字节）；
- 引擎的销毁路径（`0x17D4B30`）只遍历它的 11 个数组槽 ⇒ 永远碰不到我们；
- 我们不销毁 ⇒ 不需要引擎的 operator new/delete 配对。

### 3.2 创建流程（懒创建，模板就绪后一次建满）

```
EnsureChannels()：
  ① 引擎管理器不存在 ⇒ 调一次 g_outlineEnsure(nullptr)（幂等）后重试
  ② 读模板：mgrs[0] → id → H+0xE8 → idTab[id] → 数据数组 + 槽*32 → 32 字节
     （逐段 IsReadable + 形状校验；失败重试，超限则判定"通道不可用"）
  ③ 13 个通道各：模板参数 + 覆盖颜色 → 静态内存上 call 0x6532F0(mem, &params)
  ④ 记录 mgr / mgrId，打日志
```

**为什么要模板**：32B 里除了两个颜色，还有 4 个 float（描边宽度/相位/系数类），
它们由引擎按当前设置算好 ⇒ 直接复制引擎 state 0 的参数，保证描边粗细/观感与原版一致。

**颜色写入**（与旧路径同语义）：

| 字段 | 值 |
| --- | --- |
| `+0x00` 基色 | `NoFill=1`（默认）：`0x00RRGGBB`（不填充，物品材质透出）<br>`NoFill=0`：`0xAARRGGBB`（alpha 取 `AlphaXxx`，0 则补 0xFF） |
| `+0x08` 脉冲色 | `AlphaXxx != 0`：`(alpha<<24)│RGB`；否则保留模板 alpha + 我们的 RGB |

### 3.3 挂载 / 摘除（不写状态表）

```cpp
// 挂上（复刻 0x17D4CD0 的 visitor2）
struct MountData    { void* mgr; std::uint32_t id; std::uint32_t pad; };
struct MountVisitor { void* vtbl;  void* data; };      // vtbl = 0x4B2FA10
MountData d{ ch.mgr, ch.mgrId, 0 };
MountVisitor v{ 0x4B2FA10, &d };
g_outlineVisit(&v, root);      // 0x24181E0，引擎自己递归

// 摘除（复刻 0x17D4CD0 开头那次 visitor1）
struct UnmountVisitor { void* vtbl; void* mgrSlot; };  // vtbl = 0x4B2F9F0
UnmountVisitor u{ 0x4B2F9F0, &ch.mgr };   // *mgrSlot = 管理器指针
g_outlineVisit(&u, root);
```

- **状态表一个字节都不动**（不调 LookupOrAdd / Set）。
- 账本（`g_state.outlined`）里记 `channel`（替代旧路径的 `state` 做比较/摘除）。

### 3.4 与现有机制的相处

| 机制 | 通道模式下 |
| --- | --- |
| `ApplyColorOverrides`（写引擎配色块） | **跳过**（模板已含引擎原值，颜色只进我们参数） |
| `EnsureManagerFor(state)` / 管理器存在性检查 | 挂载不需要（只有"模板标定"需要引擎管理器） |
| 引擎开关扫描仪（`0x17D4B30` 销毁 11 个） | 不碰我们 ⇒ **不再有"高亮全灭"**；但原版扫描过的重叠目标会被原版写存储 B（变原版色），放下后照旧走 v3.2 自愈重挂 |
| `YieldTargetsWhileScanning`（举镜让位） | 保留（植物类让位 = 不主动摘，避免摘掉原版刚挂的） |
| 活人 NPC / 星球目标原版色 | **完全不受影响**（不覆盖任何引擎颜色） |
| `ChannelMode=0` | 完整旧路径（v4.33 行为），一行 INI 回退 |
| 通道创建失败（模板读不到） | **自动回退旧路径**（`g_channelsFailed`），打 WARN |

### 3.5 收益总结

1. **类别 → 颜色彻底自由**：13 通道，想改哪个改哪个（"并组"不再是限制，仅保留为用户偏好）。
2. **零引擎污染**：原版扫描仪 / NPC / 星球目标颜色 100% 原版；引擎配色块一个字节不写。
3. **不再"借槽位"**：state 0/1/4/5/7/8 的"归还"史结束；不再需要撞色 WARN。
4. **免于引擎清表**：自建管理器不在 `g_outlineManagers` 里，`0x17D4B30` 不销毁它。
5. **为"每物品独立颜色"留门**：存储 A 的参数是 per-manager 的、存储 B 是 per-ref 的 ⇒
   将来想给单个物品专属颜色，只需给它建一个专属通道（id 廉价、动态）。

## 四、风险与未验证点（如实记录）

| # | 风险 | 评估 | 失败表现 / 兜底 |
| --- | --- | --- | --- |
| R1 | **渲染收集是否只认状态表/管理器数组**（若渲染每帧还要求"id 在某个管理器哈希表里"—— 我们满足：挂载照样插了管理器哈希表） | 低（渲染闭环证据见 §2.4；挂载复刻了引擎全部动作） | 若描边不出现 ⇒ `ChannelMode=0` 回退；再挖渲染 pass |
| R2 | 参数块 `+0x08` 脉冲色被渲染侧按"动画"重算（覆盖我们的写入） | 低（引擎自己也是"创建/刷新时算一次"存进去） | 颜色变回模板色 ⇒ 每轮重调 `0x653850` 刷新参数（改动小） |
| R3 | 静态内存里的管理器被引擎某条路径误销毁 | 极低（引擎只遍历自己的数组） | 崩溃报告 + 改回引擎分配器（`0x22C7AD0` / `0x5E603C0` 全局已定位） |
| R4 | 与原版扫描仪同时挂同一个 ref（存储 B 互相覆盖） | **预期行为**（与现状同） | 放下扫描仪后自愈重挂；通道模式下不再有"状态被改"的额外污染 |
| R5 | 摘除时 `Deactivate` 把"仅原版挂着"的 ref 从渲染侧注销 | 低（`Remove` 要先在我们的管理器哈希表里命中） | 原版下轮评估会自动重挂 |

## 七、可复用经验（本轮新增）

1. **"谁消费"决定"谁重要"**：三个版本的"11 个限制"焦虑，本质是没分清
   **引擎的记账层**（状态表 / 管理器数组）与**渲染的消费层**（两张按 id 索引的存储）。
   消费层是动态容器 ⇒ 限制只是"引擎自己不用"而已。
2. **判断"限制"要看反汇编里的比较指令**（`cmp ebp,0xB`、`mov r12d,0xB`），
   而不是看"引擎只用了 11 个"这个现象。
3. **通用句柄池（`0x7CB120`）是"自建引擎对象"的钥匙**：凡是拿到句柄的对象
   （管理器、实体），都可以由外部创建并接入引擎的渲染/查询闭环。
4. **visitor 的 data 约定两个方向都要对**：挂上要 `{mgr,id}`、摘除要 `&mgr` ——
   差一层解引用就是"永远删不掉"或崩溃（v2.2 的历史教训在此再次被解释）。
