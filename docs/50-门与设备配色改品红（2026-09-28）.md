## 零、一句话结论

`颜色分类.md` 里的「**白**：门、电脑、按钮等所有可互动物品」整组换色 ——
**白 #FFFFFF → 品红 #FF3BD4**；只改颜色值：通道数 14、槽位分配（门 / 设备 = 6）、
其余类别（红 / 橙 / 黄 / 紫 / 绿 / 蓝 / 原版青 ↔ 绿）一字未动。

## 一、选色论证（为什么是品红）

把当时的全部在用颜色摆到色相环上（含引擎保留的原版色）：

| 在用颜色 | 色相 |
| --- | --- |
| 红 #FF2E2E（武器 / 投掷物 / 太空服 / 背包 / 头盔 / 服饰） | 0° |
| 橙 #FF9500（容器 / 尸体） | 35° |
| 黄 #FFE100（开锁器 / 信用币） | 53° |
| 原版绿 #27C684（弹药 / 救援） | 155° |
| 原版青 #72E8FF（星球目标·未扫描的脉冲） | 190° |
| 原版青 #3EADF2 / 淡蓝白 #B3C1EF（NPC） | 203° / 226° |
| 蓝 #1F8EE2（杂项，原生不变） | 206° |
| 紫 #B36BFF（笔记 / 资源） | 269° |

⇒ 环上唯一的大空档是 **269° → 360°（共 91°）**，其正中的 ~313°（= 品红）
与最近的两个邻居（紫 / 红）各拉开 **~44° / ~47°**，离其余颜色全部 **≥82°**。

另一个候选「青柠 ~100°-104°」（53° → 155° 那个空档）被否：
观感像「另一种绿」，与黄 / 原版绿 / 植被满满的场景放一起时对比不足；
且暖色区已有橙（35°）和黄（53°）挤在一起，再塞偏绿的黄会让色环更密。

★ 品红不是新造色：v4.19~v4.30 本项目就用过 **#FF3BD4**（当时给「服饰」，
见 `docs/18`）—— 实机跑过、从没出现过「和紫色分不清」的反馈。

顺带收益：白色无色相，在雪地 / 白墙 / 飞船内舱等亮背景上对比弱、也容易被当成
「没上色的默认轮廓」；举着原版扫描仪时 NPC 的「淡蓝白 #B3C1EF」与门白也偏近。
品红全部避开。

## 三、验收判据（下一次进游戏）

1. 启动日志：加载行出现「**第二轮配色修订**」字样（= 跑的是新 DLL）；
   `config: 配色分组(2026-09-28)` 行里「门 / 电脑 / 按钮」=「**品红 #FF3BD4**」。
2. `channel: … colors: … door=#FF3BD4 … device=#FF3BD4 …`；统计行 `通道=14/14`。
3. ★ 肉眼（核心）：门 / 电脑 / 终端 / 按钮 = **品红**；
   与紫（笔记 / 资源）同屏时一眼分得开；
   其余颜色（红 / 橙 / 黄 / 绿 / 蓝 / 原版青 ↔ 绿）全部不回归。
4. 举着扫描仪 ⇒ NPC 青 / 星球目标青 ↔ 绿仍 100% 原版。
5. （可选）`ChannelMode=0` ⇒ 门 / 设备同为品红（共用 state 6），无撞色 WARN。

## 四、可复用经验

1. **需求文件（`颜色分类.md`）是活的**：分组定稿后仍会单点改色 ——
   改「某个颜色名」时先把它翻译成「哪几个类别 + 哪个槽位 / 通道」，
   再检查这个改动会连带影响谁（门 / 设备共槽 6 ⇒ 必然同色）。
2. **改色前把全部在用颜色摆到色相环上**（含引擎保留的原版色）——
   空档最大的位置就是区分度最高的位置；本次 91° 空档里的 313° 一击命中，
   不需要动任何别的类别（对比 v4.19 那轮整套重排的代价）。
3. **「实测过的颜色」优先于「纸面最优色」**：#FF3BD4 在 v4.19~v4.30 实机跑过，
   选它就是选一条已经验证过的路径（docs/18 的历史数据反过来成了资源）。
