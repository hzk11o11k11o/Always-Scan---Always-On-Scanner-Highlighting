## 零、一句话结论

`颜色分类.md` 定稿版把「**绿 = 弹药、救援、电脑、按钮等所有可互动物品**」——
即 **2.0.1 第一 / 二轮刚被并入「门」的设备（ACTI / TERM）退回 2.0 口径**：

| 项 | 第二轮回合（旧） | 本轮（定稿） |
| --- | --- | --- |
| `stateByCategory[kDevice]` / `kStateDef` | 6（与门共槽） | **4**（= 2.0） |
| `colorOverride[kDevice]` | `kColorUnset` | `kColorUnset`（不变） |
| `kChannelColorDef[kDevice]` | `0xFF3BD4` 品红 | **`0x27C684` 原版绿** |
| 门 `kDoor` | 6 + `0xFF3BD4` | 6 + `0xFF3BD4`（**不变**） |
| 其余类别（红 / 橙 / 紫 / 黄 / 蓝 / 原版青↔绿） | — | **一字未动** |

⇒ 观感：**设备 / 电脑 / 终端 / 按钮 = 原版绿**（与「弹药 / 救援」同色，= 2.0 的观感）；
**门 = 品红**；黄 = 开锁器 / 信用币不变。

## 三、验收判据（下一次进游戏）

1. 启动日志：加载行出现「**第三轮配色修订**」（= 跑的是新 DLL）；
   `config: state4_5 -> 「设备」= state 4、「弹药救援」= state 5，两者颜色**不覆盖**`；
   `config: 配色分组(2026-09-28 第三轮)` 行里「电脑 / 按钮等可互动物品」= state 4
   （原版绿 #27C684）、「门」= state 6（品红 #FF3BD4）。
2. `channel: … colors: … device=#27C684 … door=#FF3BD4 …`；统计行 `通道=14/14`。
3. ★ 肉眼（核心）：**电脑 / 终端 / 按钮 / 开关 = 原版绿**（与弹药 / 救援同色，
   和 2.0 一致）；**门 = 品红**（与紫同屏一眼分得开）；
   其余颜色（红 / 橙 / 黄 / 紫 / 蓝 / 原版青 ↔ 绿）全部不回归。
4. 举着扫描仪 ⇒ NPC 青 / 星球目标青 ↔ 绿仍 100% 原版。
5. （可选）`ChannelMode=0` ⇒ 设备 = state 4（不覆盖 = 原版绿）、门 = state 6 品红，
   两者不再同色；无撞色 WARN（设备不参与撞色检测 —— `kColorUnset` 被跳过）。

## 五、可复用经验

1. **「退回 X 版本」先查那版的实际值，而不是凭最新印象改**：设备在 2.0 =
   `state 4` + **通道色 `0x27C684`**（两条都要一起回退）—— 只改通道色会留下
   旧路径的 state 6（与门同色），二者必须一起动，否则「通道模式 = 绿、
   `ChannelMode=0` = 品红」两个模式讲两个故事。
2. **「需求文件里保留的项不要一起回退」**：用户一句「把除了门以外的可交互物件
   退回 2.0」听起来像「撤销 2.0.1」，但需求文件明确保留「黄 = 开锁器 / 信用币」——
   **以需求文件为准，用概括句反问自己「它到底指哪一组」**（这里指 2.0.1 第一轮
   并进门的那一组 = 设备，不含黄组）。
3. **INI 里旧键值会覆盖 DLL 新默认**：`StateDevice=6` 已经在部署 INI 里 →
   只改 DLL 默认值**不会生效**。凡是改 `StateXxx` 默认值，都必须同步部署 INI
   （本轮按惯例换模板 + 保留 `LogMaxMB=10`，替换前先核对无用户自定义）。
4. **回退也要做「旧串消失」核对**：二进制里 `「门 / 电脑 / 按钮」= {}` ×0 是
   这一轮真正的回归判据（只核对新串出现不够 —— 老文案可能还留在别的日志行里）。
