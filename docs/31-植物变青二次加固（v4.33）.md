# 31 · 植物「低概率变回青色」二次加固（DLL v4.33.0 / 发布版 1.8.1）

> 建立：2026-09-26。触发：用户实测反馈（原文）——
>
> ```
> 之前说的，低概率出现已扫描过的植物还是青色，但只需要开一遍扫描仪，
> 直接关闭，不用真的扫描，就会变回已扫描的绿色的现象还在
> ```
>
> 上一轮（v4.31）的修复思路见 `docs/29`；本轮**从用户这一局的日志里拿到了完整复现证据**，
> 定位到 v4.31 修复的三个漏洞并全部补上。

一句话结论：v4.31 的「单向学习表」本身没错，但它

1. **每次「载入画面关闭」都被整表清空**（`ResetForNewScene`）——而实测日志里这个事件
   每几十秒就发生一次，清完重问引擎又大多答「未扫描」⇒ 换场景后整片植物变青；
2. **只活在内存里** ⇒ 每次重开游戏都要再「开一遍扫描仪」重新学；
3. 「重问失败沿用旧结论」的判据 `!chain.shapeOk` **对植物永远不成立**
   （植物 `produceIsMisc` 恰好把 `shapeOk` 置 true）⇒ 植物从未被保护过。

⇒ v4.33：学习表**跨场景保留 + 落盘**、沿用规则订正、未扫描缓存 TTL 30 s → 5 s、
判据未命中时「读一眼引擎状态表捡 4/5」。

### 1.4 「沿用」为什么对植物永远不生效（v4.31 的漏洞 ③）

v4.31 的代码：

```cpp
bool result = scanned;
if (!chain.shapeOk && hasPrev && prevScanned) {   // ← 植物永远进不来
    result = true;
    ++g_state.floraStickyKeeps;
}
```

而植物的 `QueryFloraResourceScanned` 在 `produceIsMisc`（产出物品直接是 MISC）
时**把 `shapeOk` 置 true**（docs/26 的设计：链「走通并判定 = 不适用」，不算失败）
⇒ `!chain.shapeOk` 对植物恒为 false ⇒ **植物从来没被沿用保护过**。

### 1.5 引擎答 1 → 答 2 的实证（「开一下扫描仪」的作用）

探针行（同一个 base，同一局）：

```
[22:36:16] flora scan: base=0x18547F … | 引擎状态=1 | 产出物品是 **MISC**（= 植物）… -> 已扫描=0 ⇒ 状态 7（青）
[22:36:24~37] 「引擎把 base=0x185479/0x185489/… 画成了绿色（outline state 4/5）」← 用户举扫描仪
[22:36:48] flora scan: base=0x18547F 记入单向学习表「已扫描」（引擎状态 GetOutlineState(ref)=2）
```

⇒ 同一个引用、同一局，**举过扫描仪之后 `GetOutlineState` 从答 1 变成答 2**。
「开一遍扫描仪、不用真的扫描」之所以有效，就是它让引擎给附近目标做了
「扫描状态登记 / 求值」，之后主判据才可靠（v4.26 起一直如此，只是之前没被记录下来）。

## 二、本轮逆向补充（供下一轮，结论标注为「疑似」）

## 六、可复用经验

1. **「日志里的时间序列」比任何单点证据都值钱**：本轮只把 `planet targets` 统计行按时间
   排开，故障窗口（3.5 分钟整片青色）、恢复时刻（举扫描仪）与「沿用=0」三个事实就同时
   现形了 —— **排查「偶发」问题的第一步应当是把同一条统计行按时间抽出来看**。
2. **「同一个 base 反复出现同一条日志」= 缓存 / 记忆被反复清空的铁证**：
   `记入单向学习表` 对同一 base 出现 5 次 ⇒ 不需要猜，直接去看 `reset (` 行。
3. **判据的「守卫条件」要用目标的实际数据形态验证**：v4.31 的「沿用」用
   `!chain.shapeOk` 表达「没有权威答案」，而植物的 `shapeOk` 恰好 = true
   ⇒ 条件写反了语义（v4.26 自己设计的「不适用 = shapeOk true」没有被沿用逻辑沿用）。
   **新增判据规则时，要把每一类目标（植物 / 矿脉）分别代入一遍**。
4. **「单向事实」的缓存策略**：已扫描 = 只增不减 ⇒ 记忆应当**跨场景、跨会话**保留，
   清空才是 bug 来源。凡「单向事实」都值得落盘（本 MOD 的 `flora-learn.txt`）。
5. **落盘文件的「读回 + 追加」比「定期全量重写」简单且安全**：去重交给内存表，
   文件只追加；解析只认一行一个 id、`#` 注释。**注意 usvfs**：MO2 下新文件会落
   `overwrite`，所以部署 / 打包脚本要**预置空文件**（日志、学习表同理）。
6. **「优先淘汰诊断性数据」**：容量保护不要整体 `clear()` —— 分门别类地淘汰
   （先扔只见过青的 false 条目），关键数据（已确认的绿）才保得住。
