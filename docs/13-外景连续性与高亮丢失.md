# 13 · 外景连续性（跨 cell 边界全灭）与「高亮丢失」自愈（v4.7）

> 本文件记录 2026-09-19 用户报告的两条现象（「星球表面原本高亮的物体突然不亮」、
> 「行走时不触发扫描」）的**取证、定性、修复与验收判据**。
> 涉及的代码全部在 `plugin/src/AlwaysScan.cpp`（DLL 内部），ESM / Papyrus 未动。

---

## 1. 用户反馈（原话）

> 我似乎观察到了一些"高亮丢失"现象，主要发生在星球表面地图，原本已经高亮的物体
> 突然不亮了，这是第一点，第二点是高亮扫描似乎只发生在玩家不动的时候，
> 行走的过程中不会触发扫描，检查一下这两个问题是不是真的存在

要求是「**检查这两个问题是不是真的存在**」，所以本轮先取证、再改。

---

## 2. 取证（全部来自当次游戏日志 + 离线查 ESM，没有猜）

日志：`%USERPROFILE%\Documents\My Games\Starfield\SFSE\Logs\SAS_AlwaysScan.log`
（本次会话 06:54:55 载入 v4.6.0 → 07:21:07 结束，共 1508 秒 / 6900 次扫描 / 284 条统计行）。

### 2.1 先把「那是哪两个 cell」查清楚（离线 `Starfield.esm`）

日志里玩家在地表阶段反复出现在两个 cell：

| FormID | EDID | CELL DATA | XCLC | 结论 |
| --- | --- | --- | --- | --- |
| `0032588C` | `LC003KreetBaseRoof` | `0x0002` | grid=(2,1) | **外景 cell** |
| `0032588B` | （无 EDID，程序生成） | `0x0002` | grid=(2,0) | **外景 cell**（与上一条相邻） |
| `000627C4` | `KreetBase01` | `0x0005`（含 0x01） | 无 | 内景 cell（进基地那一侧） |

⇒ 地表阶段（07:13 之后）玩家在 **Kreet 表面的两个相邻外景 cell 之间来回走**。
（用一次性脚本 `out/cellinfo.py` 读的，脚本不入库。）

### 2.2 现象一（高亮丢失）在日志里的直接证据

```
[07:17:56.590] reset (cell changed) outline=111
[07:17:56.590] native outline: 111 个已挂高亮转入「待摘」（deadline=+2500ms，…）
[07:17:59.075] scan#6079 cell=0032588B refs=1653 cand=27 sel=27 outline=138 …
[07:18:11.337] reset (cell changed) outline=21
[07:18:14.452] scan#6143 cell=0032588C refs=3857 cand=111 sel=111 outline=111 …
```

整个会话里 `reset` 事件 23 次，其中 **15 次是 `cell changed`**，且集中在两个外景 cell
之间（每 10~20 秒一次）。每一次的实际效果是：

1. **已经亮着的全部高亮被标成「待摘」**（`ResetForNewScene` → `MarkAllForRemoval`），
   之后按每轮 64 条的预算真的摘掉 ⇒ 屏幕上「原本亮着的突然不亮」；
2. **静置 2 秒完全不扫描**（`settleUntilMs`）；
3. 重新扫描时**只把新 cell 自己的引用当候选** —— 代码里那一句
   `if (ref->parentCell != cell) { ++skipParentCell; continue; }` 会把
   边界对面的引用整片挡掉 ⇒ 站在 `…8B` 时 `sel` 只有 20~27 个，而隔壁 `…8C`
   那 100 多个还在眼前的引用**一个都不亮**（日志里 `sel` 在 111 ↔ 20 之间反复跳）。

⇒ **现象一是真的**，而且根因不是「渲染丢了」，是**MOD 自己的账本被整批作废**。

### 2.3 现象二（行走时不扫描）在日志里的直接证据

先看总量：**1508 秒 / 6900 次扫描 = 4.57 次/秒**（节流是 200ms ⇒ 理论 5 次/秒），
也就是整体只丢了 8.6%。所以**「完全没扫描」并不成立**，
但有两处结构性停顿是实打实的（`out/log_gaps.py` / `out/log_skip_rate.py`）：

| 起 | 止 | 间隔 | 期间 scan 数 | 理论应有 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 07:00:05.22 | 07:00:49.04 | **43.8 s** | 18 | 219 | 内景 `KreetBase01`，`load` 计数**没变**、`rej=0`、refs 稳定 —— 详见 2.4 |
| 07:13:37.31 | 07:13:54.01 | 16.7 s | 21 | 84 | 正好是内景 → 外景的切换（`load` 5→6） |
| 07:17~07:19 段（地表） | | 每次 5~8 s | 15~25 | 25 | 每次 gap 里都夹着 1~3 条 `cell changed` |

地表那一段的「跳过率」按 30 秒分桶：**12%~26%**（其他时段只有 1~4%），
跳过几乎全部发生在**跨 cell 边界的前后** —— 也就是**走动的时候**。
静止不动时（不跨边界）扫描是满速的。

⇒ **现象二也是真的，但准确的说法是**：不是「行走时不扫描」，而是
**「走动会不断触发换 cell，而每次换 cell 会带来 2 秒不扫描 + 整批熄灭」**；
另外还有一条隐性成本见 2.5。

### 2.4 那个 43.8 秒的空档（顺带查出来的第三件事）

`07:00:05.221`（scan#1194）→ `07:00:49.038`（scan#1212）之间：
`load` 计数没变（= 没有载入画面由开变关）、`rej=0`、`refs` 稳定、功能一直 `on=1`。
按 `stable_rounds` / 命中时机反推，**18 次扫描全部发生在空档的前 3.6 秒内**，
中间约 39 秒**一次扫描都没有**，而且**一条日志都没有**：

- 若是被早退挡住，`refsRejected`（当时唯一带计数的早退）会涨 —— 它没涨；
- 若是载入画面，`load` 计数会 +1 —— 它没有；
- 剩下的可能只有「**`Tick`（引擎每帧调用的主循环任务）根本没有被调用**」
  或「refs 数组长度在反复微变、被稳定性判据一直挡住」两种，
  而当次日志**没有任何数据能区分它们**。

⇒ 本轮为此加了专门的诊断（见 §3.4）：`tick gap …ms` 的 WARN 行 +
`tick/场景` 统计行的 `gaps / maxGap / 合计`。**下次实测就能一次定性。**

### 2.5 隐性成本：引用数「轻微变化」会打断扫描

旧判据（v4.6）：

```cpp
if (arr.size != g_state.lastRefsSize || usedOff != g_state.cellRefsOff) {
    g_state.lastRefsSize = arr.size; g_state.cellRefsOff = usedOff;
    g_state.stableRounds = 0;  return;          // 本轮不扫
}
if (++g_state.stableRounds < kRefsStableRounds) return;   // 还要再等 1 轮
```

⇒ **引用数只要和上一轮差 1 个，就要连跳约 3 轮（≈600ms）**。
外景 / 城市里走动时加载线程一直在流式增删引用，这条判据会被反复触发
（地表阶段日志里 `refs` 在 1652↔1654 / 3856↔3863 之间抖动）。
这是「走动时扫描变稀」的第二个来源，也是本轮一起改掉的。

## 3. v4.7 修法（四条，全部在 DLL 内）

### 3.1 ★ 外景「连续过渡」：跨 cell 边界不再整批熄灭

**判据（不需要知道 cell 是不是外景、也不碰任何新偏移）**：

> 上一个 cell 还在**「近期 cell 环」**里 ⇒ 世界没有被重开 ⇒ 走「连续过渡」。

- 环只在「玩家真正待过的 cell」里攒（Rescan 每轮把当前 cell 放进去）；
- 载入画面关闭（读档 / 进门 / 快速旅行）时**清空环**，于是那些切换仍然走原来的
  「换场景」路径（整批待摘 + 2 秒静置）；
- 连续过渡做的事：**不整批摘、不清账本**，只静置 `SettleOnCellCrossMs`（默认 300ms），
  谁真的离开半径就按 `UnhighlightGraceMs`（1.5 秒）自然淘汰。

### 3.2 ★ 近期 cell 环：边界对面的引用也参与扫描

`kRingCellMax = 8` 个最近待过的 cell，每轮和当前 cell 一起遍历：

| 项 | 说明 |
| --- | --- |
| 进环 | 每轮扫描时「当前 cell」进环（= 玩家真的在这里） |
| 校验 | 环里的 cell 每轮都要过 `IsReadable` + **形状校验** + **自洽性**：抽查到的引用必须满足 `ref->parentCell == 该 cell`（垃圾数组过不了这一条） |
| 淘汰 | 连续 `kRingCellMissMax = 10` 轮校验不过（= 该 cell 已卸载）⇒ 踢出；环满 / 引用总数超过 `kRingRefsCap = 60000` ⇒ 淘汰最旧的 |
| 候选过滤 | 每个 cell 只认**它自己**的引用（`ref->parentCell == sc.cell`），这条同时把「读到别的 cell 的引用」挡在外面 |
| 成本 | 遍历量上限 = 当前 cell + 环内 cell 的引用数（≤ 6 万）；实测单轮 `loop` 仍是 1~2ms 量级 |

### 3.3 ★ 3D 复检：引擎侧描边被静默丢掉之后自动重挂

**这是「高亮丢失」的第二条根因**（与 §2.2 的账本作废是两件事）：

- 引擎侧的描边是**按 3D 图节点**登记在 `HighlightManager` 里的
  （v2.3 实证：摘除用的 `0x653F60` 那个 id 取自 **3D 图叶子节点**，不是 FormID）；
- 外景走动时引擎会**流式卸载 / 重建 3D**（LOD ↔ 真模型互换就是最典型的），
  重建之后管理器里那条登记**就没了**，而 MOD 的账本还记着「挂着」，
  默认 `ReassertMs=0` 下**永远不会再 Set 一次** ⇒ 那个物体从此不亮，
  直到它掉出半径再进来；
- 与 v3.2 修的「用完原版扫描仪后全灭」是**同一类问题**（账本与引擎侧脱节），
  区别是那次整表被销毁（有「管理器数量下跌」这条判据），这次是**单条丢失**
  （管理器数量不变，任何全局判据都看不到）。

做法：`OutlineEntry` 里记下挂的时候的 3D 根地址（**只比较、绝不解引用**），
每轮按游标复检 `Verify3DPerScan`（默认 32）个已挂目标；发现地址变了
（重建过 / 第一次加载出来）就**重新 Set 一次**（走 `MaxOutlineOpsPerScan` 预算）。

- 3D 现在是 null 就不动（看不见的东西本来没描边，等它加载出来再挂）；
- 成本：每轮 ≤ 32 次「取 3D」，默认 160 次/秒，与每轮 5~40 条 Set/Remove 相比可忽略；
- 证据：日志 `native outline: 3D 重建（ref=…）-> 重挂一次`，
  以及统计行 `3D复检: probes=… reassert=…`（后者涨 = 这条自愈真的在干活）。

### 3.4 流式变化容差 + 全套「跳过原因」诊断

| 项 | 内容 |
| --- | --- |
| 引用数判据分档 | 变化量 ≤ `StreamJumpTolerance`（默认 256）⇒ 只记一笔 `流式变化=` 并**照常扫描**；超过（换场景的批量填充）⇒ 仍等稳定轮数 |
| Tick 间隔 | 间隔 > 1500ms ⇒ 记一笔 + 打一行 `WARN tick gap …ms（… loading=… monocle=… on=… cell=…）`。**这是区分「Tick 没被调用」与「被早退挡住」的唯一手段** |
| 跳过计数 | 统计行 `skip (窗口内): off / throttle / loading / noplayer / nocell / settle / shape / unstable / warmup` |
| 场景/环计数 | 统计行 `tick/场景: … cell: changes=N 连续过渡=M \| 环: cell=N skipped=N \| 流式变化=N \| 3D复检: probes=… reassert=… \| move=X.Xm` |
| 移动距离 | 每轮累加玩家位移，统计行 `move=X.Xm` —— 把「行走」和上面的数**对起来看** |
| 主统计行 | 新增 `cells=`（本轮扫了几个 cell）与 `move=`；`rej=` 移到 `skip` 行的 `shape=`（口径不变，只是改名并改成窗口内计数） |

### 3.5 新增 INI 键（4 个，都能回退，不用换 DLL）

| 键 | 默认 | 作用 |
| --- | --- | --- |
| `ExteriorContinuous` | 1 | 0 = 退回 v4.6（每次跨边界全灭），仅用于对照 |
| `SettleOnCellCrossMs` | 300 | 连续过渡的静置时间（0 = 不静置） |
| `StreamJumpTolerance` | 256 | 引用数轻微变化的容差（0 = 退回旧判据） |
| `Verify3DPerScan` | 32 | 每轮 3D 复检的条数（0 = 关掉这条自愈） |

## 4. 验收判据（下次实测逐条对）

1. **星球表面跨 cell 边界走动**：日志出现
   `cell cross (连续过渡): 账本保留 N 个已挂目标，静置 300ms，环=K 个 cell`，
   统计行 `cell: changes` 与 `连续过渡` **同步增长**（连续过渡应占绝大多数）；
   屏幕上**不再出现「整片突然变暗」**。
2. 站在边界上时，**边界对面**的东西也亮：主统计行的 `cells=` ≥ 2、
   `sel` 不再在两个 cell 的引用数之间大幅跳（本次实测里是 111 ↔ 20）。
3. 若再有「亮着亮着突然不亮」，先看统计行 `3D复检: reassert=` 是否在涨：
   - **在涨** ⇒ 就是 §3.3 那条（引擎侧 3D 重建丢描边），现在会自动重挂；
   - **不涨** ⇒ 把那一行 + `native outline: 3D 重建…` 附近的日志发出来。
4. 「行走时不扫描」：看 `skip` 行 —— `unstable`（引用数突变）、`warmup`（等稳定轮数）
   应该显著下降；`tick/场景` 行的 `gaps / maxGap` 若还有大值，
   说明是**引擎没调用主循环任务**（暂停 / 载入 / 主线程忙），与 MOD 无关，
   那种情况在日志里会有 `WARN tick gap …ms` 直接写明。
5. **不回归**：F8 开关照旧（关 = 立刻全灭）、用完原版扫描仪后高亮自己回来
   （`resync` +1）、读档 / 进门 / 快速旅行不崩不卡（`timing2: sync` 无大值）。

## 5. 已知边界（本轮**没有**做、也不打算假装做到）

1. **只扫「玩家待过」的 cell**：环里只有玩家自己走过的 cell。站在一个**从没进去过**
   的邻 cell 边界上往里看，那边的引用仍然不会亮（要彻底解决需要枚举世界网格的
   邻 cell，那是新的偏移逆向工作，风险与本轮收益不成比例）。
2. **内景跨门仍然整批摘**（那是有意的：进门就是换世界，且都经过载入画面）。
3. 那条 43.8 秒空档**本轮没有定论**，只加了诊断。下次日志的 `tick gap` WARN 会给答案。
