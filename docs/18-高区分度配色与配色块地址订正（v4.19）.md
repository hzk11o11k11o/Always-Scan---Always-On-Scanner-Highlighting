# 18 · 高区分度配色 + 配色块地址订正（DLL v4.19.0 / 发布版 1.7.1）

> 建立：2026-09-25。触发：用户实测报告（附截图）——
>
> ```
> 现在笔记的颜色生效了，但是武器和太空服还是一样的颜色
> ```
>
> 紧接着的用户要求（本轮的设计依据）：
>
> ```
> 不同类别物品颜色区分度要高，不要弄太相近的颜色，肉眼很难分辨
> ```

本轮做两件事：**① 修掉「配色覆盖写错表」这个硬 bug；② 把默认色整套换成高区分度调色板**
（不再依赖引擎那 11 个状态的「原生色」）。

---

## 一、先把旧结论订正掉：**原生色本身就是不可用的**

`docs/16 §2.1` 那张「11 个状态原生配色」表（日志直读）里，前三行是：

| state | 名字 | ref 基色 |
| --- | --- | --- |
| 0 | Generic | `#3EADF2` 青 (62,173,242) |
| 1 | Scanned | `#B3C1EF` 淡蓝白 (179,193,239) |
| 2 | FullyScanned | `#1F8EE2` 蓝 (31,142,226) |
| 3 | Tracked | `#1F8EE2` 蓝（**与 2 完全相同**） |

⇒ 0/1/2/3 **全是蓝色系**。v4.17 把「武器 / 服饰 / 杂项」分别放在 0 / 1 / 2 上，
用户看到的必然是「一堆蓝，分不出谁是谁」——这不是没生效，是**挑的色本身太近**。

**用户截图给了数字级证据**（本轮新增工具 `tools/img_outline_color.py`，按色相分桶 + 区域取最饱和像素）：

```
武器（左侧长条物体）  最饱和像素 #68E0F9 / #6FD8F8   hue 190~194   （青）
太空服（中间箱子）    最饱和像素 #2292A0 / #3D99A4   hue 185~187   （青绿）
```

两个目标的描边色相只差 3~9°，而且**都没有出现 state 1 的淡蓝白**（全图 `#B3C1EF`
那种「R 高、B 更高」的像素只出现在 HUD / 物品卡的白字上）⇒ 单看截图无法区分
「太空服到底挂在哪个状态」，但**结论已经够用：靠原生色做不到用户要的区分度**。

## 二、真正的硬 bug：**配色覆盖一直在写「错的表」**

### 2.1 反汇编 `0x17D47B0`（建/刷新管理器）的循环体

```
017D4883  lea r14, [rip + 0x414525e]      ; r14 = 0x5919AE8  ← 块基址 + 0x60
017D48A0  <循环开始>
017D48EB  mov eax, [r14 + 0x20]           ; ★ 块 +0x80 = 描边基色 → 参数块 +0x00
017D48F3  vmovss xmm0, [r14]              ; 块 +0x60（float，原样透传）
017D48FE  vmovd xmm1, [r14 - 0x60]        ; 块 +0x00 = 脉冲 High 色
017D492D  vmovd xmm0, [r14 - 0x40]        ; 块 +0x20 = 脉冲 Low 色
017D4961  vdivss xmm6, xmm0, [r14 - 0x20] ; 块 +0x40 = float 插值除数
017D495C… 四个通道 lerp(High→Low) → clamp → ×255 → 打包成 dword → 参数块 +0x08
017D49FF  mov rcx, [rdi]                  ; managers[i]
017D4A05  jne 0x17D4AAC                   ; 已存在 ⇒ 走「已存在分支」
              （不存在）… call 0x6532F0    ; 分配 + 构造（参数块在 rdx）
017D4AAC  mov eax,[rcx+0x28]; cmp eax,[rcx+0x30]; je 0x17D4AD3   ; ★ 相等 ⇒ 跳过
017D4AB4  mov eax, [rcx + 0x40]           ; 管理器 ID
017D4ACE  call 0x653850                   ; 把参数块交给渲染侧
017D4AD3  add r14, 0xA0                   ; ★ 每轮 +0xA0
017D4AE2  sub r12, 1                      ; r12 = 0xB = 11 次（状态 0..10）
```

⇒ **块基址 = `0x5919A88`**（state k 的块 = 基址 + k×0xA0），字段：

| 偏移 | 内容 | 谁读 |
| --- | --- | --- |
| `+0x00` | 脉冲 High 色（dword `0xAARRGGBB`） | `0x17D47B0` |
| `+0x20` | 脉冲 Low 色 | `0x17D47B0` |
| `+0x40` | float 插值除数 | `0x17D47B0` |
| `+0x60` | float（原样透传） | `0x17D47B0` |
| `+0x80` | ★★ **描边基色** | `0x17D4CD0`（挂引用）+ 参数块 `+0x00` |

**而我们（v4.1 ~ v4.18）写的是 `0x591E088`** —— 它 = 块基址 + **112**×0xA0，
在镜像里是**另一片 float 常量区**（`0x44D471E0` = 1702.11f、`0x44AFB448` = 1405.63f …）。

⇒ 以前那两行「覆盖 XXX 的颜色」日志**全是假的**：RGB 被写进了无关的 float 常量，
既不会影响描边，还污染了那张表（因为一直保留 alpha 字节，才没把 float 写成 NaN）。

**唯一写对过的一处**：我们称作「ref 表」的 `0x5919B08` = 块基址 + k×0xA0 + **0x80** ——
正是**描边基色**。这解释了为什么 v4.18 只让「笔记变黄」成功（state 6 的基色被覆盖了），
而同一轮写的脉冲 High/Low 完全没有效果。

### 2.2 引擎交给渲染侧的 32 字节参数块（`0x653850`）

```
00653868  mov rax, [rip + 0x5321979]      ; rax = [RVA 0x59751E8] = 高亮宿主对象
0065387A  mov rsi, [rax + 0xe8]           ; rsi = 高亮管理器集合
00653894  mov rcx, [rsi + 0x2c8]          ; u32 数组：managerID → 槽号
006538BF  mov rax, [rsi + 0x3c8]          ; 槽数组：每槽 32 字节
006538C6  vmovups ymm0, [r15]             ; 参数块（0x17D47B0 造的）
006538CB  mov edx, [rbx + rcx]            ; 槽号 = idTab[id]
006538D0  shl rcx, 5                      ; ×32
006538D4  vmovups [rcx + rax], ymm0       ; ★ 写进渲染侧
```

参数块布局（`0x17D47B0` 里那段打包的落点）：

| 偏移 | 内容 |
| --- | --- |
| `+0x00` | **基色**（= 块 `+0x80`）← 画出来的颜色 |
| `+0x04` | 0 |
| `+0x08` | 脉冲色（High/Low 按相位插值） |
| `+0x0C` | float（= 块 `+0x60`） |
| `+0x10` | float（引擎常量） |

⇒ 于是有了**「颜色到底有没有送进渲染器」的直接证据来源**：按
`[0x59751E8] → +0xE8 → +0x2C8/+0x3C8` 读回来即可（v4.19 的 `renderer params[...]` 日志）。

## 三、v4.19 的改动（`plugin/src/AlwaysScan.cpp`）

| # | 改动 | 说明 |
| --- | --- | --- |
| ① | `kRvaOutlineMgrParams 0x591E088` → **`kRvaOutlineParams = 0x5919A88`**，并新增块内偏移常量 `kOffStatePulseHigh/Low/Divisor/Extra/BaseColor` | 订正写错表；`0x591E088` 在 DLL 里**不再出现**（二进制核对：0 处） |
| ② | `WriteColorOverrides` 改成**按状态归并**后写三处：`+0x00` High、`+0x20` Low、`+0x80` 基色（基色 alpha=0 补 0xFF） | 脉冲两端也改成我们的色 ⇒ 脉冲相位切到 Low 时不会闪回原生色；同一状态被两个类别共用只写一次 |
| ③ | 新增**撞色 WARN**：两个类别共用同一 state 却给了不同颜色时报警并保留先出现的 | 共享 state 的两组（容器+尸体 = 9、弹药救援+植物 = 5）必须同色 |

| ⑥ | **默认配色整套替换**（见下 §四），`RendererProbe` 新键写进发布 INI | 不再依赖原生状态色 |
| ⑦ | 版本：DLL `4.18.0` → **`4.19.0`**；MO2 / N 网公开版 `1.7` → **`1.7.1`** | `tools/build-sas.ps1` 的 `meta.ini` 同步 |

## 四、新调色板（默认值全在 DLL 里，INI 只用于「想改才写」）

| 类别 | state | 颜色 | 色相 | 依据 |
| --- | --- | --- | --- | --- |
| 武器、投掷物 | 0 | **红 `#FF2E2E`** | 0° | 与其它五个物品组拉开最大 |
| 太空服 / 背包 / 头盔 / 服饰 | 1 | **品红 `#FF3BD4`** | 316° | 不在蓝系里（旧值是淡蓝白，正是「分不开」的主因） |
| 弹药、救援 | 5 | **亮绿 `#00FF66`** | 150° | 与植物同 state ⇒ 同色 |
| 笔记 | 6 | **黄 `#FFD700`** | 51° | 沿用（用户已确认生效） |
| 资源 | 7 | **紫 `#B36BFF`** | 268° | 比旧值 `#AA6EFF` 更亮一点，紫得更纯 |
| 杂项 | 2 | 蓝 `#1F8EE2` | 207° | **= 原生值，用户要求「不变」** |
| 容器 / 尸体 | 9 | **橙 `#FF9500`** | 33° | 沿用（搜刮目标） |
| 设备 | 4 | **青 `#00E5FF`** | 187° | 原生 4 是绿，会和弹药撞色 ⇒ 改青 |
| 门 | 10 | **白 `#FFFFFF`** | — | 原生 10 是红，会和武器红撞色 ⇒ 改白 |
| 植物 | 5 | 亮绿（= 弹药救援） | 150° | 同 state |
| 其它（MSTT，默认关） | 3 | 不覆盖（原生蓝） | 207° | 装饰物，跟杂项同蓝即可 |

**六个物品组的色相间隔**（排序后）：
`红 0° → 黄 51° → 亮绿 150° → 杂项蓝 207° → 紫 268° → 品红 316° → （回到红 360°）`
⇒ 相邻间隔 **51 / 99 / 57 / 61 / 48 / 44 度**，全部 ≥ 44°，且都不在「低饱和/暗」区间。

**★ 副作用（如实记录）**：配色块是**引擎全局**的，而覆盖把**脉冲 High/Low 也写成了同一个色**
⇒ ① 原版手掌扫描仪在**同一状态**上的描边颜色也会变成我们的类别色（state 7 会变紫等等）；
② 那套「脉冲两端不同色」的色移效果随之消失（描边颜色变"稳"，alpha 动画不受影响，因为
alpha 字节原样保留）。取舍：**颜色稳定可辨**优先于「脉冲时轻微变色」——这正是用户要的。
不想要的话把这些 `ColorXxx` 清空即可（立刻退回原生配色）。

## 五、验收点（下一次进游戏）

1. 启动日志（install）应出现 **`outline colors: state=N 覆盖为 #RRGGBB <- 类别…`** 共 **9 行**
   （state **0 / 1 / 2 / 4 / 5 / 6 / 7 / 9 / 10** —— 容器+尸体共用 9、弹药救援+植物共用 5，各只写一次），
   之后一行 `outline colors[install]: 已在管理器创建之前写入 9 个状态的覆盖色（管理器 alive=0/11 …）`；
   * 有「描边基色原值」列可对照：note/resource 之外的类别原本是青/淡蓝白/蓝/绿…
     日志形态：`[install] outline colors: state=1 覆盖为 #FF3BD4 <- apparel（描边基色原值 0xFFB3C1EF；脉冲 High 原值 0x…）`。
2. `outline colors[...]` 那组 11 行里 **state 0 = #FF2E2E、1 = #FF3BD4、2 = #1F8EE2、
   4 = #00E5FF、5 = #00FF66、6 = #FFD700、7 = #B36BFF、9 = #FF9500、10 = #FFFFFF**；
   脉冲 High/Low 也应等于基色（说明写到了正确的块）。
3. ★ `renderer params[stats]: … 基色=#…` 每状态与上表一致 ⇒ **覆盖真的进了渲染器**。
4. ★★ 肉眼（本轮核心）：地上放**武器 / 宇航服 / 弹药 / 便条 / 矿石**五样东西，
   应该是 **红 / 品红 / 亮绿 / 黄 / 紫** 五种一眼分得开的颜色；箱子橙、电脑青、门白、
   杂项（Digipick / Credits / 玩具）保持蓝。
5. 不回归：F8 / 扫描仪自愈（用完扫描仪 1 秒内重挂且颜色仍是新的）/ 展示柜拿空熄灭 /
   换场景不崩 / 活人一个都不亮。

## 六、可复用经验

1. **「写进表」之前先确认「谁读这张表、读的是哪一段」** —— 本轮最大的教训：
   同一个地址区间里 `0x591E088` 和 `0x5919B08` 只差 0x4580，前者是 float 常量、
   后者才是描边基色；老文档把前者的+0x00/+0x20 当成「脉冲 High/Low」记了三个版本，
   于是三个版本的覆盖都在写常量区（日志还很像成功）。
   **验证手段**：反汇编要连「循环初值 + 步长 + 次数」一起读（`lea r14,[rip+…]` 之后
   必须追到 `add r14, 0xA0` 与 `sub r12, 1`），并把每个读取点的**真实块偏移**算出来。
2. **读写偏移差 0x80 的两张「表」其实是同一个块**：这类「按 stride 拼出来的大数组」
   很容易被误记成多张表；把 stride / 偏移写成常量并在注释里列成表格，后续才不会错。
3. **「谁消费」优先于「谁存储」**：终局证据是**渲染侧那份 32 字节参数块**
   （`0x653850` + `0x59751E8/+0xE8/+0x2C8/+0x3C8`）。有了这条只读探针，
   「颜色有没有生效」不再需要靠肉眼猜。
4. **配色需求要按「色相间隔」设计**：给定 N 个类别时，先排色相再挑明度
   （本轮六个物品组间隔 ≥44°）；**共享状态的两组必须同色**，并在代码里用
   WARN 把「同状态不同色」这种配置错误顶出来。
5. **默认值进 DLL，INI 只当覆盖层**：用户改过 INI 不能被构建脚本冲掉，
   但「不写 INI 也有一套好颜色」必须成立（否则每个新默认色都要用户手动补键）。
6. **截图的颜色差异要用工具量化**：`tools/img_outline_color.py`（色相分桶 + 区域最饱和像素）
   把「看起来一样」变成「hue 190 vs 187」这种可比较的数字，
   比反复问用户「到底哪里一样」高效得多。
