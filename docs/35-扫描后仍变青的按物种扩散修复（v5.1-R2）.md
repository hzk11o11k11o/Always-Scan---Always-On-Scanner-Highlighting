# 35 · 「有些植物扫描后还是青」的修复：**按物种（base）扩散**（DLL v5.1.0 订正 R2 / 公开版**仍是 2.0**）

> 建立：2026-09-27。触发：用户实测报告（原文）——
>
> ```
> 有些植物还是出现了扫描后颜色未扫描前的青，但是打开扫描仪再关闭又变成绿色的现象
> ```
>
> 一句话结论：**"已扫描"的事实是 species（资源）级的（引擎知识库就是这么存的），
> 而 v5.1 的记忆是引用级的** —— 同 species 里"引擎没画过"的那些实例
> （不在扫描仪求值范围 / 视角外 / 数量上限）永远学不到 ⇒ 停在青色；
> 玩家再举一次扫描仪，它们被引擎画成 4/5 绿色 ⇒ 才补上
> （这正是用户说的"打开扫描仪再关闭又变成绿色"）。
>
> **修法**：新增**会话级"按物种扩散"表** —— 任一实例被权威确认"已扫描"
> （引擎画过 4/5 ∨ 引擎状态 == 2 ∨ 资源链命中）⇒ 同 base 的**所有**实例一起变绿。
> 物种表**不落盘**（避免 v5.1 修掉的"跨存档外溢"），重启后靠**引用级落盘记忆
> 动态激活**恢复。

## 一、证据链

### 1.1 用户那一局的日志（`SAS_AlwaysScan.log`，2026-09-27 07:29~07:31，v5.1 订正 R1）

```
[07:31:07.871] planet targets (窗口内): 未扫描=245 已扫描=383
              | 判据: 查询=589 命中=395 链失败=142 缓存=88 …
              | 引擎状态: 问=589 已扫描=0 未扫描=447 未知=142

              | 引擎状态表: 条目=0 读=829 绿=616 青=0 无条目=5519

```

四条硬证据：

| 观察 | 含义 |
| --- | --- |
| `引擎状态: 问=589 已扫描=0` | ★★ 主判据 `GetOutlineState(ref)` 整局**一次都没答 2** —— v4.28 的"主判据"实际上从未可靠工作（见 §1.3） |
| `引擎状态表: 读=829 绿=616` | 绿**全部**来自"引擎亲手画过 4/5"的只读探针（举着扫描仪时读到） |
| `引擎状态表: 条目=0` 反复出现 | 放下扫描仪后引擎把状态表**清空** ⇒ 放下的时段探针什么都读不到（`无条目=5519` 在涨） |
| `按引用记忆: 绿=56 / 总量=74` | 学到的绿是**逐个引用**的 —— 同 species 的实例**学不全**（见 1.2） |

追加证据（同局，举着扫描仪时探针逐条学到的是一个 species 的一串实例）：

```
[07:30:51.889] flora scan: 引擎把 ref=0xFF037727（base=0x185489）画成了绿色（outline state 4）-> 记下…
[07:30:51.890] flora scan: 引擎把 ref=0xFF03772A（base=0x185489）画成了绿色（outline state 4）-> 记下…
[07:30:52.118] flora scan: 引擎把 ref=0xFF037720（base=0x185489）画成了绿色（outline state 4）-> 记下…
…
```

⇒ **引擎是"按 species 一起画绿"的**（知识库是 species 级），但**我们只学到了"被画到的那几个引用"**。

### 1.2 为什么"学不全"：四条判据在"放下扫描仪"后全堵

| 判据 | 放下扫描仪后 |
| --- | --- |
| ⓪ 引用级记忆 | 只有"举着时被引擎画到过"的引用有绿 —— 没被画到的实例**没有** |
| ⓪.5 引擎状态表探针 | 引擎**放下即清表**（`条目=0`）⇒ 读不到任何东西（`无条目` 单调涨） |
| ① 主判据 `GetOutlineState` | 本局 0/589 命中（§1.3） |
| ② 资源链 | 植物产出是 MISC ⇒ 引擎那一段要求 LVLI ⇒ 不适用（docs/26） |

⇒ 对植物来说，**唯一可靠的"已扫描"证据 = 举着扫描仪时探针读到引擎画的 4/5**。
同一个物种里，**引擎没画到的实例**（不在扫描仪求值范围 / 视角外 / 数量上限）
直到"下一次被画到"之前都没救 —— 用户看到的"打开扫描仪再关闭又变成绿色"
就是"下一次被画到"。

### 1.3 反汇编复核：主判据查的**不是**"引擎画 4/5 用的那套表"

`GetOutlineState`（RVA `0x1306E80`）本轮完整反汇编，三条返回路径全部定位：

```asm
01306E91  mov dl, 0x2a                 ; 组件类型 0x2A = Scannable
01306E9A  call 0x2c5c90               ; 取组件
01306EA4  je 0x1306fdc                ; 组件缺失 ⇒ 0/2 那条（xor sil,sil / inc sil）
01306EB2  lea eax, [rsi + 0x1000000]  ; esi = ref FormID
01306EBB  cmp eax, 0xfffffe
01306EC0  ja 0x1306fbb                ; ★ FormID ∈ [0x00…, 0xFE…] ⇒ 静态路径
01306F66  call 0x7b8260               ; ★ 动态引用（FF 开头）⇒ 这条路
01306F9E  movzx eax, [rsp + 0xb0]     ; 结果字节
01306FA8  setne al / inc al           ; 0 ⇒ 1（未扫描）/ 非 0 ⇒ 2（已扫描）
```

* 静态路径 `0x7b7d60`：查"DB 里按 FormID 的一张 map"，读元素 `+0x21` 的 1 字节
  （`call 0x23467b0` 找到条目、`cmp rax,[rbx+0x68]` 判末端）⇒ 字节非 0 ⇒ 2。
* 动态路径 `0x7b8260`：**存在性查询** —— 在红黑树里按"3 个 dword 的复合 key"
  找节点（`movzx r9d,word [rcx+rdx*4+0x12]` → `cmp byte [rax+0x19],cl` 树上游走 →
  `cmp rdx,r9` / `setne cl`）⇒ **找到 ⇒ 1 / 没找到 ⇒ 0**（再 `setne/inc` ⇒ 2 / 1）。

**结论**：它查的表与"引擎给星球目标画 4/5"用的表/条件**不是同一套** ——
日志里"引擎亲手画成 4/5 绿"的引用，`GetOutlineState` 几乎全部答 **1**。
历史贡献率：docs/31 那局 5/325（1.5%）、docs/34 那局 7/833（0.8%）、本局 **0/589**。
⇒ **不能依赖它**；真正可靠的证据只有"引擎亲手画 4/5"（探针）+ 资源链（矿脉）。
修法必须让这条证据**扩散到同 base 的所有实例** —— 这正是引擎自己的行为。

**行为变化（给用户的三句话）**：

1. **扫过一个植物 / 矿脉 ⇒ 同 species / 同资源的整片一起变绿**（不再需要"打开扫描仪再关闭"补）；
2. **重启游戏后**：落盘记忆里的引用一旦遇到就"动态激活"其 base ⇒ 同 species 的其它实例**立刻**一起变绿（不必再举一次扫描仪）；
3. 观感、配色、其它功能与 2.0 完全一致；无需改 INI。

**已知边界（如实记录）**：

* 物种表**不落盘** ⇒ **不会外溢到别的存档**（v5.1 修掉的"矿石、植物扫描前后都是绿色"不回归）；
  代价：**跨存档切换**（同一次游戏内读另一个存档）时，前一个存档学到的物种表仍在内存里
  —— 与"引用级落盘记忆"本身的跨存档影响**同级**（都只在"遇到过记忆中的引用"时激活），
  不再额外扩大；
* 引擎 `GetOutlineState` 判据本轮**不改**（它答 2 时仍被采纳），但**不再依赖**它。

## 四、验收判据（下一次进游戏）

1. 启动日志出现**订正标记**（判断"跑的是不是修好的 DLL"的唯一依据）：
   ```
   SAS_AlwaysScan v5.1.0 loading（订正 R2：状态表 0x5F39CE0 + 「青」不短路 + 按物种扩散）…
   config: 星球目标记忆(v5.1 / 订正 R2) -> 引用级记忆 + **按物种（base）扩散**：…
   ```
2. ★★ **肉眼（核心）**：
   * 扫一个植物 ⇒ **同 species 的整片**都变绿（**包括以前"打开扫描仪再关闭才变绿"的那些**）；
   * 没扫过的 species **仍然青色**（不回归 v5.1 的"没扫过不绿"）；
   * 矿脉同理（同矿脉类型一起变绿）；
3. ★ 统计行：`按物种扩散(★v5.1.2): 命中=/物种表=/新增=` 出现；
   `物种表=` 的数字约等于"这台存档里学到过的物种 / 资源数"（几十~几百）
   —— 它**不会**像 `引擎状态表: 条目=` 那样随时间无意义增长；
4. ★ **重启游戏**后：走到上次扫过的植物旁（不举扫描仪），**一片都绿**
   （物种表靠"引用级落盘记忆 + 动态激活"恢复）；
5. 不回归：F8 / 扫描仪自愈 / 展示柜拿空熄灭 / 换场景不崩 / 活人一个都不亮 / 分组配色。

## 五、经验（写给下一轮）

1. **判据的粒度必须与事实的粒度一致** —— 这是 docs/33 的教训的**反面**：
   引擎知识库是 **species 级**的（扫一个实例 ⇒ 同 species 全绿是原版行为），
   所以"只记引用"会漏掉"引擎没画到的实例"。正确做法不是二选一，而是
   **引用级记忆 + 向 base 扩散（但要防跨存档外溢）**。
2. **"打开 X 再关闭就恢复"永远是"缺一条判据"的信号** —— 恢复动作本身暴露了
   "引擎在这个动作里写了什么"（本例 = 画 4/5 绿）；顺着这个动作去找
   "它写了、我们没读到"的那一步，根因就出来了。
3. **统计行要留"从不出现的那一档"**：`引擎状态: 问=589 已扫描=0` 一眼破案 ——
   主判据从未生效；有分母、有零值，才可证伪。
4. **反汇编要读到"返回值的来源表"**：`0x1306E80` 的 `0x7b8260` 是**存在性查询**
   （找到 ⇒ 2、没找到 ⇒ 1），而它查的表与"引擎画 4/5"用的表**不是同一套**
   ⇒ 两个判据不能互相替代；"名字像"不等于"语义同"。
5. **跨会话恢复用"动态激活"，不要"落盘第二份表"**：把"扩散"挂在"引用级记忆命中"
   这个**已有**的事件上，影响面与已有机制**完全相同**（零新增外溢面），
   还省掉了格式变更与迁移成本。
