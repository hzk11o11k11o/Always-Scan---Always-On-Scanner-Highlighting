# 02 · 载入存档崩溃：诊断过程与修复（2026-09-16）

> 结论：**是 mod 导致的。** 第一次崩溃的异常地址 100% 落在
> `SAS_AlwaysScan.dll` 内，符号化后就是 `AlwaysScan.cpp:515` 的
> `cell->ForEachReference(...)`。根因是 **commonlibsf 里 `TESObjectCELL` 的成员偏移
> 比真实游戏整体大 8 字节**，而 v1 直接信了头文件。

---

## 一、现象

- 通过 MO2 启动游戏两次，**都在载入存档后不久崩溃**（没进到能玩的状态）。
- 游戏根目录留下两个转储：
  - `Starfield_09-16-09-54.dmp`（153 模块，90 MB）
  - `Starfield_09-16-09-55.dmp`（165 模块，123 MB）
- 文件名里的时间是 **UTC**，本地时间 = +8h ⇒ 本地 17:54 / 17:55 各崩一次。

## 二、证据链

### 1. SAS 自己的日志（`Documents\My Games\Starfield\SFSE\Logs\SAS_AlwaysScan.log`）

```
[17:54:26.178] SAS_AlwaysScan v1.0.0 loading (SFSE build 131408)
[17:54:26.180] config: radius=50.0m duration=90s targets=160 hotkeyVK=0x77 startEnabled=true
[17:54:26.180] SAS_AlwaysScan installed (main thread 23176)
[17:54:33.544] BindForms: quest 'SAS_AlwaysScanQuest' not found yet      ← 主菜单期间
[17:55:10.874] forms bound: prefix=04000000 quest=04000806 arrayOfForms@0x38
[17:55:17.521] reset (first cell) play=0 stop=0 glow=0                    ← 最后一条
```

**关键推理**：`scan#N` 统计日志的设计是「每 5 秒一条，且 `lastStatsMs` 初值 0，
所以第一轮扫描就必然打印」。日志里**一条都没有** ⇒ `Rescan()` 第一次调用就没有返回
—— 崩在 `Rescan` 里面。

顺带解释了另一个现象：`17:54:48 → 17:55:10` 之间约 22 秒没有任何 `BindForms` 警告，
那正是读档时主线程忙于重建世界、`Tick` 不被调用的时段。

### 2. 崩溃转储的异常记录

| | 第一次（09-54） | 第二次（09-55） |
| --- | --- | --- |
| 异常码 | `0xC0000005` ACCESS_VIOLATION | `0xC0000005` ACCESS_VIOLATION |
| 异常地址 | `00007FFF1ADC0E20` → **`SAS_AlwaysScan.dll+0x10E20`** | `00007FF70215B114` → `Starfield.exe+0xAEB114` |
| 访问地址 | `0` | `0x1449CB5B48C`（野指针） |
| 故障线程 | 非主线程 | 非主线程 |

第一次是**铁证**：异常地址直接落在我们这个 DLL 里。

### 3. 符号化（用 PDB）

```
SOURCE : D:\workspace\starfield mod\always scan\plugin\src\AlwaysScan.cpp : 515  (+0x81)
```

`AlwaysScan.cpp:515` 就是：

```cpp
cell->ForEachReference([&](const RE::NiPointer<RE::TESObjectREFR>& a_refPtr) {
```

### 4. 反汇编崩溃指令流

`ForEachReference` 是**头文件里内联**的，反汇编出来是这样：

```asm
00010DE7  mov  rdi, [rbp+0xb8]        ; rdi = cell
00010DEE  lea  rbx, [rdi + 0x128]     ; ← BSAutoReadLock(lock)，用了 0x128
00010DFC  call 0x1ad10                ; BSReadWriteLock::LockRead
00010E02  mov  rsi, [rdi + 0x90]      ; ← references._data，用了 0x90
00010E09  mov  eax, [rdi + 0x88]      ; ← references._size，用了 0x88
00010E17  lea  rdi, [rax*8 + rsi]
00010E1E  je   0x10e49
00010E20  cmp  qword ptr [rsi], 0     ; ← 崩在这里，rsi = 0 ⇒ 读 [nullptr]
```

崩溃时的寄存器：`RDI = 0x0000000233F00000`（= `size*8` ⇒ **`_size` = 0x467E0000**），
`RSI = 0`（**`_data` = nullptr**）。

**一个「size 巨大、data 为 null」的 BSTArray 是自相矛盾的** ⇒ 读到的不是真的 BSTArray。

### 5. 和头文件对不上

`commonlibsf` 的 `TESObjectCELL` 注释写的是 `references // 080`、`lock // 120`，
但编译器生成的代码用的是 **`0x88` / `0x128`** —— **整体正好差 8 字节**。

---

## 三、根因

`TESObjectCELL` 的**声明算出来的**成员偏移比**真实游戏**整体大 8 字节：

| 成员 | 真实（游戏 / 头文件注释） | commonlibsf 声明算出来的 |
| --- | --- | --- |
| `cellFlags` | 0x40 | 0x48 |
| `cellState` | 0x47 | 0x4F |
| `references` | **0x80** | **0x88** |
| `lock` | 0x120 | 0x128 |
| `sizeof` | ? | 0x150 |

**为什么 `static_assert` 抓不到**：现有断言只有 `static_assert(sizeof(TESObjectCELL) == 0x150)`。
整体 +8 之后最后一个成员 `unk140` 刚好落在 0x148、结束于 0x150 —— **尺寸仍然自洽**，
位移被完美掩盖。这和本项目已经修过的
`BGSListForm::arrayOfForms`（0x30→0x38）、`TESGlobal::value`（0x40→0x48）
是**同一类**「派生类成员整体偏 8」问题，只是这次偏的是基类 `TESHandleForm`
的声明尺寸（`TESObjectCELL : TESHandleForm, TESFullName`）。

> 交叉验证：上一代项目 `高亮物品` 的 `Highlight.cpp` 里 v20 实测日志写着
> `refs=517865472`（= `0x1EDE0000`，一个**指针的低 32 位**），
> 本次读到 `0x467E0000` —— **完全同一种现象**。他们最终的结论就写在那份代码里：
> > ⇒ **commonlibsf 头文件里 TESObjectCELL 的成员偏移对这个游戏版本是错的**
>
> 所以他们从 v20 起一律用 `kOffCellRefs = 0x80` **手工读数组**，绝不调用
> `cell->ForEachReference()`。本项目 v1 把这条教训漏掉了。

顺带一提：`v18` 还在「加载画面里遍历 cell 引用数组」上崩过一次 —— 同一类场景，同样漏掉了。

## 四、修复（v1.1）

全部集中在 `plugin/src/AlwaysScan.cpp`：

1. **弃用 `cell->ForEachReference()` 和 `cell->IsAttached()`**
   —— 这两个都按「声明偏移」访问 `TESObjectCELL` 成员，正好踩在错的那 8 字节上。
2. **候选偏移 + 形状校验自适应**（`kCellRefsOffCandidates = {0x80, 0x88}`）
   —— 不赌单一偏移。校验判据两条，都不依赖固定成员偏移：
   - BSTArray 头形状自洽：`size <= 200000 && capacity >= size && capacity <= 1<<20`
     且 `data` 可读；
   - 抽查前 4 个元素：指针可读，且 `formType(+0x2E) ∈ {REFR(0x4A), ACHR(0x4B)}`
     （`formType` 在 `TESForm` 基类里，不受那 +8 位移影响）。
   谁通过用谁；都不过就**本轮不扫描**。
3. **`cell` 指针本身先过 `IsReadable`**（挡 `parentCell` 万一也不对）。
4. **换场景 / 读档后静置 2 秒**（`kSettleAfterSceneChangeMs`）再开始扫描。
5. **引用数组长度连续 2 轮一致才扫**（`kRefsStableRounds`）—— 长度突变 = 加载线程
   还在往数组里塞引用。
6. **保留了 `ref->parentCell` / `ref->data` 的成员访问**：这两个是 `TESObjectREFR` 的
   成员，上一代长期实测可靠（只有 `TESObjectCELL` 有问题），且每个元素解引用前都过了
   `IsPlausiblePointer`。
7. 新增**偏移探针**（static_assert），把「声明算出来是 0x88 / 0x128」这个事实钉在代码里：

```cpp
static_assert(offsetof(RE::TESObjectCELL, references) == 0x80 + 0x08, "...");
static_assert(offsetof(RE::TESObjectCELL, lock) == 0x120 + 0x08, "...");
```

哪天有人把基类声明修对了，这里会**编译失败**，提醒重新核对 `kCellRefsOffCandidates`。

8. 统计日志加了两个字段：`off=0x80`（本轮采用的偏移）和 `rej=N`（数组校验被拒次数）。
   **实测判据**：正常进游戏后 `off=0x80`、`rej` 不再增长、`refs` 是个合理值。

## 五、本次新增的逆向工具（`tools/re/`）

| 工具 | 用途 | 依赖 |
| --- | --- | --- |
| `dmpinfo.py` | 通用 minidump 解析：模块列表、异常记录、寄存器、从 RSP 起扫栈 | 无 |
| `pdbsym.py` | 用 `dbghelp` + PDB 把一个 `基址+RVA` 解析成**函数 + 源文件行号** | 无（ctypes） |
| `disasm.py` | 反汇编 `exe/dll` 的指定 RVA 附近，用来读崩溃现场那条指令 | `pip install capstone` |

用法：

```
python tools\re\dmpinfo.py "D:\...\Starfield_09-16-09-54.dmp"
python tools\re\pdbsym.py "<dll 路径>" 7FFF1ADB0000 10E20
python tools\re\disasm.py "<dll 路径>" 10E20 60 18
```

> 解析 minidump 时踩过的两个坑（已在新工具里修好，记下来防止再犯）：
> 1. `MINIDUMP_EXCEPTION_STREAM` 里 `ThreadContext` 的
>    `MINIDUMP_LOCATION_DESCRIPTOR` 是 **`{DataSize, Rva}`**，顺序写反会读到
>    全 0 的寄存器，让人误判「上下文没保存」。
> 2. `MINIDUMP_THREAD` 的 `Stack` 在 **+24**（不是 +16，+16 是 `Teb`），
>    写错就会「扫」到一段根本不是栈的内存。
