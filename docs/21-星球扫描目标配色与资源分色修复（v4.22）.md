## 一、取证 ①：星球扫描目标为什么「扫描前后一个色」

### 1.1 MOD「植物」类别的覆盖面（离线全量，新探针）

新工具 **`tools/re/esm_resnode_probe.py`**（Starfield.esm 全量 3 823 315 条记录 + 关键词表；
输出留档 `out/esm_resnode_probe.txt`）：

| 记录类型 | 数量 | 说明 |
| --- | --- | --- |
| **FLOR** | **300 条** | 其中 **125 条是 `MineralDeposit*`**（矿石 / 气体 / 液体矿脉：`MineralDepositUncommonFluorineSmall03`、`…Chlorosilanes…`、`…Benzene…`、`…Tetrafluoride…`、`AkilaLife05_MineralDepositCommonIron01`、`FFNewHomeSteadR04_MineralDepositCommonWater02` …）；其余是植物（`FloraBloodStoneTall` 等） |
| FLOR 上的关键词 Top | — | `FloraTypeOrganic` 169、**`FloraTypeInorganic` 125**、`CCT_Enviro_Rockbreaker` 125、`ElementalBlastAllowedResource` 122、`FloraTypeGas` 52、`FloraTypeSolid` 37、`FloraTypeLiquid` 33、`ResourceVents` 81 |
| （对照）带 `ResourceType*` 的记录 | MISC 410 / CONT 202 / IRES 128 / BMMO 7 | 真正的「资源**物品**」判据仍是 MISC + `ResourceType*`（= 需求 2 的「资源」） |

⇒ **FLOR 是个混合类别**：既含植物，也含星球上的矿脉 / 气泉 / 液池。
而 MOD 从 v4.0 起把整个 FLOR 归入「植物」类（`state 5` → 亮绿），**常亮 + 走到哪涂到哪**。

### 1.2 引擎那一对槽位（state 7 / 8）本来就是干这个的

`SAS_AlwaysScan.log`（v4.21 那一局，`outline colors[install]` 11 行原生值）：

```
state= 7 TargetScannable  基色=#000000 a=00  脉冲High=#72E8FF a=FF 脉冲Low=#115B69 a=FF
state= 8 TargetScanned    基色=#000000 a=00  脉冲High=#72E8FF a=FF 脉冲Low=#115B69 a=FF
```

* 引擎的逐引用求值函数（`0x159ED90`，见 `docs/16` §2.2）只会写 **0/1、2/3、7/8、9**，
  其中 `7/8` 正是「可扫描目标 / 已扫描目标」这一对 —— 星球上扫矿石 / 气体 / 液体 /
  植物 / 动物走的就是它；
  > ★★★ **v4.24 订正**：这句「只会写 0/1、2/3、7/8、9」**漏了 4/5 与 10**
  > （当时只反汇编了函数尾部一段）。完整账本：**引擎会写 0/1、2/3、4/5、7/8、9、10，
  > 只有 state 6 它不写**；其中 **4/5 = 「已扫描的星球目标」= 原生绿 `#27C684`**
  > （v4.24 已归还引擎，见 `docs/23`）。本文件 §1.2 说的「7 与 8 原值完全相同
  > ⇒ 差异只能来自引擎自己写的东西」仍然成立（7/8 = 扫描前 / 扫近的判定），
  > 但**「扫描后变绿」那一步其实是 7/8 → 4/5 的切换**，不是 7 与 8 的区别。
* 7 与 8 的**原值完全相同**（基色 0、脉冲同色同 alpha）⇒ 两者的差别**只能**来自引擎
  自己往这对槽位里写的东西，我们**一旦覆盖 7 的 RGB**（v4.17~v4.21 的「资源 = 紫」），
  就等于把这对槽位的表现改掉；
* 另一边，MOD 的「植物 = 亮绿 state 5」是**单一颜色**，FLOR 只要在半径里就一直是它，
  引擎就算中途写了 8/9，`MonocleMenu` 一关（`native outline: 引擎侧高亮疑似丢失`）
  又会**整批重挂回 state 5** ⇒ 用户看到的必然是「扫描前后一个色」。

⇒ 结论：**这两个状态要「保持原版颜色」，就不能再借 7 当「资源色」，也不能再让 MOD 去涂 FLOR。**

## 二、取证 ②：「资源」为什么和「杂物」同色（自检卡死）

用户那一局日志（`[09:25:39]` 会话，星球表面）：

```
[09:26:51] [W] resource keyword: 自检样本还没进内存（iron=0 pick=1 cred=1；第 1 次尝试）  -> 「资源」暂归「杂项」
[09:26:58] [W] …（第 18 次尝试）
[09:27:03] [W] …（第 42 次尝试）
[09:27:08] [W] …（第 66 次尝试）
[09:27:13] [W] …（第 90 次尝试）
[09:27:18] [W] …（第 121 次尝试）
```

* 该局 46 条 `category (本轮选中)` 统计行里，**`resource=` 永远是 0**（`out/count` 核对：
  `resource=0`×46，只有 config 行的 `resource=1/7` 是开关与状态值）；
* **`InorgCommonIron`(0x0005556E) 整局都是 `null`**（`iron=0`），而 `Digipick`(0xA) /
  `Credits`(0xF) 第一次就拿到了 ⇒ 不是 API 坏了，是这个**具体记录当时不在内存里**
  （Starfield 的记录是按需流式的，静态 masters 里也有大量记录开局不建对象）；
* 旧代码的语义是「**自检通过（== 1）才让资源分类生效**」⇒ 这种「样本永远拿不到」的
  场景下，资源分类**永久不生效**，而且只在日志里留一条 WARN —— 用户看到的现象就是
  「资源和杂物一模一样」；
* 离线再核一次：`0000556E InorgCommonIron` 确实带 `ResourceTypeSolid`（属于 410 条之一）
  ⇒ 判据本身没错，错的是**门控方式**。

### 3.1 为什么「资源」不能借用 4 / 5 / 6 / 10，也不能用 8？

11 个槽位的账（`docs/16` §2.2：引擎只写 **0/1、2/3、7/8、9**）：

| 槽位 | 谁在用 | 结论 |
| --- | --- | --- |
| 0 / 1 | MOD：武器 / 服饰 | 已用（用户要的红 / 品红） |
| 2 | MOD：杂项 —— **写的就是原生色**（观感零变化） | 保留 |
| **3** | 空（v4.17 起是 MSTT，而 MSTT 默认关） | **借给「资源」** |
| 4 / 5 / 6 / 10 | MOD 专用：设备 / 弹药救援+植物 / 笔记 / 门 | 都被占满，且每个都是用户点名要的颜色 |
| **7 / 8** | **原版扫描仪的「可扫描目标 / 已扫描」** | **本轮归还，不碰** |
| 9 | MOD：容器 / 尸体（橙 ≈ 原生橙） | 保留 |

⇒ 12 个类别 + 11 个槽位，且「6 个物品组 + 容器 / 设备 / 门」都要可区分的颜色 ⇒
**必然要借一个引擎状态**。借 3（`Tracked`，用得最少、原生与 2 同蓝）是代价最小的选择。

## 六、可复用经验

1. **「自检/门控」只能用来否决，不能用来准入**。v4.17 的设计是「样本验通过 → 功能才生效」，
   看似更安全，实则把「样本恰好不在内存」（Starfield 按需流式加载记录，实测 121 次全 null）
   变成了**功能静默失效**——用户看到的是「颜色没变」，日志里只有 WARN。
   正确姿势：**默认生效 + 形状校验兜底 + 只在拿到明确反证时关闭**。
2. **给「有语义的引擎状态」分类前，先问一句「引擎自己会不会写它」**。
   state 7/8 是原版扫描仪的目标槽位，借它 = 和原版抢画面（`docs/16` §2.2 那张表就是账本）。
   本轮把它归还，并改用 `Tracked`（3）。
3. **一个 form 类型不等于一种东西**：`FLOR` 里既有植物也有矿脉 / 气泉 / 液池
   （`FloraTypeOrganic` vs `FloraTypeInorganic` + `Solid/Gas/Liquid`）——
   凡是要「按类别上色」的功能，都得先离线把这一类**全量摊开看一眼**（本轮新工具
   `tools/re/esm_resnode_probe.py` 已入库，可复跑）。
4. **用户报「颜色分不出来」时分两个方向查**：① 我们的颜色**没写进去**（表地址 / 门控 /
   manager 出生时机）；② 我们的**常亮覆盖**盖住了原版自己的状态色。
   本轮两条同时命中，一条在「写」，一条在「盖」。
5. **复盘用的诊断要「一句话可 grep」**：`首个资源命中 base=0x…` 这种一次性 INFO
   比统计行里的计数更快定性（这次就是靠 `iron=0` 的 WARN 一行破的案）。
