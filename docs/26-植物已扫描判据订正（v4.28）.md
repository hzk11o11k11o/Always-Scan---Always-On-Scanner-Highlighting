# 26 · 植物「扫描前就是绿色」的修复：产出物品必须是 LVLI + 主判据换成引擎自己的 IsScanned（DLL v4.28.0 / 发布版 1.7.7）

> 建立：2026-09-26。触发：用户实测反馈（原文）——
>
> ```
> 植物颜色错误，扫描前也显示成了扫描后的颜色，矿石，动物是好的
> ```
>
> 一句话结论：**v4.25~v4.27 那条「已扫描」资源链对植物根本不适用**。
> 引擎的扫描求值函数 `0x159ED90` 在走那条链之前有一条硬门槛
> ——「产出物品」字段必须是 **LVLI**（`cmp byte [rax+0x2E],0x3F / jne <跳过>`），
> 而**植物的产出物品是 MISC**（`OrgCommonFiber` 之类）、只有**矿脉 / 气泉 / 液池**
> （`MineralDeposit*`）的产出才是 LVLI。MOD 放行了 MISC
> ⇒ 拿「植物产出的资源在不在勘测数据里」当成了「植物扫没扫过」
> ⇒ **没扫描过的植物也变成原版绿**（矿石 / 气体 / 液体一直是对的，正因为它们走的是 LVLI）。
>
> 修法两条：① **主判据换成引擎自己的 `ScannableComponent::GetOutlineState(ref)`**
> （`1` = 未扫描 / `2` = 已扫描，引擎原生 `IsScanned` 就是它 `== 2`）；
> ② **资源链只对 LVLI 产出的 FLOR 生效**（与引擎逐字节同口径）。

## 一、证据链

### 1.1 用户那一局的日志：植物与矿脉在链上就是两类（`SAS_AlwaysScan.log`，17:46）

```
[17:46:07.781] flora scan: base=0x18547F 产出字段[+0x260]=0x1E34F5B37C0 misc=0x1E34F5B37C0
               资源数组[+0x238]=1个 irES=[0x00077821] -> 已扫描=1 ⇒ 状态 5（原版「已扫描」绿）
[17:46:07.781] flora scan: base=0x185479 产出字段[+0x260]=0x1E34F5B37C0 misc=0x1E34F5B37C0 …  已扫描=1
[17:46:07.781] flora scan: base=0x185489 …                                                      已扫描=1
[17:46:07.781] flora scan: base=0x185478 …                                                      已扫描=1
[17:46:07.782] flora scan: base=0x25232B 产出字段[+0x260]=0x1E369240C40 misc=0x1E34F5A4980
               资源数组[+0x238]=1个 irES=[0x000057C1] -> 已扫描=0 ⇒ 状态 7（原版「未扫描」青色脉冲）
[17:46:07.815] flora scan: base=0x75CAD  产出字段[+0x260]=0x1E3692407A8 misc=0x1E34F5B17C0 … 已扫描=0
```

* **植物**（`0x185478/79/7F/89` = `FloraBiomeForestConiferous*`）：
  `产出字段 == misc`（同一个指针）⇒ 我们的代码走的是「**字段直接是 MISC**」那条分支
  （v4.26 为兼容引擎另一处代码 `0x1479549`/`0x1479AC9` 而放行的）；
  它的资源数组元素 = `IRES 0x77821`（有机纤维那类资源），**引擎说它"已扫描"**
  ⇒ 整片植物被判成「已扫描」⇒ 涂绿。
* **矿脉**（`0x25232B` = `MineralDepositCommonLead01`、`0x75CAD` = `MineralDepositCommonWaterLiquid01`）：
  `产出字段 != misc`（是 LVLI → 首条目 MISC），判据结果也是对的（`已扫描=0`）。
* 同局统计行 `planet targets (窗口内): 未扫描=117 已扫描=491` —— **80% 的目标被判"已扫描"**，
  与用户「植物扫描前就是绿的」完全一致。

### 1.2 引擎的扫描求值函数：那条链**只对 LVLI 成立**（`0x159ED90` 反汇编原文）

```
0159F4D7  cmp byte [rax+0x2e], 0x2e   ; base formType == kFLOR (0x2E) ?
0159F4E1  mov rax,[rax+0x260]         ; FLOR+0x260 = 产出物品（produceItem / PFIG）
0159F4F1  cmp byte [rax+0x2e], 0x3f   ; ★ formType == **kLVLI** (0x3F) ?
0159F4F5  jne 0x159f57f               ; ★ 不是 LVLI ⇒ **整段跳过**（不判「已扫描」）
0159F4FB  cmp byte [rax+0x13a], 0     ; 条目数 > 0 ?
0159F504  mov rax,[rax+0x120]         ; 第一个条目
0159F513  cmp byte [rcx+0x2e], 0x28   ; formType == kMISC (0x28) ?
0159F519  mov rbx,[rcx+0x238]         ; MISC+0x238 资源数组
  for each 24 字节元素: cmp [rcx+0x2e],0x9f（IRES）; call 0x1597A50（资源已扫描？）
0159F562  add eax, 4                  ; ⇒ state 4（远）/ 5（近）= 原生绿 #27C684
```

⇒ 引擎自己**从来不会**因为「植物产出的资源已扫描」而把植物画成绿色；
植物的「扫没扫过」是另一条路（见 §1.3）。v4.25~v4.27 把 MISC 当入口放行，
等于给植物接了一条引擎不认的判据。

### 1.3 引擎自己的「扫没扫过」在哪：`ScannableComponent::GetOutlineState(ref)`（1 / 2）

| 事实 | 证据 |
| --- | --- |
| `GetOutlineState` 的 RVA = **`0x1306E80`** | commonlibsf `RE/IDs.h`：`ScannableComponent::GetOutlineState{ REL::ID 83007 }` ⇒ `tools/re/versionlib.py id 83007` = `0x1306E80` |
| 返回值 **1 = 未扫描 / 2 = 已扫描** | 引擎原生函数注册表里有一条 **`IsScanned`**（名字字符串 RVA `0x4BCA548`，注册点 `0x2088F49`），实现 = thunk `0x2076660`：`call 0x1306E80` / `cmp al,2` / `sete al`（`tools/re/func.py strings "IsScanned"` + `func.py rip 0x2076660`） |
| 它内部查的是**玩家知识库的物种槽** | 函数体：`[ref+0xC8]` → `call 0x2C5C90`（组件类型 `0x2A` = Scannable）→ `0x23FF640` = `BSGalaxy::GetKnowledgeManager`（`REL::ID 126578`）→ `+0x8B0` = knowledge DB（commonlibsf `RE/P/PlayerKnowledge.h`：`kKnowledgeDbOffset = 0x8B0`、`SpeciesSlot.percent / scanFlag`）→ `setne al; inc al` |
| 它是**按引用**回答的 | 引擎自己的扫描求值函数也调它内部那套：`0x159F34B` = `call 0x1307180`（`ScannableComponent::GetCanonicalId`，`REL::ID 83009`），键 = canonical species / resource id ⇒ 植物 / 矿脉 / 气泉 / 液池 / 动物通用 |
| 语义旁证 | 同一函数还被 HUD 侧（`0x15997A1` 一带）与另一个 `SetScanned(ref, …, 类别 0xD)` 包装（`0x2081440`）使用 |

⇒ v4.28 把它作为**主判据**：`GetOutlineState(ref) == 2` ⇒ 挂 `StateFloraScanned`（原版绿）。

1. **植物**：扫描前 = 原版青色脉冲、**扫描后（含以前扫过的）= 原版绿**；

## 四、验收判据（下一次进游戏）

1. 启动日志：
   ```
   SAS_AlwaysScan v4.28.0 loading
   config: floraScannedByEngineState=1 floraScannedByResource=1 stateFloraScanned=5 -> …
   flora scanned: 主判据就绪 —— ScannableComponent::GetOutlineState(ref)（RVA 0x1306E80，签名核对通过；1 = 未扫描 / 2 = 已扫描 = 引擎原生 IsScanned）
   flora scanned: 引擎判据就绪（RVA 0x1597A50，签名核对通过）…
   ```
2. ★★ 肉眼（核心）：
   * **植物**：没扫描过的 = **青色脉冲**（不再一上来就绿）；用扫描仪扫一次（或以前扫过的）
     ⇒ **绿色**（放下扫描仪后 ≤0.2 s 内变色）；
   * **矿石 / 气体 / 液体**：与 v4.27 一样（扫过的绿、没扫过的青）；
   * **动物**：不变（引擎自己画）。
3. 诊断：统计行出现 `| 引擎状态: 问=… 已扫描=… 未扫描=… … ready=1/1`；
   `flora scan: … | 引擎状态=N | …` 里植物的 `引擎状态` 应当是 **1**（未扫描）—— 若它是 2
   而肉眼仍看到「没扫描过的植物是绿的」⇒ 把 `FloraScannedByEngineState=0`（不用换 DLL）
   并把这行日志发出来；
4. 不回归：F8 / 扫描仪自愈 / 展示柜拿空熄灭 / 换场景不崩 / 活人一个都不亮 /
   笔记黄 / 资源紫 / 杂项蓝 / 容器·尸体橙 / 门白 / 武器红·服饰品红。
5. 回退开关（都不用换 DLL）：`FloraScannedByEngineState=0`（只用资源链）、
   `FloraScannedByResource=0`（只信引擎状态 + 学到的绿）、两个都 0（= v4.24 观感）、
   `FloraScanProbeMax=0`（关探针）。

## 五、可复用经验（写给下一轮）

1. **「照抄引擎的一条链」不等于「这条链对谁都适用」** —— 引擎在链前面还有**类型门槛**
   （本例 `cmp [produce+0x2E],0x3F / jne`）。抄链时必须把**门前那几条 `cmp/jne` 一起抄**，
   否则「适用的对象」会悄悄变大（v4.25~v4.27 给植物接了矿脉的判据，用户一眼就看出来了）。
2. **同一个字段在引擎里可能有多个语义**（`+0x260` 既被当 LVLI 也被当 MISC 用）；
   「另一处代码这么读」**不能**当作「这一段也这么读」的理由 —— 要看**当前这一段**的断言。
3. **数据本身就带着分类证据**：植物的产出物品是 MISC、矿脉的产出是 LVLI（一条日志就能分开），
   排障时先把两类样本并排打出来（`produce` 与 `misc` 是不是同一个指针），根因立刻现形。
4. **优先找「引擎自己的查询函数」而不是自己复刻判定**：本轮找到的
   `ScannableComponent::GetOutlineState`（原生 `IsScanned` = 它 == 2）一条调用就顶掉
   整条资源链猜测，而且对植物 / 矿脉 / 气泉 / 液池通用。
   找法：`func.py strings "<可能的函数名>"` → `func.py rip <字符串 RVA>` 找注册点 →
   紧随其后的 `lea r9,[rip+实现]` 就是实现地址；再用 `versionlib.py id` 与 commonlibsf
   的 `IDs.h` 交叉确认 REL::ID。
5. **判据缓存要跟着判据的"粒度"走**：主判据是按**引用**回答的（物种 / 资源由引擎解析），
   缓存键就得是引用（并带上 base FormID 防指针复用）；继续按 base 缓存会把
   「同一 base 的不同实例」串在一起（本例恰好同物种同结果，但换个目标就会错）。
6. **诊断行要能独立定性**：本轮探针加了 `引擎状态=N`、统计行加了
   `引擎状态: 问/已扫描/未扫描` + `ready=资源链/主判据` —— 即使下一轮结论又错，
   日志也能直接指出是**哪条判据**给出错的值。
