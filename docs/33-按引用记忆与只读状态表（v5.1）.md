>

> 1，现在矿石、植物扫描前后颜色都是绿色

> 一句话结论（两条 bug 两个根因，都在「星球目标判据」这一小段里）：
> **① 「已扫描」记忆记错了粒度** —— v4.31~v5.0 记的是 **base（物种 / 资源）**，
> 于是扫过一个实例 ⇒ 同 base 的**所有**实例（含跨星球、跨存档）全变绿；
> **② 读引擎状态表用错了函数** —— v4.33 起调的 `0x17D5BE0` 是 Lookup**OrAdd**
> （查不到就**插入** + 对 REFR 引用计数 ++），而这一路是「每个 flora 引用 ×
> 每次判据未命中」都要跑的 ⇒ 引擎状态表与内存随游玩持续增长 —— 正好对上
> 「1.8.1 越玩越卡、1.7.3（v4.21，那时还没有这一步）没事」。
>
> 两个修法都很小：记忆粒度 base → **引用**；状态表读取 **只读走树**（零副作用）。

### 1.1 用户那一局的日志（`SAS_AlwaysScan.log`，2026-09-27 06:45~06:50，v5.0）

```

[06:48:57] flora scan: base=0x253227 记入单向学习表「已扫描」（资源链命中）
[06:50:58]   planet targets (窗口内): 未扫描=88 已扫描=264
            | 判据: 查询=392 命中=1001 链失败=352 缓存=16
            | 引擎状态: 问=392 已扫描=0 未扫描=40
            | 引擎学到: 绿=1 base 青=0 base
            | 学习表: 命中=1000 沿用=0 捡漏=0 落盘=10 写入=1
```

* **`引擎状态: 已扫描=0`** —— 这一局里引擎**一次都没说**「这个引用已扫描」；
* **`学习表: 命中=1000`** —— 而 MOD 的结论 74%（`已扫描=264 / 352`）来自学习表；
* 落盘文件当时长这样（11 行，全是 **base**）：

```
0x0025232B  0x00185479  0x00075CAD  0x00270039  0x001854C1
0x0025323A  0x00185489  0x0018547F  0x00185478  0x0027002C  0x00253227
```

⇒ 这些 base 是**别的星球 / 别的会话**里学到的（`0x1854xx` = 森林针叶植物、
`0x2523xx/0x2700xx/0x75CAD` = 矿脉 / 液体矿），而 MOD 把「base 已扫描」当成了
「这个引用已扫描」⇒ 到了新星球，同物种 / 同资源的**所有**实例一起绿 ——
这就是用户看到的「**扫描前后都是绿色**」（扫不扫都是绿，等于没有区分）。

★ `docs/26`（v4.28）里用户抱怨过一次**同一类**问题（「植物颜色错误，扫描前也显示成
扫描后的颜色」），当时的成因是「资源链判据被套到植物上」；v4.28 修了那条链，
却没发现 v4.31 新加的**学习表**又用另一种方式把同一个症状带了回来。

### 1.2 引擎自己的粒度：**按引用**（v4.28 已实证，结论没变）

`docs/26` §1.3：`ScannableComponent::GetOutlineState(ref)`（RVA `0x1306E80`）
= 原生 `IsScanned`（1 = 未扫描 / 2 = 已扫描），内部走
`ref+0xC8 → 组件 0x2A → GetCanonicalId → 玩家知识库 `+0x8B0``。**它按引用回答**，
所以 MOD 的记忆也必须按引用 —— base 只是「校验用的附属信息」。

### 1.3 「越玩越卡」的机制：`0x17D5BE0` 的**插入**路径（反汇编原文）

```
017D5BF7  mov rbx, qword ptr [rip + 0x47640e2]   ; rbx = *(RVA 0x5949CE0) = 哨兵节点
017D5BFE  mov rax, qword ptr [rbx + 8]           ; rax = 根（哨兵+8 = _Parent）
017D5C10  cmp byte ptr [rax + 0x19], sil         ; 节点 +0x19 = IsNil？
017D5C16  mov r8, qword ptr [rdx]                ; 键 = *slot = TESObjectREFR*
017D5C25  cmp qword ptr [rax + 0x20], r8         ; 节点 +0x20 = 键
017D5C29  jae 0x17d5c35 / 017D5C2F mov rax,[rax+0x10]   ; 右子 +0x10
017D5C35                 / 017D5C40 mov rax,[rax]        ; 左子 +0x00
…
017D5C53  cmp qword ptr [rdx], rax ; jae 0x17d5d15       ; 命中 → 返回 node+0x28
;; ↓↓↓ 没命中 = 插入（这就是问题所在）
017D5CA3  mov edx, 0x30                                   ; new 0x30 字节节点
017D5CC9  movabs rax, 0x80000200001
017D5CD3  lock xadd qword ptr [rdx + 8], rax              ; ★ 对 REFR 做引用计数 ++
017D5CDE  mov qword ptr [r8], rdx                         ; 节点 +0x20 = 引用指针
017D5CE1  mov dword ptr [r8 + 8], esi                     ; 节点 +0x28 = 状态 = 0
017D5D0D  call 0x3222e0                                    ; 红黑树插入
```

插入函数 `0x3222E0` 的第一条指令就是 **`inc qword ptr [rcx+8]`**（rcx = `0x5949CE0`）：

| 事实 | 值 |
| --- | --- |
| 状态表（红黑树）树头 | **RVA `0x5949CE0`**（`0x17D5BE0` 里 `lea rbp,[rip+0x4764066]`） |
| 树头 +0x00 | 哨兵节点指针（哨兵 +0x08 = 根） |
| 树头 +0x08 | **条目数**（`0x3222E0` 第一条指令 `inc [rcx+8]`） |
| 节点 +0x00 / +0x08 / +0x10 | 左子 / 父 / 右子 |
| 节点 +0x19 | IsNil（哨兵标志） |
| 节点 +0x20 | 键 = `TESObjectREFR*` |
| 节点 +0x28 | 值 = outline 状态 dword（★ MOD 要读的就是它） |
| 查不到时 | **插入新节点 + 对引用 `lock xadd [ref+8]`（引用计数 ++）** |

⇒ v4.33 把这一步（`docs/31` 的「⓪.5 状态表捡漏」）从「只在举着扫描仪时」改成
「**每次判据未命中都读一眼**」，而它调的是 `0x17D5BE0` ⇒

* 每个 flora 引用**第一次**被读到就往引擎表里塞一条（0x30 字节 + 树节点）；
* 每条都**持有该 REFR 的引用计数**（cell 卸载后也放不掉）；
* 这些条目只有引擎自己拆 Monocle HUD（`0x17D4B30`）时才会被清 —— 玩家不开关
  扫描仪就不会清。

⇒ 「玩得越久，越卡」；而 **1.7.3 = v4.21 根本没有这一步**（判据链是 v4.25 才出现的），
与用户报告的时间线完全对上。

### 1.4 v5.0 的「不写状态表」承诺被自己破了

`docs/32` / v5.0 的设计前提是「**状态表一个字节都不动**（不调 LookupOrAdd / Set）」，
但 v4.33 留下的 ⓪.5 一直在调 `LookupOrAdd` —— 自建通道模式（2.0）里它是**唯一**
还在写引擎状态表的地方。v5.1 把它改成只读之后，这条承诺才真正兑现。

## 四、验收判据（下一次进游戏）

1. 启动日志：
   ```
   SAS_AlwaysScan v5.1.0 loading
   config: 星球目标记忆(v5.1) -> 粒度 = **引用** … 引擎状态表探针 = **只读走树（RVA 0x5949CE0 …）**

   ```
   （如果是老安装、旧文件还在，会多一行 `；★ 旧格式（base 级）行被忽略 N 条`）
2. ★★ **肉眼**：找一个没扫过的植物 / 矿脉 ⇒ **青色**；扫它 ⇒ **绿色**；
   旁边**同 species / 同资源的另一个** ⇒ 仍然**青色**（这是本次修复的核心判据）。
3. ★ **肉眼**：以前扫过的那些实例（本存档内）依然保持绿色（记忆没丢）；
4. 统计行出现 `按引用记忆(★v5.1): 命中=… 绿=… 青=… 总量=…` 与
   `引擎状态表: 条目=… 读=… 绿=… 青=… 无条目=…`；
5. ★ **长会话**（≥1 小时）：`引擎状态表: 条目=` 应**基本稳定**（同场景上下抖动是引擎
   自己写状态造成的，**不应单调增长**）；`timing: scan avg` 不随游玩时间上升；
6. 不回归：F8 / 扫描仪自愈 / 展示柜拿空熄灭 / 换场景不崩 / 活人一个都不亮 /
   分组配色不变（红 / 橙 / 紫 / 绿 / 白 / 青绿）。

★ **待观察（若用户仍报「矿石在没扫过的星球上就是绿的」）**：排查顺序 =
① 看统计行 `按引用记忆: 绿=/青=`、`引擎状态: 问=/已扫描=/未扫描=` ——
   若「已扫描」也在涨，说明是**引擎自己**这么判的（② 资源链判据与引擎 0x159ED90
   同口径：资源进了勘测数据 ⇒ 该资源的所有矿脉都是绿）；
② 若「已扫描=0」而 `绿=` 仍在涨，那只可能是落盘文件里真有这些引用（删文件复测）；
③ 只有在 ① ② 都不成立时才去怀疑 `IsResourceScanned`（0x1597A50）的**作用域**
   （引擎调用点的参数是否比我们多传了一个「当前星球」—— docs/26 §1.2 只记了 call，
   没记参数）。这一条本轮**没有**动，因为它 v4.28 起就被用户确认「矿石是好的」。

★ **一次性副作用（预期内，要提前告诉用户）**：旧版本记的是 base 级、且旧文件会被忽略 ⇒
升级后**以前扫过的实例会先显示为青色**；扫它一次（或随便举一下扫描仪）就会重新记上
（这次是按引用记的）。这正是本次修复要的「重置」。

## 五、经验（写给下一轮）

1. **「记忆」的粒度必须与「事实」的粒度一致**：引擎的「已扫描」是**按引用**回答的，
   我们却按 base 记 —— 这种「比事实更粗的缓存」一定会以「到处都对」的假象暴露出来
   （用户的原话是「扫描前后都是绿色」）。
2. **调引擎函数前先问一句「它有没有副作用」**：名字里带 `OrAdd` / `GetOrCreate` /
   `Ensure` 的函数都会**写**。高频路径（每引用 × 每轮）上，一次「顺手读一眼」就足以
   变成泄漏 —— 而且它不会立刻表现为卡，而是「越玩越卡」。
3. **只读的替代方案通常存在**：这次的解法只是「自己走一遍那棵红黑树」——节点布局
   在反汇编里就摆着（+0x19 IsNil / +0x20 键 / +0x28 值），代价是十几行代码。
4. **诊断值要给「可证伪的数字」**：`引擎状态表: 条目=N` 就是这种数 —— 修完以后
   用户自己能盯着它看「是不是还在涨」，不需要再看我们的推理。
5. **同一类 bug 会换一条路回来**：v4.28 修「植物没扫就绿」只修了「资源链」那条路，
   两条版本之后「学习表」又用另一种方式制造了同一个症状 ⇒ 修完要把**所有**判据
   都按同一把尺子过一遍（这次过完之后，「绿」只可能来自三个按引用的权威来源）。
