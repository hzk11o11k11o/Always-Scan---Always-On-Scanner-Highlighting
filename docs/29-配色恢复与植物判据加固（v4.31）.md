# 29 · 容器橙 / 门白恢复 + 植物「低概率变回青色」修复（DLL v4.31.0 / 发布版 1.7.9）

> 建立：2026-09-26。触发：用户实测反馈（两条原文）——
>
> ```
> 1，上次改动把容器/尸体/门的颜色也变了，不能保持之前版本的颜色吗？
> 2，已经扫描完成的植物有低概率变成扫描前的颜色，但是开启扫描仪再关闭，
>    就又会变成扫描后的颜色，检查
> ```

一句话结论：
① **配色重排** —— 0/1 归还引擎后全表只剩 **2/3/6/9/10 五个可借槽位**，而「容器橙 / 门白」
必须回来 ⇒ 用「服饰品红」「笔记黄」让位：容器 / 尸体 = 9（橙）、门 = 6（白，**引擎唯一
不写的槽位**）、武器 = 10（红）、服饰 = 1、笔记 = 0（不覆盖 = 原版淡蓝白 / 青）。
② **植物判据加固** —— 旧版 30 秒 TTL 一过就重问引擎，引擎偶尔「拿不到 / 答未扫描」
⇒ 已确认的「绿」被擦成「青」；修法 = **⓪ 单向学习表**（权威确认过「已扫描」的 base
本会话直接命中，不再重问）+ **重问拿不到权威答案时沿用旧结论**。

## 一、问题 1：容器 / 尸体 / 门的颜色 —— 为什么上一版会变，怎么恢复

### 1.1 约束（v4.30 之后的既定事实）

| 槽位 | 引擎用它画什么 | 能不能覆盖 |
| --- | --- | --- |
| 0 / 1 | **通用引用（含活人 NPC）**（远 / 近） | ❌ 用户实测报告过「行人变赏金色」（docs/28） |
| 4 / 5 | **已扫描的星球目标**（远 / 近）= 绿 #27C684 | ❌ 用户要求「扫描后变绿」（docs/23） |
| 7 / 8 | **未扫描的星球目标**（远 / 近）= 青脉冲 | ❌ 用户要求「扫描前青」（docs/21/22） |
| 2 / 3 / 6 / 9 / 10 | 4 = 已扫描星球目标（远）……见下表 | ✅ 可借（代价见下） |

⇒ 全表 11 个槽位里**只有 2/3/6/9/10 五个能借**（6 是引擎全镜像不写的；9/10 引擎目标罕见）。

### 1.2 原生色表（docs/16 §2.1 实测，本轮的关键依据）

| state | 名字 | 原生 ref 色 | 备注 |
| --- | --- | --- | --- |

### 1.3 需求 vs 槽位的算术（为什么必须有人让位）

用户要的同时存在的外观：容器 / 尸体**橙**、门**白**、武器**红**、杂项**蓝**、
资源**紫**、NPC **原版青**、星球目标**扫描前后区分**、**（历史）**服饰品红 / 笔记黄。

- 免费（原生色直接可用）：杂项蓝 = 2/3/6、容器橙 = 9、武器红 = 10；
- 必须覆盖：门白、资源紫、**服饰品红**、**笔记黄** —— 四个需求，而剩余可借槽位
  （扣除杂项 / 容器 / 武器已占的 2、9、10）只有 **3、6 两个**。

⇒ **数学上只能五选五**。本轮的取舍（按用户价值排序）：

| 项 | 结果 | 理由 |
| --- | --- | --- |
| 容器 / 尸体 = 9（橙 #FF9500）、门 = 6（白 #FFFFFF） | ✅ 恢复 | 本轮用户明确要求；9/6 的引擎代价最小（6 = 引擎从不写） |
| 武器 = 10（红 #FF2E2E） | ✅ 保留 | 10 的引擎目标罕见（城市实况约 11 个元素，v4.30 实测） |
| 杂项 = 2（蓝）、资源 = 3（紫） | ✅ 保留 | 用户历史要求（v4.17 / v4.22） |
| **服饰 = 1（不覆盖 = 原版淡蓝白）** | ⚠️ 让位 | 品红与「容器橙 / 门白」不可兼得 |
| **笔记 = 0（不覆盖 = 原版青）** | ⚠️ 让位 | 黄与「门白」不可兼得（6 只有一个） |

⇒ **最终覆盖槽位：2（杂项蓝，= 原生值）、3（资源紫）、6（门白）、9（容器 / 尸体橙）、10（武器红）**
—— 与 v4.30 的覆盖数量相同（5 个），但 0/1/4/5/7/8 依旧一个字节不写（NPC / 星球目标的原版色不动）。

### 1.4 想要「服饰品红 / 笔记黄」回来的两个互换（INI，不用换 DLL）

```ini

StateApparel=10
ColorApparel=FF3BD4
StateWeapon=0        ; 不覆盖 = 原版青

; 笔记黄回来（代价 = 门失去白色）

StateDoor=0          ; 不覆盖 = 原版青
```

★ 注意：`StateXxx` 与 `ColorXxx` 必须成对改；「同 state 撞色 / 撞透明度」会有 WARN（保留先出现的）。
完整推理见 INI 里的 v4.31 段（`resources/SAS_AlwaysScan.ini`）。

## 二、问题 2：植物「低概率变回青色」的根因与修法

### 2.1 旧行为（v4.28 ~ v4.30）

```
判据缓存（引用级，TTL = kFloraScanCacheTtlMs = 30 秒）
  ↓ 过期
擦掉旧值 → 重问引擎 `GetOutlineState(ref)`（1 = 未扫描 / 2 = 已扫描）
  ↓ 引擎这次答 0（拿不到）/ 1（未扫描）—— 组件重建 / 时序等原因
  ⇒ 「已扫描」结论被推翻 ⇒ 挂回 StateFlora（7 = 青）
```

用户看到的：「已经扫描完成的植物**低概率**变成扫描前的颜色，但是**开启扫描仪再关闭**，
就又会变成扫描后的颜色」——后半句正是 `NoteFloraEngineState`（v4.26 的「引擎亲手画过绿」
学习）在举扫描仪时把绿学回来。

### 2.2 v4.31 的两层修复

| # | 改动 | 说明 |
| --- | --- | --- |
| ① | **⓪ 单向学习表**（`floraEngineSeen`，base 级） | **三个权威来源**（引擎状态 == 2 / 资源链命中 / 引擎亲手画过绿）**首次**确认「已扫描」时写入 `true`；之后这个 base 的任何引用直接命中（不再重问引擎、不再走链） |
| ② | **重问拿不到权威答案 ⇒ 沿用旧结论** | 缓存过期重查时，若「引擎没答已扫描」且「资源链没走通」（= 没有权威答案），而旧值是 `true` ⇒ 保持 `true`（已扫描单向：勘测数据不会退回） |

- 学习表**只写 true、不写 false**（「见过青」只记一笔诊断，不参与判定）；
- 清空点与旧版相同：**换场景 / 读档**（`ResetForNewScene` ≈ 勘测数据可能完全不同）；
  **放下扫描仪不清**（那一局扫描结果刚变，但「已扫描」只会增加）。

### 2.3 新增日志（可 grep 验收）

```
flora scan: base=0x… 记入单向学习表「已扫描」（引擎状态 GetOutlineState(ref)=2）->
            本会话不再重问引擎（换场景 / 读档才清；这是「变回青色」的根治）
flora scan: base=0x… 判据 = 单向学习表（本会话已确认「已扫描」）-> 已扫描 ⇒ 状态 5
  planet targets (窗口内): … | 学习表: 命中=… 沿用=…（★ v4.31：都 > 0 = 「变回青色」的修复在干活） | …
```

## 六、可复用经验

1. **「借槽位」的账要按「必须存在的颜色」算**：v4.30 只算了「归还 0/1 后谁住哪」，
   没算「用户回头要哪些颜色」—— 本轮把账重算（五个可借槽 vs 八个需求）才定性
   「必须有两项让位」，而不是「改错了、改回来」。
2. **原生色表是「免费色」的来源**：9 原生橙、10 原生红、2/3/6 原生蓝 —— 这三处
   可以直接「不覆盖」拿到用户要的色，不需要占覆盖预算。**先查原生色，再谈借槽**。
3. **6 号槽（引擎从不写）是全表最安全的一个**：「门白」放在 6 = 对原版零影响；
   9/10 只是「罕见」，6 是「从不」—— 优先级最高。
4. **判据缓存过期后的「重问失败」也是一种 bug 来源**：TTL 机制默认「重问结果总是可信」，
   而对**单向事实**（已扫描、已完成、已解锁）来说这个默认是错的 ——
   「拿不到 / 答否」时应当**沿用旧结论**，并把「权威确认过的值」升级为**长期记忆**。
5. **用户描述里的「开启 X 再关闭就恢复」是根因的强提示**：它精确指出了
   「哪条路径能重新确认事实」（本例 = 举扫描仪 ⇒ 引擎画绿 ⇒ 被学到），
   顺着这条线就能找到「另一条路径在撤销它」。
6. **让位项要「如实记录 + 给出互换写法」**：用户对颜色的偏好会变，只要把
   「五选五」的约束与两行 INI 互换写进文档与 INI 注释，下一轮就不会再当 bug 报回来。
