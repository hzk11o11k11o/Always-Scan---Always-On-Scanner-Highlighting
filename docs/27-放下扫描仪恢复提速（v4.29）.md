## 二、「植物和矿石的高亮速度明显低于其他物品」的检查

### 2.1 结论先行：三条机制（都有日志证据）

| # | 机制 | 证据（v4.28 那一局） | 影响 |
| --- | --- | --- | --- |
| ① | **放下扫描仪 ⇒ 引擎拆表 ⇒ 全量重挂，且重挂按 64 条/轮分摊** | `native outline: 引擎侧高亮疑似丢失（MonocleMenu 关闭）-> 268 个已挂目标转入「待重申」（按每轮 64 条预算重挂，累计 10 次）`——这一局共触发 **12 次** | 268 个 ÷ 64 ≈ **5 轮 ≈ 1.05 秒**才铺完；**「刚扫完 ⇒ 青变绿」也排在这条队列里**（按距离消耗同一份预算） |
| ② | **每次放下扫描仪清空 flora 判据缓存** | `flora scanned: 判据缓存作废（放下扫描仪，清了 56 条）-> 下一轮重新问引擎` | 下一轮对全部 flora 重新查引擎（例：+56 次 `GetOutlineState` + 47 次资源链），`timing2: loop avg=13~30ms`（平常 0~2ms） |
| ③ | **候选上限 256 + 按距离排序** | 大场景 `cand=278 sel=256`；flora 每轮只选中 4~10 个（候选 16 个）⇒ 一半植物排队 | 部分植物「晚亮 / 一亮一灭」（1.5 秒宽限后掉队被摘） |

### 2.2 机制 ① 的完整链路（主因）

1. 引擎在扫描仪生命周期结束时销毁 11 个 HighlightManager + 清空「引用→状态」表
   （RVA `0x17D4B30`，v3.2 已实证）⇒ MOD 账本必须整体作废重挂。
2. `DetectEngineOutlineLoss` 命中 `MonocleMenu 关闭` ⇒ `MarkAllForReassert`
   （把每个已挂条目的 `reassertMs=0`）。
3. `SyncNativeOutline` 第 3 步按 `a_chosen`（**按距离排序**）逐个重挂，**每轮预算
   `MaxOutlineOpsPerScan=64`**（v2.2 为「零突发」定的值）。
4. 268 个目标 ⇒ 5 轮（≈1.05 s）。**「青→绿」的状态变化同样走这条队列**
   （`it->second.state != c->state` 分支），所以「刚扫完的植物 / 矿脉」
   在视觉上明显晚于「本来就亮着、颜色不变」的其它物品。

★ 为什么其它物品「看起来不慢」：它们的颜色不变化，玩家不会盯着它们的「重新挂载」；
而星球目标是**在放下扫描仪那一刻才换色**（青→绿），排队延迟被直接看到。

### 2.3 机制 ② / ③ 的定位（本轮不改，保留观察）

- ② 是**正确性**要的：这一局很可能刚扫成某个目标，不清缓存最多要等 30 s（TTL）才换色。
  成本可控（几十次引擎调用 ≈ 十几 ms，分摊在 1~3 轮）。
- ③ 是**容量**问题：`MaxTargets=256` 在大场景会被占满。若实测仍见「远处的植物
  不亮」，下一步考虑提高上限或给「已挂目标」增加黏性权重（本轮不动）。

## 三、v4.29 改动

| 项 | 内容 |
| --- | --- |
| 新键 | `ResyncBoostMs`（默认 **2500**）/ `ResyncBoostBudget`（默认 **192**）—— 任一设 0 退回旧行为，不用换 DLL |
| ① 提速窗口 | `MarkAllForReassert` 时记 `resyncBoostUntilMs = now + ResyncBoostMs`；窗口内 `SyncNativeOutline` 的每轮预算由 64 提到 192（**只提速不降速**：预算比 boost 大时取原值）⇒ 268 个 ≈ **2 轮 / 0.42 秒** |
| ② 状态变化优先 | `SyncNativeOutline` 新增 **2.5 步**：先把「已挂但 `state` 不一致」的条目（青↔绿）摘 + 挂（不排队），处理完把 `reassertMs` 复位成 `nextMs` ⇒ 第 3 步不会重复摘挂；≥8 个时打一行 `状态变化优先换色 N 个` |
| 配置 / 日志 | 启动日志新增 `config: resyncBoost=…ms budget=…`；resync 那行括号里写明「未来 Nms 内提速到每轮 M 条 + 状态变化优先」 |
| 版本 | DLL **4.29.0**（`xmake.lua` ×2 / `main.cpp` ×1）；N 网公开版仍 **1.7.7** |

### 3.1 为什么不是别的方案

- **不做「放下后不清缓存」**：这一局刚扫过的目标必须立刻换色，缓存必须作废（正确性）。
- **不做「一次性全挂 268 个」**：`UnoutlineRef` 走 3D 图 visitor（较贵），集中做完会有
  可见卡顿（v2.2 引入预算就是为此）；192 条/轮是「快」与「不卡」的折中（可由 INI 回调）。
- **不动 `MaxTargets`**：缺乏「远处植物被挤掉」的直接实证（本轮场景里被挤的是全部类型的
  尾部），先不加变量。

## 五、待实测验收点（v4.29）

① 启动日志出现 `SAS_AlwaysScan v4.29.0 loading` +
   `config: resyncBoost=2500ms budget=192 -> …`；
② ★★ 肉眼（核心）：在**目标多**的场景（物品 + 植物 / 矿脉混在一起）**举起扫描仪扫一圈
   再放下** ⇒ 全部高亮应在 **约 0.4 秒内**回来（旧版约 1 秒），其中「刚扫过的」植物 / 矿脉
   **先变绿**（`状态变化优先换色 N 个` 会出现在日志里）；
③ resync 那一行应带 `；未来 2500ms 内提速到每轮 192 条 + 状态变化优先（ResyncBoostMs / ResyncBoostBudget）`；
   统计行的 `timing2: sync avg/max` 不应出现明显大值（>50ms 的话把 `ResyncBoostBudget` 降到 96 / 64）；
④ 回退（不用换 DLL）：`ResyncBoostMs=0` 或 `ResyncBoostBudget=0` = 退回 64 条/轮旧行为；
⑤ 不回归：F8 / 扫描仪自愈 / 展示柜拿空熄灭 / 换场景不崩 / 活人一个都不亮 /
   笔记黄 / 资源紫 / 杂项蓝 / 容器·尸体橙 / 门白 / 武器红·服饰品红 / 植物没扫过青、扫过绿。

## 六、可复用经验

1. **「谁在排队」比「谁慢」更重要**：本轮所有目标共用同一条重挂队列与预算，
   差异只来自「谁的状态会变」——**会变色的那个永远显得慢**。定位这类问题的第一问：
   「这个操作在队列里排第几？谁在它前面？」
2. **「零突发」的预算值要跟着「恢复时延」一起验收**：64 条/轮是 v2.2 为「不卡」定的，
   但没人量过「268 个要多久」——1 秒的恢复期在游玩里是可感知的。**性能开关的两端
   （上限 / 时延）都要写进验收判据。**
3. **提速要用「窗口 + 可回退」**：只在「刚放下扫描仪」这 2.5 秒里放大预算（那时玩家
   正盯着屏幕），并把两个数都开放到 INI ⇒ 出问题不用换 DLL（本项目一贯做法）。
4. **改「优先顺序」要检查下游分支是否重复处理**：2.5 步处理完必须把 `reassertMs`
   复位成 `nextMs`，否则第 3 步会把同一目标**再摘挂一次**（双层描边 / 白耗预算）。
5. **部署脚本的「保留旧 INI」分支**：当新模板带新键时，`build-sas.ps1` 不会覆盖
   部署 INI，而是写 `*.ini.new` + WARN。**换模板前必须先证明「部署文件 = 上一版模板」**
   （`git cat-file blob HEAD:... > tmp` + `git diff --no-index --ignore-cr-at-eol --exit-code`），
   否则会丢用户自定义值。
